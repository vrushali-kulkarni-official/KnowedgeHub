00 · The foundation The testing mindset.

Before we touch any tool, you need three mental models. They will quietly decide every decision you make for the rest of this guide.

1. The cost of a bug grows 10× every step it survives

A typo caught by your editor costs 0 minutes. A typo caught by your unit test costs 2 minutes. A typo caught in staging costs 30 minutes. A typo that ships to a paying customer costs hours — or a churned account. The single biggest reason to test is to find bugs at the cheapest possible moment.

Caught in editor
$0
Caught in unit test
~$5
Caught in PR review
~$30
Caught in staging
~$150
Caught in production
~$1,500+
Caught by customer
∞ trust

Numbers are the industry rule of thumb (IBM Systems Sciences Institute, refreshed by many since). The point isn't precision — it's that you want to push detection as far left as possible.

2. The testing pyramid tells you how much of each kind to write

E2E / UI · a handful
Integration / API · dozens
Component · hundreds
Unit · thousands
Static (lint / types) · automatic, on every keystroke

The bottom of the pyramid is the cheapest, fastest, most reliable layer. The top is the slowest, flakiest, most realistic layer. So you write a lot at the bottom and a little at the top. If your E2E suite is bigger than your unit suite, something is off.

3. Shift-left AND shift-right

Shift-left = move testing earlier in the timeline (lint on save, PR checks, fast unit tests). Shift-right = keep testing after deploy (synthetic checks, real-user monitoring, chaos experiments). In 2026 the two are not opposites — they're the same loop, just at different speeds.

The 2026 twist: AI assistants now write a large share of your code. That same AI can also write your tests, generate edge cases, and judge subjective outputs like LLM responses. We'll cover that in section 13. For now, just remember: AI-generated code is not tested code until your tests pass.

The journey Stage by stage, what you test and when.

Below is the spine of this whole guide. We'll follow a single feature from idea to production — say, "users can upload a PDF and ask questions about it" — and look at every kind of test that touches it along the way. Each stage answers: why this test, how to do it in your stack, and when in the journey.

Stage 0

Before any code is written.

This is the stage most beginners skip. Don't.

Why this stage exists

A bug in your requirements is the most expensive bug of all — because everything you build on top of it will also be wrong. Testing starts by testing the idea.

What you actually do

  • Threat modeling — draw the data flow, list what could go wrong (STRIDE is the classic 2026 standard).
  • Acceptance criteria — write Given/When/Then for each user story. These become your first tests.
  • Test plan — one paragraph: what types of tests will cover this feature?

Example: "Upload PDF and ask questions" — acceptance criteria

# Given a logged-in user
# When they POST /v1/docs with a 1 MB PDF
# Then the API returns 202 with a doc_id
# And within 30 s the doc is searchable
# And asking "what is page 3 about?" returns an answer grounded in the PDF

These four lines are tests. They will resurface, almost word-for-word, in your E2E and integration tests later.

For your AI SaaS specifically: threat-model the prompt. What if a user uploads a 1 GB PDF? What if the PDF is just a picture of text (OCR needed)? What if a user uploads someone else's confidential data? Decide before coding — every decision becomes a test.
Stage 1

The first line of code.

You're typing a function. The cheapest test possible fires before you save the file.

What you test (automatically)

  • Linting — style + obvious bugs (ruff).
  • Formatting — black / ruff format.
  • Type checking — mypy or pyright.
  • Secret scanning — gitleaks, trufflehog.

Why it matters

These run on every save (in VS Code) and on every commit (pre-commit hook). They catch 30–50% of beginner mistakes for $0 of effort. They never get tired, never get skipped, and cost milliseconds.

The pre-commit hook that protects you

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.13.0
    hooks: [{id: mypy, additional_dependencies: [types-all]}]
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.4
    hooks: [{id: gitleaks}]

When in the journey: every keystroke (via VS Code) and every commit (via pre-commit). This is the bottom of the pyramid — but it's actually below the pyramid: it's static testing and it never breaks.

Stage 2

Pure functions and small units.

You write a function like chunk_text(pdf_text). It takes input, returns output, no DB, no network, no LLM. This is the happiest place to test.

What you test

  • Unit tests — one function, one behavior.
  • Property-based tests — describe a property, the tool invents the inputs (hypothesis).
  • Snapshot tests — record the output once, alert on change.
  • Mutation testing — verify your tests would actually catch a bug (mutmut).

Why this stage is the foundation of everything

Fast (milliseconds), deterministic (same input = same output), isolated (no setup), easy to write. If you skip these, every later test has to compensate — and the pyramid inverts.

Your stack: a real unit test (pytest)

# tests/unit/test_chunking.py
import pytest
from brain.chunking import chunk_text

def test_chunk_text_splits_on_paragraphs():
    text = "First paragraph.\n\nSecond paragraph.\n\nThird."
    chunks = chunk_text(text, max_chars=30)
    assert chunks == ["First paragraph.", "Second paragraph.", "Third."]

def test_chunk_text_never_exceeds_max():
    text = "a " * 10_000
    chunks = chunk_text(text, max_chars=500)
    assert all(len(c) <= 500 for c in chunks)

@pytest.mark.parametrize("text,size", [("", 0), ("x", 1), ("x"*200, 2)])
def test_chunk_text_edge_cases(text, size):
    assert len(chunk_text(text, max_chars=100)) == size

Property-based test (hypothesis) — the 2026 pro move

from hypothesis import given, strategies as st

@given(st.text(min_size=0, max_size=2000))
def test_chunk_text_never_crashes_on_any_string(s):
    chunks = chunk_text(s, max_chars=100)
    # Property: every chunk is a substring of the original,
    # and the join reconstructs the input.
    assert "".join(chunks) == s
    assert all(c in s for c in chunks)
Why bother with property tests? A junior dev can think of 5 examples. Hypothesis tries thousands of weird strings — empty strings, emoji, control characters, 1 MB blobs. It finds the bug you didn't know to test for. It's free with hypothesis.

When in the journey: every time you write a function. Tests live next to the code in tests/unit/. Runs in <1 s on every save and <10 s in CI. This is the layer you write the most of.

Stage 3

Components — bigger chunks that work together.

Your DocumentService class now ties together: download from S3, extract text, chunk, embed, store in Qdrant, save metadata in Postgres. It's still a single Python process, but it does real work.

What you test

  • Component tests — the class with its real collaborators, but using fakes for slow/expensive ones.
  • Contract tests — "I promise to send Qdrant vectors of this shape" (Pact).
  • Behaviour tests — does the doc end up in both Postgres and Qdrant?

Why it matters

You catch integration bugs (wrong column name, wrong vector dimension) without paying the cost of a real network. The fake services give you speed; the real Postgres/Qdrant containers give you realism. You want both.

Your stack: component test with fakes

# tests/components/test_document_service.py
import pytest
from services.document_service import DocumentService
from services.fakes import FakeS3, FakeEmbedder

@pytest.fixture
def svc(pg_session, qdrant_container, fake_embedder):
    return DocumentService(
        s3=FakeS3(),
        embedder=fake_embedder,         # fake — fast, deterministic
        qdrant=qdrant_container,        # real — but isolated per test
        db=pg_session,
    )

def test_upload_creates_doc_and_chunks(svc, qdrant_container):
    doc_id = svc.upload(b"hello world", filename="a.txt")
    assert svc.get(doc_id).status == "ready"
    assert qdrant_container.count("docs") == 1
    # Property: every chunk's vector has the right dimension
    pts = qdrant_container.scroll("docs", with_vectors=True)
    assert all(len(p.vector) == 768 for p in pts)

When in the journey: every time you finish a service. Runs in a few seconds. Lives in tests/components/. This is the layer the 2026 pro teams also run locally with Docker Compose for parity with prod.

Stage 4

Services & APIs — wiring it up to the world.

Your FastAPI app is alive. Routes exist, Postgres is real, Qdrant is real, Redis caches real things. Now you verify the system behaves correctly when everything talks to everything.

What you test

  • Integration tests — full stack with real Postgres, Qdrant, Redis, but in Docker.
  • API tests — every endpoint, every status code, every error path.
  • Schema-fuzz testing — schemathesis hammers your OpenAPI schema with weird inputs.
  • Migration tests — Alembic upgrade → downgrade → upgrade must round-trip.

The "Testcontainers" pattern (the 2026 default)

Don't mock Postgres. Don't mock Qdrant. Spin up a real Postgres in Docker for the test, run your test, throw it away. testcontainers-python does this in 4 lines. You get the speed of mocks with the realism of prod.

Your stack: API integration test

# tests/integration/test_docs_api.py

Schemathesis — let the computer break your API

# tests/integration/test_api_contract.py

from main import app

Stage 5

Auth, security, and the bad guys.

You're exposing your app on the internet. Time to assume the worst — and prove it can't happen.

What you test

  • Auth tests — invalid tokens, expired tokens, missing scopes, wrong audience.
  • Authz tests — user A cannot read user B's docs (IDOR bugs).
  • SAST — static analysis of your code (Bandit, Semgrep, GitHub CodeQL).
  • Dependency scan (SCA) — known CVEs in your libraries (pip-audit, Snyk, Trivy).
  • Secret scan — already in pre-commit, but also in CI on every push.

Why security tests are special

Every other test asks "does the happy path work?" Security tests ask "what if someone tries to break it on purpose?" You need both questions, every release.

Your stack: auth & authz tests

def test_missing_token_returns_401(client): ...
def test_expired_token_returns_401(client, expired_token): ...
def test_wrong_audience_returns_401(client, wrong_aud_token): ...
def test_user_cannot_read_other_users_doc(client, user_b_token, doc_of_a):
    r = client.get(f"/v1/docs/{doc_of_a.id}",
                   headers={"Authorization": f"Bearer {user_b_token}"})
    assert r.status_code == 403

@pytest.mark.parametrize("payload", [
    {"role": "admin"},                   # trying to escalate
    {"sub": "00000000-0000-0000-0000-000000000000"},
    {"exp": 99999999999},                # far-future exp
])
def test_jwt_tampering_is_rejected(client, payload, valid_token):
    forged = jwt.encode(payload, "wrong-secret", algorithm="HS256")
    r = client.get("/v1/me", headers={"Authorization": f"Bearer {forged}"})
    assert r.status_code == 401

Static analysis in CI

When in the journey: auth tests live with integration tests. SAST/SCA run on every PR. White-box testing (where you know the code) is what SAST does. Black-box testing (where you don't) is what your pen-tester does — see section 14.

Stage 6

AI / LLM features — the hard one.

This is the stage that didn't exist in 2018 and now consumes half your test budget. A function that calls an LLM is not deterministic. So you can't just check ==. You need a new vocabulary.

What you test

  • Retrieval quality — does Qdrant return the right chunks? (Recall@K, MRR).
  • Answer quality — is the LLM's answer correct, grounded, relevant? (LLM-as-judge).
  • Hallucination — does the answer invent facts not in the PDF? (DeepEval, RAGAS).
  • Latency & cost — p50 / p95 latency, tokens per request, dollars per request.
  • Refusal & safety — does it refuse to answer when it should?
  • Prompt regression — change a prompt, did quality go up or down?
  • LangGraph state tests — does the agent reach the right state?

Why this is its own discipline

An LLM can pass 100 traditional tests and still be terrible for users. Quality is statistical, not boolean. So you build eval datasets (50–500 question/answer pairs), run them on every prompt change, and track a quality score over time.

Your stack: a RAG eval test (DeepEval + RAGAS)

# tests/ai/test_rag_quality.py
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import (
    AnswerRelevancyMetric, FaithfulnessMetric, ContextualRecallMetric
)
from brain.rag import answer

EVAL_SET = [
    LLMTestCase(
        input="What's the refund policy on page 4?",
        expected_output="30-day money-back guarantee, no questions asked.",
        actual_output=answer("What's the refund policy on page 4?"),
        retrieval_context=[...],   # populated by your RAG
    )
]

def test_answer_is_faithful_to_pdf():
    assert_test(EVAL_SET[0], [
        FaithfulnessMetric(threshold=0.85),       # no hallucination
        AnswerRelevancyMetric(threshold=0.8),     # actually answers
    ])

LangGraph — testing the agent's state machine

from brain.graph import build_graph

def test_graph_reaches_answer_state():
    graph = build_graph()
    result = graph.invoke({"question": "summarize page 2"})
    # The graph should have visited 'retrieve' then 'answer' then END
    assert [n.name for n in result["__trace__"]] == ["retrieve", "answer"]
    assert "answer" in result
    assert result["citations"]                   # always cites sources

def test_graph_refuses_when_no_docs_found():
    graph = build_graph()
    result = graph.invoke({"question": "irrelevant question",
                           "indexed_docs": []})
    assert result["answer"].startswith("I don't have information")
For your free-tier Gemini setup: add LangSmith tracing (free tier) so every test run logs the full prompt, retrieved chunks, and response. You'll thank yourself the first time quality mysteriously drops.

When in the journey: eval tests run on every PR that touches brain/ or prompts. The eval set lives in tests/ai/golden_set.jsonl and grows every time a user finds a real failure.

Stage 7

UI & end-to-end.

Your Streamlit (or React) page renders, the user clicks, things happen, answers appear. Time to verify the whole story as a real user would.

What you test

  • Component tests (UI) — one widget behaves correctly (Streamlit AppTest).
  • E2E tests — drive a real browser through the real user journey (Playwright).
  • Visual regression — screenshot diffs catch "I accidentally moved that button" (Percy / Playwright snapshots).
  • Accessibility — axe-core inside Playwright.

The rule: very few E2E tests, all of them critical.

E2E is slow, flaky, and expensive. So you only automate the money path: signup → login → pay → first success. Everything else stays at a lower layer.

Your stack: Playwright E2E

# tests/e2e/test_upload_flow.py
from playwright.sync_api import expect

def test_new_user_can_upload_and_ask(pw_page, fresh_user):
    pw_page.goto("/signup")
    pw_page.fill("input[name=email]", fresh_user.email)
    pw_page.fill("input[name=password]", "Strong-Pass-123!")
    pw_page.click("button[type=submit]")

    pw_page.set_input_files("input[type=file]", "tests/fixtures/sample.pdf")
    pw_page.click("text=Upload")
    expect(pw_page.locator("[data-test=upload-status]")).to_have_text("Ready", timeout=30_000)

    pw_page.fill("textarea[name=question]", "What's on page 2?")
    pw_page.click("button:has-text('Ask')")
    expect(pw_page.locator("[data-test=answer]")).to_be_visible()
    expect(pw_page.locator("[data-test=citations] li")).to_have_count(>=1)

When in the journey: nightly + before any release. Not on every PR (too slow). Use the same Playwright suite for smoke testing right after deploy — see stage 8.

Stage 8

Pre-deploy gate — "is this build safe to ship?"

You have a Docker image. You are about to push it to your Ubuntu server. One last wall of checks. If any of these fails, the deploy is blocked.

The wall of checks

  • Smoke Spin up the image, hit /healthz, hit one happy-path endpoint.
  • Container scan Trivy / Grype on the image — known CVEs in your base image.
  • SBOM Software Bill of Materials — list of every dep (CycloneDX).
  • DAST Dynamic scan of the running app (OWASP ZAP baseline).
  • License No GPL-tainted deps if you want to stay proprietary.
  • Perf budget A 5-min k6 smoke against staging — p95 < 800 ms?

Why a gate?

Catching a high-severity CVE in your base image after it's in prod is a 2 a.m. job. Catching it before the push is a 2-minute job. The gate turns that into a process.

Trivy in your pre-deploy step

- name: Build & scan image
  run: |
    docker build -t myapp:${{ github.sha }} .
    trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:${{ github.sha }}
    trivy image --format cyclonedx --output sbom.json myapp:${{ github.sha }}
    # Fail the deploy if anything high or critical shows up

Smoke testing explained: the lightest possible end-to-end check you can run. Does the service start? Does /healthz return 200? Can you log in? If smoke fails, you don't even try the full E2E — you assume the build is broken and roll back.

Stage 9

Releasing — canary, blue-green, and feature flags.

You have a green build. You could ship it to 100% of users in one go. In 2026, you don't.

The three release patterns

  • Canary release — 1% of traffic hits the new version; you watch error rate and latency; if green, ramp to 10%, 50%, 100%.
  • Blue-green — keep the old version (blue) live; deploy the new (green) next to it; flip the load balancer; if anything breaks, flip back.
  • Feature flag — code is deployed, but the feature is off for everyone (or for 1%) via a config flag. No redeploy to turn it off.

Why this is a "test" stage

The new version is the canary — you're literally using real users as a final test, in a controlled way. The metrics you watch (error rate, p95 latency, conversion) ARE your production test suite.

Feature flag in your FastAPI app (Unleash or Flagsmith — both free tiers)

# brain/features.py
from unleash import UnleashClient
client = UnleashClient(url=os.environ["UNLEASH_URL"],
                       app_name="myapp",
                       api_key=os.environ["UNLEASH_TOKEN"])

def answer_question(q: str) -> str:
    if client.is_enabled("new-rag-pipeline"):
        return new_pipeline(q)        # only 5% of users see this
    return old_pipeline(q)            # everyone else still gets the safe path

Canary check in your GitHub Actions

- name: Deploy canary (1%)
  run: ./scripts/deploy.sh canary 1
- name: Wait & observe
  run: sleep 300
- name: Compare error rates (canary vs stable)
  run: ./scripts/canary_gate.sh
  # Gate fails if canary error rate > 1.5x stable, or p95 > 1.5x stable

When in the journey: every release, for the lifetime of the product. Flags are how you test in prod without risking prod.

Stage 10

Production reality — testing never stops.

Your code is in front of real users. The testing doesn't end — it just changes shape. Three big ideas live here.

1. Synthetic monitoring

A simulated user runs the smoke flow every 1 minute from 5 regions. If it fails, you get paged. This is your "test in prod" insurance.

2. Real User Monitoring (RUM)

Capture latency, errors, and UX metrics from real browsers (Sentry, Datadog, Grafana Faro).

3. Chaos engineering

Deliberately kill Postgres. Throttle the network. Inject 500 ms latency into Qdrant. Verify your app survives gracefully (LitmusChaos, ChaosMesh).

4. Load & performance testing

Find the breaking point before your users do. k6, Locust, or Grafana Cloud's k6 are the 2026 standards. Run weekly, not just pre-release.

5. A/B testing

Two versions, real users, real revenue. Statistics tells you which one wins. Distinct from canary: canary = "is it safe?" A/B = "is it better?"

6. Alpha & beta programs

Alpha = internal dogfood. Beta = a small invited cohort. Both are "tests" run on real users with managed expectations.

Your stack: k6 load test

// load-test.js  (k6)
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [
    { duration: '1m', target: 50 },     // ramp to 50 users
    { duration: '3m', target: 200 },    // 200 users
    { duration: '1m', target: 0 },
  ],
  thresholds: {
    http_req_duration: ['p(95)<800'], // fail if p95 > 800ms
    http_req_failed:   ['rate<0.01'],  // fail if >1% errors
  },
};

export default function () {
  const r = http.post(`${__ENV.BASE}/v1/ask`, JSON.stringify({q: "hi"}),
                      { headers: { "Content-Type": "application/json",
                                   "Authorization": `Bearer ${__ENV.TOKEN}` }});
  check(r, { '200': r => r.status === 200 });
}

Chaos experiment (the simplest one)

# chaos/kill_postgres.yml

Beginner warning: chaos engineering on a real production system before you have observability and on-call is reckless. Start chaos only after you have dashboards, alerts, and a runbook. The 2026 safe order: observability → canary → synthetics → chaos.

Regression testing — the permanent background

Every test in every previous stage is a regression test the moment the next release happens. The trick is to keep the suite fast and trustworthy: under 10 minutes, never flaky, always re-run before a release. In CI, run only the impacted tests for fast PR feedback (test impact analysis), and the full suite nightly.

12 · Pipelines How it all runs automatically.

All the stages above are useless if they only run "when I remember." In 2026, the bar is: every test runs on every push, automatically, in the right order, in parallel, with results blocking the merge. GitHub Actions is the right tool for a beginner on your stack — free for public repos, generous free tier for private.

13 · AI for testing The 2026 cheat code.

In 2026, AI is used in four distinct ways across the testing journey. They are not magic — they're tools you point at the right problem.

1. AI generates test cases

Point an LLM at a function and ask "what edge cases am I missing?" Tools: Qodo (CodiumAI), Diffblue Cover (Java), Meticulous, GitHub Copilot in test mode. For your stack: Copilot Chat + pytest is the lowest-friction combo.

Example prompt: "Given this function, list 10 inputs that could break it. Then write pytest cases for each."

2. AI judges subjective output

For LLM features, an LLM-as-judge scores the answer for faithfulness, relevance, tone. Tools: DeepEval, RAGAS, Promptfoo, LangSmith evaluators. You saw the example in Stage 6.

3. AI heals flaky tests

When a Playwright selector breaks because a CSS class renamed itself, an AI agent rewrites the selector. Tools: Healenium, Testim, Mabl, QA Wolf. Big time-saver for UI tests.

4. AI tests security and monitors production

LLM agents now drive OWASP ZAP-style scans with reasoning ("that endpoint returned 500 with a stack trace — try a path traversal"). Tools: BurpGPT, Strawberry. For monitoring, AI summarises Sentry/Datadog alerts into runbooks and suggests fixes.

How to use AI for testing in your project (the safe 2026 way)

  • Use AI to draft tests, but you own correctness. A generated test that never fails is worse than no test — it gives false confidence. Always run mutation testing to verify.
  • Use AI to grow your eval set. Every real user complaint is a candidate test case. Feed it to the LLM, get 20 variations, add to golden_set.jsonl.
  • Use AI as a reviewer, not an oracle. AI in the PR review catches things humans miss. coderabbit, Sourcery, Codeium Reviewer are good free tiers.
  • Never let AI touch prod without a human in the loop. AI in canary gate decisions? Sure — but a human can override in one click.
The honest truth about 2026: AI makes you faster, not safer. It writes more code, so you need more tests. It writes tests, so you need mutation testing to verify they actually test. The leverage is real — but the discipline is the same.

14 · DevSecOps White box, black box, and the AppSec review.

You've heard the term "DevSecOps." It just means: security is part of the same pipeline, not a separate team you hand things to at the end. Three flavors of security testing show up across the journey.

White-box (you know the code)

You read the source and look for vulns. SAST tools automate this: Bandit, Semgrep, CodeQL, SonarQube. Run on every PR. Catches SQLi, XSS, deserialization bugs, hardcoded secrets.

You are doing white-box when you write a security unit test that asserts "SELECT * WHERE id={user_input} is never reached."

Black-box (you don't)

You poke the running app like an attacker. DAST tools: OWASP ZAP, Burp Suite. Run against staging. Catches misconfigurations, missing auth, IDOR.

"Black box" because the tool sees only HTTP — no source code. Best for finding "what's exposed that shouldn't be."

Grey-box (a little of both)

You give the attacker one account and a known schema. Most realistic pen tests are grey-box. Tools: StackHawk, prowler, nuclei.

The AppSec review (the human part)

Twice a year, an AppSec engineer (in-house or contracted) does a deeper review: threat model refresh, architecture risk analysis, secrets-handling audit, dependency-graph review, infra-as-code scan. It's a meeting, not a tool — but it's the highest-signal security activity you can do.

Penetration testing vs bug bounty

  • Pen test — a paid, time-boxed engagement (1–2 weeks, $5–25k). You get a report, you fix the high-severity findings.
  • Bug bounty — open invitation, paid per finding. Cheap to start (HackerOne, Bugcrowd), scales with the size of your product.
  • For a beginner SaaS: skip both for the first year. SAST + SCA + DAST + a yearly external pen test is enough.

The other "boxes" the industry uses

  • Alpha testing = the team uses the product themselves (dogfooding).
  • Beta testing = a real cohort of users tries the product pre-launch; you collect feedback.
  • Smoke testing = the bare-minimum checks before any further testing (you saw this in stage 8).
  • Sanity testing = a quick check after a small bugfix ("did the fix work and not break anything obvious?").
  • Acceptance testing (UAT) = the customer or product owner verifies the feature meets their criteria. The Given/When/Then lines from Stage 0 are the acceptance tests.

If you only remember five things…

1. Test cheap layers first. Lint and unit tests run in milliseconds — that's where 80% of bugs should die.

2. Use real Postgres, real Qdrant, real Redis in tests via Testcontainers. Mocks hide real bugs.

3. For LLM features, build a golden eval set and treat quality like a metric on a dashboard, not a boolean.

4. Block the merge in GitHub branch protection. A test suite you can ignore isn't a test suite.

5. Ship behind a feature flag. Deploy ≠ release. The cheapest rollback is one that doesn't need a deploy.
