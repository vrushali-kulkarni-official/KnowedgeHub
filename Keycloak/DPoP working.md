Yes. Since you’re learning Keycloak practically, the most useful way to understand **DPoP** is to compare it directly with the normal Bearer-token flow and then trace exactly what Keycloak checks.

Keycloak has officially supported DPoP since **Keycloak 26.4**; before that it was a preview feature. ([Keycloak][1])

## 1. First: what problem does DPoP solve?

Normally, OAuth/OIDC gives your client an access token:

```http
Authorization: Bearer eyJhbGciOi...
```

The important property of a **Bearer token** is:

> Whoever possesses the token can use it.

For example:

```text
Your FastAPI app
      |
      | access_token
      v
   Keycloak
      |
      v
  access_token
```

Suppose your legitimate client gets:

```text
ACCESS_TOKEN = abc123
```

An attacker somehow steals `abc123`.

The attacker can simply do:

```http
GET /api/users
Authorization: Bearer abc123
```

The API has no way to know:

> "Is this the legitimate client or an attacker who stole the token?"

That's the fundamental weakness of bearer tokens.

DPoP changes this model from:

```text
Bearer token
    ↓
Whoever has token can use it
```

to:

```text
DPoP-bound token
    ↓
Token + possession of private key required
```

This is called **sender-constraining**. ([Keycloak][2])

---

# 2. The key idea

The client generates an asymmetric key pair:

```text
             Client
               |
       ┌───────┴────────┐
       │                │
   Private Key       Public Key
       │                │
       │                └─── can be shared
       │
       └── MUST remain secret
```

For example:

```text
Private key:
    K_private

Public key:
    K_public
```

The private key never needs to be sent to Keycloak.

The client instead proves:

> "I possess the private key corresponding to this public key."

That's where **DPoP proofs** come in.

---

# 3. There are actually TWO JWTs involved

This is one of the most important things to understand.

With DPoP you can have:

### JWT #1 — Access Token

Issued by Keycloak:

```text
ACCESS TOKEN
```

It contains a confirmation (`cnf`) claim identifying the client's public key.

### JWT #2 — DPoP Proof

Generated by the client:

```text
DPoP PROOF JWT
```

It is signed using the client's **private key**.

So:

```text
                 Keycloak
                    |
                    | Access Token
                    v
                  Client
                    |
          ┌─────────┴──────────┐
          |                    |
      Access Token         DPoP Proof
          |                    |
          |              signed with
          |              private key
          v                    v
                    FastAPI Resource Server
```

This distinction is extremely important.

---

# 4. Step 1 — Client generates a key pair

Before requesting a token, the client generates:

```text
Private key
    +
Public key
```

For example, using ES256:

```text
Private key = EC private key
Public key  = EC public key
```

The private key stays inside the client.

The public key is included inside the DPoP proof as a JWK.

---

# 5. Step 2 — Client requests a token from Keycloak

Instead of simply:

```http
POST /token

grant_type=authorization_code
code=...
```

the client sends a DPoP proof:

```http
POST /realms/myrealm/protocol/openid-connect/token

DPoP: <DPoP-Proof-JWT>
```

The DPoP JWT contains a header similar to:

```json
{
  "typ": "dpop+jwt",
  "alg": "ES256",
  "jwk": {
    "kty": "EC",
    "crv": "P-256",
    "x": "...",
    "y": "..."
  }
}
```

Notice something interesting:

The **public key is actually inside the DPoP JWT**.

But the JWT is signed using:

```text
PRIVATE KEY
```

Therefore Keycloak can verify:

```text
Public key from JWT
        ↓
verify signature
        ↓
Does this client actually possess
the corresponding private key?
```

The DPoP specification defines this proof JWT and requires a unique proof for each request. ([rfc-editor.org][3])

---

# 6. What does the DPoP proof contain?

The body contains important information such as:

```json
{
  "jti": "unique-id",
  "htm": "POST",
  "htu": "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token",
  "iat": 1756780000
}
```

And when accessing a resource, it also contains:

```json
{
  "ath": "hash-of-access-token"
}
```

Important fields:

| Claim   | Meaning                        |
| ------- | ------------------------------ |
| `jti`   | Unique ID for this proof       |
| `htm`   | HTTP method                    |
| `htu`   | HTTP URI                       |
| `iat`   | Time proof was created         |
| `ath`   | Hash of access token           |
| `nonce` | Optional server-provided nonce |

The HTTP method and URI binding are important because the proof isn't just saying:

> "I own this private key."

It is saying something closer to:

> "I own this private key, and I am using it for THIS particular HTTP request."

Keycloak's documentation describes these claims and their purpose. ([Keycloak][2])

---

# 7. Step 3 — Keycloak binds the token to the public key

This is the magic part.

Suppose the client's public key is:

```text
K_public
```

Keycloak calculates a cryptographic thumbprint of that public key.

Conceptually:

```text
K_public
   |
   | SHA-256 / JWK thumbprint
   v
K_THUMBPRINT
```

Keycloak then puts this into the access token:

```json
{
  "cnf": {
    "jkt": "0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I"
  }
}
```

`jkt` is the JWK thumbprint.

Keycloak documents this exact `cnf.jkt` mechanism. ([Keycloak][2])

So the access token is effectively saying:

```text
"This token belongs to the holder of private key
 corresponding to public-key thumbprint X."
```

---

# 8. Now the access token is no longer a normal Bearer token

Normally:

```text
ACCESS TOKEN
      |
      v
Anyone possessing it can use it
```

With DPoP:

```text
ACCESS TOKEN
      |
      +---- bound to ----> Public Key
                              |
                              |
                         Private Key
```

Therefore:

```text
Access token alone
       ↓
     useless
```

The attacker needs:

```text
Access token
      +
corresponding private key
```

That's the entire security improvement.

---

# 9. Step 4 — Client calls your FastAPI API

Now suppose your application is:

```text
React / Mobile App
        |
        v
     FastAPI
```

The client wants:

```http
GET https://api.example.com/users
```

It sends **two headers**:

```http
Authorization: DPoP <access-token>

DPoP: <new-DPoP-proof>
```

Notice:

```http
Authorization: DPoP
```

not:

```http
Authorization: Bearer
```

Keycloak specifically documents this distinction for DPoP-bound tokens. ([Keycloak][2])

---

# 10. The DPoP proof for this request

The client creates a completely new DPoP proof.

For example:

```json
{
  "jti": "abc-987",
  "htm": "GET",
  "htu": "https://api.example.com/users",
  "iat": 1756780100,
  "ath": "hash-of-access-token"
}
```

And signs it:

```text
                 Private Key
                     |
                     v
              Sign DPoP JWT
                     |
                     v
              DPoP Proof JWT
```

Then:

```http
GET /users HTTP/1.1

Authorization: DPoP eyJhbGciOi...
DPoP: eyJ0eXAiOiJkcG9wK2p3dCI...
```

---

# 11. What does FastAPI verify?

Your FastAPI API is the **Resource Server**.

It receives:

```text
Access Token
+
DPoP Proof
```

It performs several checks.

### Check 1 — Is access token valid?

For example:

```text
signature
issuer
expiration
audience
scope
etc.
```

Same kinds of checks you already know from normal JWT validation.

---

### Check 2 — Does the DPoP proof have a valid signature?

The proof contains the public key:

```text
DPoP JWT
   |
   └── JWK = Public Key
```

FastAPI extracts that public key and verifies:

```text
signature
      ↓
valid?
```

If the attacker doesn't possess the private key:

```text
❌ cannot create valid DPoP proof
```

---

### Check 3 — Does the public key match the access token?

Remember:

```json
{
  "cnf": {
    "jkt": "XYZ"
  }
}
```

FastAPI calculates the thumbprint of the public key contained in the DPoP proof:

```text
DPoP public key
      ↓
thumbprint
      ↓
XYZ
```

Then:

```text
Token cnf.jkt
      =
DPoP public-key thumbprint
```

If:

```text
XYZ == XYZ
```

good.

If:

```text
XYZ != ABC
```

reject.

---

# 12. Check 4 — Is this DPoP proof actually for THIS request?

Suppose the client requested:

```http
GET /users
```

The proof says:

```json
{
  "htm": "GET",
  "htu": "https://api.example.com/users"
}
```

Good.

But suppose an attacker captures that proof and tries:

```http
DELETE /users
```

The proof still says:

```json
"htm": "GET"
```

Therefore:

```text
actual request:
DELETE /users

proof:
GET /users

        ↓

       ❌
```

The proof is bound to the request.

---

# 13. Why `ath` is important

The proof can also contain:

```json
{
  "ath": "SHA256(access-token)"
}
```

This binds the proof to the particular access token.

So conceptually:

```text
DPoP proof
    |
    +---- private key signature
    |
    +---- HTTP method
    |
    +---- HTTP URI
    |
    +---- hash(access token)
```

This makes it much harder to take a valid proof and reuse it with another token.

---

# 14. Let's look at the complete flow

Here's the complete picture:

```text
                         KEYCLOAK
                            |
                            |
                     Authorization
                          Server
                            |
                            |
        ┌───────────────────┴────────────────────┐
        │                                        │
        │                                        │
        │             Client                     │
        │                                        │
        │       Generate key pair                │
        │       ┌───────────────┐                │
        │       │ Private       │                │
        │       │ Public        │                │
        │       └───────────────┘                │
        │             │                          │
        │             │                          │
        │       Create DPoP proof                │
        │             │                          │
        └─────────────┼──────────────────────────┘
                      │
                      │ POST /token
                      │
                      │ DPoP: <proof>
                      ▼
                  Keycloak
                      │
              verify signature
                      │
               extract public key
                      │
               calculate jkt
                      │
                      ▼
                Access Token
                ┌───────────────┐
                │ cnf:          │
                │   jkt: XYZ    │
                └───────────────┘
                      │
                      ▼
                    Client
                      │
                      │
                      │ GET /users
                      │ Authorization: DPoP <token>
                      │ DPoP: <new proof>
                      ▼
                  FastAPI
                      │
             ┌────────┴────────┐
             │                 │
        Validate JWT      Validate DPoP
             │                 │
             │          verify signature
             │          verify jkt
             │          verify htm
             │          verify htu
             │          verify ath
             │                 │
             └────────┬────────┘
                      │
                      ▼
                   ALLOW
```

# 15. Now let's understand the attack DPoP prevents

Suppose you have:

```text
Client
  |
  | Access Token
  v
FastAPI
```

Attacker somehow steals:

```text
Access Token = ABC
```

### Normal Bearer token

Attacker does:

```http
GET /users

Authorization: Bearer ABC
```

FastAPI says:

```text
Token valid?
YES

      ↓

ALLOW
```

🔥 Attack succeeds.

---

### DPoP

Attacker steals:

```text
Access Token = ABC
```

But doesn't have:

```text
Private Key
```

Attacker attempts:

```http
GET /users

Authorization: DPoP ABC
DPoP: ??????
```

They need to create a valid DPoP proof.

But:

```text
DPoP proof must be signed
with private key
```

They don't have it.

Therefore:

```text
❌ Invalid DPoP proof

       ↓

     REJECT
```

That's the fundamental reason DPoP exists.

---

# 16. But what if the attacker steals BOTH?

This is an important security boundary.

Suppose malware compromises the client and steals:

```text
Access Token
+
Private Key
```

Then DPoP cannot save you.

The attacker can generate legitimate proofs.

So DPoP protects primarily against:

```text
Access token leakage
```

not:

```text
complete compromise of the client
```

The RFC explicitly describes DPoP as a mechanism for sender-constraining tokens and preventing their unauthorized reuse; it isn't itself an authentication or access-control mechanism. ([rfc-editor.org][3])

---

# 17. What about replaying the DPoP proof itself?

You might now ask:

> "If the attacker captures the DPoP proof, can't they replay THAT?"

This is why the proof has:

```text
jti
iat
htm
htu
```

and optionally:

```text
nonce
```

The server can detect/reject old or reused proofs.

The optional **nonce mechanism** makes this even stronger: the resource server can return a `DPoP-Nonce`, requiring the client to generate a new proof containing that nonce. ([Keycloak][2])

---

# 18. Where does Keycloak fit vs FastAPI?

This is especially important for your FastAPI + Keycloak architecture.

You have:

```text
             ┌─────────────┐
             │   Keycloak  │
             │             │
             │ Authorization
             │   Server    │
             └──────┬──────┘
                    │
              issues token
                    │
                    ▼
             ┌─────────────┐
             │   Client    │
             └──────┬──────┘
                    │
                    │ DPoP token + proof
                    ▼
             ┌─────────────┐
             │   FastAPI   │
             │             │
             │  Resource   │
             │   Server    │
             └─────────────┘
```

Keycloak's job:

```text
Authenticate user
       ↓
Issue DPoP-bound token
```

FastAPI's job:

```text
Receive token
       ↓
Validate token
       ↓
Validate DPoP proof
       ↓
Authorize request
```

**Keycloak doesn't magically protect your FastAPI API merely because you enabled DPoP in Keycloak.**

Your resource server must understand and enforce DPoP.

# 19. Keycloak configuration

In current Keycloak, go to:

```text
Clients
   ↓
your-client
   ↓
Settings
   ↓
Capability config
   ↓
Require DPoP bound tokens
```

If enabled:

```text
Require DPoP bound tokens = ON
```

the client must provide a valid DPoP proof when requesting tokens.

If disabled:

```text
Require DPoP bound tokens = OFF
```

the client can still send DPoP, and Keycloak can issue a DPoP-bound token, but DPoP isn't mandatory. ([Keycloak][2])

# 20. DPoP vs PKCE

Since you were recently learning PKCE, this distinction is **very important**.

They solve different problems.

### PKCE

Protects:

```text
Authorization Code
```

during the authorization-code flow.

Conceptually:

```text
Authorization Code
       +
Code Verifier
       ↓
Token
```

PKCE protects the **authorization-code exchange**.

---

### DPoP

Protects:

```text
Access Token
Refresh Token
```

from unauthorized reuse by binding them to a key.

Conceptually:

```text
Access Token
      +
Private Key
      ↓
Authorized API request
```

So:

```text
PKCE
 ↓
Protect authorization code

DPoP
 ↓
Protect token from replay/theft
```

And they can absolutely be used together:

```text
Authorization Code Flow
          +
        PKCE
          +
        DPoP
```

That's a very strong OAuth setup.

---

# 21. DPoP vs JWT

Another common confusion:

**DPoP is not an alternative to JWT.**

You can have:

```text
JWT Access Token
        +
DPoP Proof JWT
```

There are two separate JWTs serving different purposes.

```text
                JWT #1
           Access Token
        issued by Keycloak
               |
               | contains
               v
           cnf.jkt = XYZ


                JWT #2
             DPoP Proof
         generated by client
               |
               | signed with
               v
          Private Key
```

# 22. The simplest mental model

If you remember only one thing, remember this:

### Bearer

```text
TOKEN = password-like capability

Whoever has TOKEN
        ↓
      access
```

### DPoP

```text
TOKEN = locked to a key

TOKEN
  +
PRIVATE KEY
  +
VALID DPoP PROOF
        ↓
      access
```

Or even simpler:

```text
Bearer:

    "I have the token."


DPoP:

    "I have the token
     AND
     I can cryptographically prove
     that I possess the private key
     that this token belongs to."
```

That is the essence of DPoP.
