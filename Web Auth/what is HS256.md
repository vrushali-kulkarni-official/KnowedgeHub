`HS256` in FastAPI is **not actually a FastAPI feature**. It is a **JWT signing algorithm** used when creating and verifying JSON Web Tokens (JWTs).

Let's understand it step by step.

---

# Step 1: What is HS256?

HS256 stands for:

* **H** = HMAC (Hash-based Message Authentication Code)
* **S** = SHA
* **256** = SHA-256 hashing algorithm

So,

> **HS256 = HMAC + SHA-256**

It is one of the algorithms used to **digitally sign a JWT**.

---

# Step 2: Why do we need HS256?

Suppose your backend creates this JWT payload:

```json
{
    "sub": "bhargav",
    "role": "admin"
}
```

If this payload is simply Base64 encoded,

```
Header.Payload
```

anyone can decode it, change it to

```json
{
    "sub": "bhargav",
    "role": "superadmin"
}
```

and re-encode it.

That would be a huge security problem.

So we add a **digital signature**.

JWT becomes

```
Header.Payload.Signature
```

The signature proves:

* nobody modified the token
* the token was generated by your server

HS256 is the algorithm used to generate that signature.

---

# Step 3: JWT Structure

A JWT has three parts.

```
Header
.
Payload
.
Signature
```

Example:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

.

eyJzdWIiOiJiaGFyZ2F2Iiwicm9sZSI6ImFkbWluIn0

.

r9w3a8Kdf9as9d98as8d98asd98asd98asd
```

The Header looks like

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

Notice

```json
"alg": "HS256"
```

This tells everyone

> "This JWT was signed using HS256."

---

# Step 4: How is the signature created?

Suppose

Header

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

Payload

```json
{
  "sub": "bhargav"
}
```

Secret key

```
my_super_secret_key
```

The server computes

```
Signature =
HMAC_SHA256(

Base64(Header) + "." + Base64(Payload),

Secret Key

)
```

Notice the secret key is used.

Without the secret key, nobody can generate a valid signature.

---

# Step 5: What happens when a user sends the JWT?

Suppose browser sends

```
Authorization:
Bearer
eyJh...
```

FastAPI receives it.

Now FastAPI (actually the JWT library you're using) does this:

It extracts

```
Header
Payload
Signature
```

Then it recomputes

```
Expected Signature

=
HMAC_SHA256(

Header + Payload,

Secret Key

)
```

Now it compares

```
Expected Signature

vs

Received Signature
```

If they match

✅ Token is valid

If they don't

❌ Token has been modified or wasn't signed with your secret.

---

# Step 6: FastAPI Example

Suppose

```python
SECRET_KEY = "mysecretkey"

ALGORITHM = "HS256"
```

Creating a token

```python
from jose import jwt

data = {"sub": "bhargav"}

token = jwt.encode(data, SECRET_KEY, algorithm=ALGORITHM)
```

Notice

```python
algorithm = "HS256"
```

This tells the JWT library

> Use HS256 to sign this JWT.

---

Decoding

```python
payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
```

The library now

* verifies the signature
* checks if the algorithm is HS256
* uses your secret key
* returns the payload if valid

---

# Step 7: Why is the Secret Key Important?

Imagine

```
SECRET_KEY = "apple"
```

Server signs the JWT.

Now hacker changes

```
role=user
```

to

```
role=admin
```

To create a valid signature, the hacker needs

```
SECRET_KEY = "apple"
```

Without it,

they cannot produce the correct HMAC-SHA256 signature.

So the server immediately rejects the modified token.

---

# Step 8: Why is it called "Symmetric"?

HS256 uses the **same secret key** for both signing and verification.

```
Create Token

Server
     |
     | SECRET KEY
     V
Sign JWT
```

Later

```
Verify Token

Server
     |
     | SAME SECRET KEY
     V
Verify Signature
```

Same key.

Therefore,

**HS256 is a symmetric algorithm.**

---

# Step 9: Other JWT Algorithms

HS256 is not the only algorithm.

| Algorithm | Type       | Keys Used                              |
| --------- | ---------- | -------------------------------------- |
| HS256     | Symmetric  | Same secret for signing and verifying  |
| HS384     | Symmetric  | Same secret                            |
| HS512     | Symmetric  | Same secret                            |
| RS256     | Asymmetric | Private key signs, public key verifies |
| ES256     | Asymmetric | Elliptic Curve keys                    |

---

# Step 10: HS256 vs RS256

### HS256

```
            SECRET KEY
               |
Sign JWT ------+
               |
Verify JWT ----+
```

Only one key.

---

### RS256

```
Private Key
      |
      V
Sign JWT

        Internet

Verify using

Public Key
```

Different keys.

The private key stays secret, while the public key can be distributed to services that need to verify tokens.

---

# Which should you use?

* **HS256** is a good choice for a single backend or a small system where the same server issues and verifies tokens. It's simple, fast, and widely used.
* **RS256** is often preferred in larger systems, microservices, or when using an external identity provider (such as OAuth/OpenID Connect providers), because many services can verify tokens using the public key without having access to the private signing key.

So, in FastAPI code like:

```python
SECRET_KEY = "a_long_random_secret_key"
ALGORITHM = "HS256"

token = jwt.encode(
    {"sub": "bhargav"},
    SECRET_KEY,
    algorithm=ALGORITHM,
)
```

`HS256` tells the JWT library: **"Use the HMAC-SHA256 algorithm with this secret key to generate and later verify the token's signature."** It protects the token from being tampered with, but it **does not encrypt** the payload—the payload remains readable by anyone who has the token. Only the signature is used to verify integrity and authenticity.
