This act is the payoff. You didn't learn "how to use React" — you learned what React is made of. Now the framework isn't a new language; it's a set of conventions on top of what you already own.

The one-paragraph summary

React takes the state → render loop you built by hand in Act 5 and makes it declarative. You describe what the UI should look like for the current state; React figures out the minimal DOM changes. Everything else — components, props, keys, effects — exists to make that loop scale.

11.1 — How React Maps Onto What You Know

See React as a set of conventions on top of the DOM, not a new paradigm.

Your hand-written version (Act 5)

let count = 0;
const display = document.querySelector("#display");

function render() {
  display.textContent = count;
}

plusBtn.addEventListener("click", () => { count++; render(); });

The React version

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
Your versionReact's versionWhat changed
let count = 0const [count, setCount] = useState(0)state is per-component, not a global variable

The virtual DOM

React keeps a JavaScript representation of your UI (the "virtual DOM"). When state changes, it:

  1. re-runs your component function, producing a new virtual tree
  2. diffs it against the previous virtual tree (a fast, cheap comparison)
  3. applies only the real differences to the actual DOM

That's why React can re-render a whole tree on every state change and still be fast — the DOM itself is touched minimally.

You already know all of this. You built the render loop by hand. React is the same loop, with the diffing automated and the state scoped per component.

What to notice

  • React's re-render is not the DOM being rebuilt. It re-runs your functions and patches the DOM. That's why components should be pure functions of their props and state.
  • React 18+ batches multiple state updates into a single re-render automatically — you don't need to batch manually.

Challenge — Predict the React behaviour

For each snippet, work out what the browser shows after one click:

  1. setCount(count + 1) called twice in the same handler — what's the count?
  2. setCount(count + 1) then setCount(count + 2) — what's the count? (This is the stale closure trap.)
  3. setCount(c => c + 1) called twice — what's the count?
  4. Three different components each with their own useState — do they share state?

Then set up a real React project and verify your answers. The difference between #2 and #3 is one of the most important things to understand about React state.

Stuck? Open the hints
  • React batches state updates, but two updates based on the same count value both compute from that stale value. The functional form c => c + 1 always uses the latest.
  • useState is a hook — and hooks must be called at the top level of a component, never inside a condition or loop.

11.2 — Components, Props & State

Learn React's three core ideas, and the rules that govern them.

Components are functions

function Greeting(props) {
  return <h1>Hello, {props.name}!</h1>;
}

function App() {
  return (
    <div>
      <Greeting name="Ana" />
      <Greeting name="Bruno" />
    </div>
  );
}

JSX is not a string — it's a function call

<Greeting name="Ana" />
// is really:
Greeting({ name: "Ana" })

JSX compiles to React.createElement(...) (or jsx(...)). It looks like HTML, but it's JavaScript: you can put {expression} inside it, and you can use .map() inside it. That's why you need a key on each item in a list.

Props: passed down, immutable

  • Props go from parent to child. A child never changes them.
  • They can be anything: strings, numbers, objects, functions, JSX.
  • A function passed as a prop is a callback — exactly like addEventListener in vanilla JS.
function List({ items, onSelect }) {
  return (
    <ul>
      {items.map(item => (
        <li key={item.id} onClick={() => onSelect(item)}>
          {item.name}
        </li>
      ))}
    </ul>
  );
}

The key prop. It's required for every element in a list. React uses it to identify which item is which across re-renders, so it can update the DOM efficiently. Use a stable, unique id — never the array index (unless the list is never reordered, and even then it's risky).

State: the component's own memory

const [value, setValue] = useState(initialValue);
  • useState returns the current value and a setter.
  • Each component instance has its own independent state.
  • Calling the setter tells React "re-render me with the new value".
  • State is immutable — you never modify it directly, you always replace it.
// WRONG - mutates the array in place; React won't notice
items.push(newItem);
setItems(items);

// RIGHT - a new array
setItems([...items, newItem]);
setItems(prev => [...prev, newItem]);   // when you need the latest value

That "never mutate" rule is exactly the Python instinct to avoid — and it exists for the same reason React uses immutability: to detect changes cheaply and to make time-travel debugging possible.

What to notice

  • Hooks must be called at the top level of a component or a custom hook. Not inside an if, not inside a loop, not inside a callback. React relies on the call order being identical every render.
  • A component's name must start with a capital letter — <mycomponent /> is treated as an HTML tag, not a component.
  • Components must return a single element. Wrap multiple in a fragment: <>...</>.

Challenge — Rebuild an Act 5 project in React

Take the number counter (Act 5 Step 5.2) and rebuild it in React:

  1. Split it into components: <Counter>, <Display>, <Button>.
  2. State lives in <Counter> and is passed down as props.
  3. The buttons receive an onClick callback prop.
  4. Add a second counter to the page and confirm they are independent — that's per-component state.
  5. Then lift the state up: put count in the parent and pass it plus a setter down. Why might you need to do that?

Extra: a "Reset" button and the same disabled-at-min/max behaviour as the vanilla version.

Stuck? Open the hints
  • If two components need the same state, the state belongs in their closest common ancestor — that's "lifting state up".
  • Props flow down, events flow up. That's the mental model for every React form.

11.3 — Effects & Data Fetching

Understand useEffect — the hook people misuse most — and the modern data-fetching alternative.

What an effect is

An effect lets a component reach outside itself after it renders: subscribe to something, set up a timer, fetch data, talk to an imperative API.

useEffect(() => {
  // runs AFTER the render
  const id = setInterval(() => setTick(t => t + 1), 1000);
  return () => clearInterval(id);      // cleanup: runs BEFORE the next effect / on unmount
}, [dependencies]);

The dependency array

Dependency arrayEffect runs
omittedafter every render
[]once, on mount (and cleanup on unmount)
[a, b]when a or b changes (compared by Object.is)

React's rule: if an effect uses a value from the component (props.x or state), that value should be in the dependency array. The linter (react-hooks/exhaustive-deps) will tell you when you've missed one. This is the "stale closure" bug: an effect that captured an old value.

Fetching data

function Users() {
  const [users, setUsers] = useState([]);
  const [status, setStatus] = useState("loading");

  useEffect(() => {
    let cancelled = false;
    fetch("/api/users")
      .then(r => r.json())
      .then(data => { if (!cancelled) { setUsers(data); setStatus("done"); } })
      .catch(() => { if (!cancelled) setStatus("error"); });
    return () => { cancelled = true; };
  }, []);

  if (status === "loading") return <p>Loading…</p>;
  if (status === "error") return <p>Something went wrong</p>;
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>
}

Two important details:

  • Cleanup prevents a "set state on unmounted component" warning — and more importantly prevents a stale response overwriting fresh data.
  • All three states — loading, error, and data. (Act 6 Step 6.2.)

Modern React: you might not need useEffect

React 18.3+ / Next.js App Router have server components and a use hook. But the rule stands: don't put data fetching in an effect if there's a framework feature for it. In Next.js App Router, you fetch in the component itself (it runs on the server) — no effect, no loading state boilerplate, no waterfall.

The most common effect mistake: using an effect to derive state. If you can compute a value from props/state during render, don't store it in state — just compute it. Effects are for synchronising with the outside world, not for deriving values.

// WRONG - state that could be derived
const [full, setFull] = useState("");
useEffect(() => { setFull(first + " " + last); }, [first, last]);

// RIGHT - just compute it
const full = first + " " + last;

What to notice

  • An effect's cleanup function is essential: it's what prevents duplicate subscriptions and memory leaks.
  • React 18's StrictMode deliberately runs effects twice in development (mount → unmount → mount) to surface missing cleanup. If you see things happening twice, that's why — it's a development-only behaviour.
  • useEffect with an empty dependency array is the equivalent of "on mount". Use useLayoutEffect only when you need to measure or mutate the DOM before the browser paints.

Challenge — Effects, done and done wrong

  1. Build a component with a counter that increments every second, with proper cleanup. Navigate away and back — does the interval keep running?
  2. Break the cleanup on purpose (remove the return). React's StrictMode in dev will show you the double-increment. Now you understand why cleanup matters.
  3. Add a search box that filters a list, using derived state (compute the filtered list during render) — not an effect.
  4. Fetch from the fake API with all three states (loading / error / data) and a cleanup that prevents setting state after unmount.
  5. Add a "Refresh" button that re-fetches — and figure out how to re-run an effect on demand (the answer involves a dependency array, and it's a common interview question).
Stuck? Open the hints
  • To re-run an effect on demand, put a counter in state and include it in the dependency array — increment it to trigger a refetch.
  • React 18's useEffect cleanup pattern with a cancelled flag is the standard pattern; React 19 may handle unmount automatically, but the flag is still good practice.

11.4 — Next.js & shadcn

See the structure of a modern Next.js app with shadcn/ui, and how it uses everything you know.

What Next.js adds

FeatureWhat it does
File-based routingapp/page.tsx → /, app/about/page.tsx → /about
Server Componentscomponents that run on the server — no JS shipped to the browser
Server Actionsfunctions that run on the server, callable from the client like an API
Data fetchingfetch in the component, with built-in loading.tsx and error.tsx
Built-in optimisationimage optimisation, font optimisation, code splitting, caching

The folder structure

my-app/
  app/
    layout.tsx        -> the shell (like <body>)
    page.tsx          -> /
    about/page.tsx    -> /about
    blog/[slug]/page.tsx -> /blog/:slug
    api/hello/route.ts  -> /api/hello (a route handler)
    loading.tsx       -> the loading state for this segment
    error.tsx         -> the error boundary
  components/
  lib/
  public/

Server vs Client Components is the concept to understand:

  • A component is a Server Component by default. It runs on the server, can access the database directly, and its JavaScript is never sent to the browser.
  • Add "use client" at the top to make it a Client Component — it ships JavaScript and can use state and effects.
  • You can nest them: a server component can render a client component and pass it serialisable props.

Rule of thumb: keep it on the server unless you need interactivity. The less JavaScript you ship, the faster your site.

shadcn/ui

shadcn is not a component library you install — it's a set of components copied into your project as source code you own.

npx shadcn@latest init
npx shadcn@latest add button card dialog input

What you get is real, readable code in components/ui/, built with Tailwind and CSS variables:

// components/ui/button.tsx  (simplified)
const buttonVariants = cva(
  "inline-flex items-center justify-center rounded-md text-sm font-medium",
  {
    variants: {
      variant: {
        default: "bg-primary text-primary-foreground hover:bg-primary/90",
        destructive: "bg-destructive text-destructive-foreground hover:bg-destructive/90",
        outline: "border border-input bg-background hover:bg-accent",
      },
      size: { default: "h-10 px-4 py-2", sm: "h-9 px-3", lg: "h-11 px-8" },
    },
    defaultVariants: { variant: "default", size: "default" },
  }
);

Look at what that is: your Act 2 and Act 3 knowledge. CSS variables for theming (bg-primary → var(--primary)), Tailwind utilities for styling, and a variant system for composition.

Why shadcn works this way: you can edit every component to fit your design system. No fighting a library's opinions, no "how do I override this component" — it's your code.

What to notice

  • The cva function (class-variance-authority) is the variant pattern from Act 3 Step 3.6, packaged. cn() (clsx + tailwind-merge) resolves conflicting Tailwind classes so the last one wins deterministically.
  • shadcn's theme lives in app/globals.css as CSS variables — exactly the Act 3 Step 3.5 approach, with an added .dark class.
  • Next.js has its own Tailwind setup, but the utility vocabulary is identical to Act 3.

Challenge — Read the framework code

  1. Create a Next.js app: npx create-next-app@latest my-app (choose TypeScript + Tailwind + App Router).
  2. Read app/layout.tsx and app/page.tsx. Where is the <html> and <body> tag? (Act 1 Step 1.3.)
  3. Add a route: create app/about/page.tsx and visit /about. What file did you create? What would happen if you'd created app/about.tsx instead?
  4. Add a client component with a counter and use it inside a server component. Notice the "use client" directive and where it has to be.
  5. Run npx shadcn@latest init and then npx shadcn@latest add button. Read the generated component. How much of Act 2 and Act 3 do you recognise?
  6. Open app/globals.css and find the CSS variables. How is dark mode implemented?
Stuck? Open the hints
  • In the App Router, a folder named page.tsx defines a route; a file named about.tsx inside a folder is just a module.
  • Next.js uses a tsconfig.json with a paths alias — @/components/ui/button resolves to the components/ui/button.tsx file.
