Act 3 of 12

Tailwind CSS

The same layout knowledge, expressed as small composable utility classes.

Everything in Act 2 still applies — the box model, the cascade, flexbox, grid. Tailwind doesn't replace CSS knowledge; it replaces writing CSS.

The shift: instead of inventing a class name and writing a rule for it, you compose small single-purpose utilities directly onto the element.

<!-- CSS -->
.card {
  display: flex;
  align-items: center;
  gap: 12px;
  padding: 16px;
  border-radius: 8px;
  background: #fff;
  border: 1px solid #e5e5e5;
}
<div class="card">...</div>

<!-- Tailwind -->
<div class="flex items-center gap-3 p-4 rounded-lg bg-white border border-gray-200">...</div>

What this buys you: you never leave your HTML, you never invent class names, you never write a selector, and you can see exactly what's applied by reading the class list. What it costs you: long class lists, and you need to know the scale (which is what this act teaches).

3.1 — The Utility-First Shift

Get past the 'this is just inline styles' objection and understand the real trade-off.

Your first reaction will be: "these class names are absurd — flex items-center gap-3 p-4 rounded-lg." That's a fair reaction. The counter-arguments, honestly stated:

Traditional CSSUtility-first
Class names describe appearance (.red-button) or purpose (.cta) — often both, inconsistentlyClass names describe what they do, so they're self-documenting
You must decide the name before you know the stylesStyles are visible in the markup — you decide the name after
Unused CSS accumulates foreverOnly the utilities you use end up in the output
Debugging means hunting a stylesheetDebugging means reading the class list
Changing a shared button style means editing CSSChanging it means editing every markup usage — this is the real cost

When to break out

Tailwind is not for everything. You'll extract a component when:

  • the same long class list appears three or more times (the rule of three — below that, duplication is cheaper than abstraction),
  • or the styles need pseudo-selectors, keyframes, or complex nesting that utilities can't express,
  • or it's a real design-system component (a button, a dialog) that should have a single API.

That's exactly what shadcn/ui does tomorrow: real components, but copied into your project as source code that you own and can edit — built with Tailwind utilities. Nothing in Act 2 or Act 3 is wasted; it's the foundation you customise.

What to notice

  • Tailwind classes are just CSS. `flex` is `display:flex`, `p-4` is `padding:1rem`, `text-center` is `text-align:center`. Every single one.

Challenge — Spot the CSS behind the classes

Without looking anything up, write the plain CSS that these Tailwind classes produce:

  1. flex items-center gap-3 p-4
  2. text-sm text-gray-600
  3. w-full max-w-md mx-auto
  4. grid grid-cols-3 gap-2
  5. absolute top-0 right-0 z-10

Then build the same card in plain CSS and compare how much code you wrote. Which did you enjoy more?

Stuck? Open the hints
  • The spacing scale: `p-1` = 0.25rem, `p-2` = 0.5rem, `p-3` = 0.75rem, `p-4` = 1rem. It doubles: 1, 2, 4, 8, 16, 32, 64.
  • The colour scale: 50 is lightest, 500 is the base, 900 is nearly black.

3.2 — Reading the Scales

Stop memorising class names individually — learn the scales and the names derive themselves.

Spacing — the number is the size

ClassValue
p-1 / m-10.25rem (4px)
p-20.5rem (8px)
p-30.75rem (12px)
p-41rem (16px)
p-61.5rem (24px)
p-82rem (32px)
p-123rem (48px)

Note the jumps: the scale isn't every integer. It roughly doubles. So p-2 → 8px, p-3 → 12px, p-4 → 16px, p-5 → 20px, p-6 → 24px. The gap between p-4 and p-5 is real, and the jump to p-8 is bigger. This is a design system — the numbers are meant to be a small, curated set, not every possible pixel.

The same numbers apply to width, height, gap, margin, padding, and (with a different prefix) inset. w-4 = width 1rem. gap-4 = gap 1rem.

Colours

{colour}-{shade}, where shade runs 50 (lightest) → 900 (darkest).

bg-slate-50    text-slate-900
bg-indigo-500  text-indigo-600
text-red-500   border-emerald-200

Colours you will use constantly: slate (neutral greys), gray, zinc, indigo, blue, green/emerald, red/rose, amber, yellow. The default palette is intentionally neutral — brand colours are added by you, in the config.

Typography

text-xs  text-sm  text-base  text-lg  text-xl
text-2xl text-3xl text-4xl text-5xl
font-normal  font-medium  font-semibold  font-bold
tracking-tight  tracking-wide  tracking-widest
leading-none  leading-tight  leading-relaxed
underline  line-through  uppercase  lowercase

Everything else

rounded-sm  rounded  rounded-lg  rounded-xl  rounded-full  rounded-none
border  border-2  border-t  border-b  divide-y
shadow-sm  shadow  shadow-lg  shadow-none
opacity-0  opacity-50  opacity-100
z-0  z-10  z-50
hidden  block  inline  inline-block  flex  grid
overflow-hidden  overflow-auto
cursor-pointer  select-none
transition  duration-200  ease-in-out

The meta-skill: you don't memorise these. You learn the pattern — text- for size, font- for weight, bg- for background, border- for border, p-/m- for spacing, w-/h- for size, flex/grid for display, justify-/items- for alignment. Then autocomplete in your editor does the rest. Every good editor has Tailwind IntelliSense.

Arbitrary values — when the scale isn't enough

&lt;div class="w-[137px]"&gt;&lt;/div&gt;              &lt;!-- exact pixels --&gt;
&lt;div class="bg-[#ff00aa]"&gt;&lt;/div&gt;            &lt;!-- exact colour --&gt;
&lt;div class="top-[calc(100%-2rem)]"&gt;&lt;/div&gt;   &lt;!-- calc() --&gt;

What to notice

  • In Tailwind v3+ the space is top-[calc(100%-2rem)]. In v4 the syntax changed to top-[calc(100%-2rem)] with underscores for spaces: top-[calc(100%_-_2rem)].
  • Arbitrary values are an escape hatch, not a default. If you find yourself writing p-[13px] a lot, the scale is wrong for your design — configure a custom one instead.

  • Responsive padding: `p-3 md:p-8` — the prefix goes before the utility, and the unprefixed one is the mobile default.
  • The checkmark can just be the character ✓ in a <span class="text-emerald-500">.

3.3 — Layout with Utilities

Translate Act 2's flexbox and grid knowledge into class lists.

This is the payoff act. Everything from Act 2 Step 2.6 and 2.7 has a Tailwind equivalent:

/* flexbox */
display: flex        ->  flex
flex-direction: row  ->  flex-row        |  column -> flex-col
justify-content      ->  justify-start | center | between | around | evenly
align-items          ->  items-start | center | end | stretch
gap: 12px           ->  gap-3
flex: 1             ->  flex-1
flex-wrap: wrap     ->  flex-wrap

/* grid */
display: grid        ->  grid
grid-template-columns: repeat(3, 1fr)  ->  grid-cols-3
grid-template-columns: 200px 1fr       ->  grid-cols-[200px_1fr]
grid-template-rows: auto 1fr         ->  grid-rows-[auto_1fr]
gap: 16px           ->  gap-4

/* sizing */
width: 50%          ->  w-1/2
width: 100%         ->  w-full
max-width: 640px    ->  max-w-xl
height: 100vh       ->  h-screen
aspect-ratio: 1     ->  aspect-square

The flex-1 and min-w-0 pair

Recall the Act 2 trap: flex items default to min-width: auto, so a long unbreakable word stops them shrinking. The fix is min-w-0. You'll write this constantly:

<div class="flex gap-4">
  <div class="min-w-0 flex-1">...</div>
  <button class="shrink-0">Save</button>
</div>

shrink-0 does the mirror-image job: stop this item from shrinking.

Centering

<!-- centre a single element, both axes -->
<div class="min-h-screen grid place-items-center">...</div>

<!-- centre a row, push the ends apart -->
<div class="flex items-center justify-between">...</div>

<!-- centre text -->
<p class="text-center">...</p>

Pattern worth memorising: flex items-center justify-between is the single most common layout in real dashboards — label on the left, action on the right. And grid place-items-center is the shortest "centre everything" in CSS.

What to notice

  • Tailwind's gap-3 is 0.75rem = 12px, while gap-4 is 1rem = 16px. Always map class numbers to the Act 2 scale — the spacing number is the CSS number divided by 4 (except 0 and fractions).

Challenge — Rebuild your Act 2 layouts

  • Tailwind v3 has arbitrary grid templates: `grid-cols-[240px_1fr_240px]`.
  • For the responsive navbar, use `flex-col md:flex-row` plus `md:hidden` on a mobile menu button.

3.4 — Variants

Master the prefix syntax — responsive, state, group, peer.

A variant is a prefix that changes when the utility applies.

Responsive variants

flex-col md:flex-row        /* column on mobile, row from 768px up */
p-3 md:p-8 lg:p-12
hidden md:block
text-sm md:text-base lg:text-lg
grid-cols-1 sm:grid-cols-2 lg:grid-cols-4

Tailwind's breakpoints: sm 640px, md 768px, lg 1024px, xl 1280px, 2xl 1536px. Mobile-first, same as Act 2.

State variants

hover:bg-indigo-500
focus:ring-2 focus:ring-indigo-500 focus:outline-none
active:scale-95
disabled:opacity-50
group-hover:text-white
peer-invalid:text-red-500

The important ones for quality work:

  • focus-visible: — shows the focus ring for keyboard users but not mouse users. Always use it instead of focus: for buttons — otherwise clicking a button leaves an ugly ring behind. This is an accessibility detail that separates good work from great work.
  • group / group-hover: — style a parent when a child is hovered. The parent gets group, the child gets group-hover:*.
  • peer / peer-invalid: — style a sibling based on a preceding sibling's state. Perfect for form validation: the input gets peer, and an error message gets peer-invalid:text-red-500.

Order matters in the class list. Tailwind generates CSS in a fixed order, not in the order you write them. When two utilities conflict, the one defined later in Tailwind's output wins — not the one later in your class attribute. (In Tailwind v4, conflicting utilities are resolved by source order in your class list instead. Either way: don't rely on it — use variants to disambiguate.)

A group-hover card

&lt;div class="group relative overflow-hidden rounded-xl"&gt;
  &lt;img src="/photo.jpg" class="h-48 w-full object-cover transition duration-300 group-hover:scale-105" /&gt;
  &lt;div class="absolute inset-0 bg-gradient-to-t from-black/70 to-transparent
              opacity-0 transition group-hover:opacity-100"&gt;
    &lt;p class="absolute bottom-4 left-4 text-white font-semibold"&gt;Read more&lt;/p&gt;
  &lt;/div&gt;
&lt;/div&gt;

What to notice

  • The group class must be on the parent; group-hover: goes on the child that should react.
  • Add transition to the parent and duration-300 to control the timing of the state change.

Challenge — A product card with real states

3.5 — Dark Mode

Build dark mode with CSS variables so it doesn't require duplicating every class.

There are two ways to do dark mode in Tailwind, and the difference matters.

Approach A — duplicate every class (the naive way)

<div class="bg-white text-gray-900 dark:bg-gray-900 dark:text-gray-100">...</div>

This works, but every element needs both variants, and it's easy to forget one. It also can't be a "toggle" that affects third-party content.

Approach B — CSS variables (the right way)

Define semantic tokens once, and let dark mode redefine the tokens:

:root {
  --background: 0 0% 100%;
  --foreground: 222 47% 11%;
}
.dark {
  --background: 222 47% 11%;
  --foreground: 210 40% 98%;
}
body { background: hsl(var(--background)); color: hsl(var(--foreground)); }

Then every element uses the semantic token, and the whole theme flips from one class on a root element. This is exactly how shadcn/ui does it — and it's why shadcn's bg-background works in dark mode without a single dark: variant on the element.

Configuring the strategy

// tailwind.config.js
module.exports = {
  darkMode: 'class',   // instead of the default 'media'
}

With darkMode: 'class', dark mode is active when an ancestor has the dark class. With the default 'media', it follows the OS setting and you can't toggle it manually.

Two real gotchas:

1. Flashing white. On a dark-mode site, the browser may paint a white page before your JS adds the dark class. The fix is a tiny inline script in <head> that sets the class before first paint (read the stored preference and apply it immediately).

2. Images and logos. Dark mode doesn't invert your PNGs. You need explicit handling — a dark: variant on the image, or CSS filter: invert() for icons.

The anti-flash snippet (goes in <head>, before any stylesheet)

&lt;script&gt;
  if (localStorage.theme === 'dark' ||
      (!('theme' in localStorage) &amp;&amp; matchMedia('(prefers-color-scheme: dark)').matches)) {
    document.documentElement.classList.add('dark');
  }
&lt;/script&gt;

What to notice

  • Act 5's dark-mode project does exactly this — it's the perfect place to apply everything from Acts 3 and 4 together.

Challenge — A theme that persists

Build a proper theme switcher:

  1. A button that toggles dark mode.
  2. The choice persists across reloads — that means localStorage (Act 4 Step 4.9 will show you the API).
  3. On first visit, respect the OS setting via matchMedia('(prefers-color-scheme: dark)').
  4. Add the anti-flash snippet to the <head> so the page never flashes white.
  5. Use the CSS-variable approach (Approach B) so you only write bg-background and text-foreground once.

Bonus: add a "system" option that follows the OS and updates live when the OS changes.

Stuck? Open the hints
  • `localStorage.setItem('theme','dark')` and `localStorage.getItem('theme')` — you'll use these in the Act 5 dark-mode project too.
  • The anti-flash script must run in <head> BEFORE the stylesheet, so the class is set before the first paint.

3.6 — Customising & Extracting

Make Tailwind yours — custom colours, fonts, and a rule for when to break out of utilities.

The config file

// tailwind.config.js
module.exports = {
  content: ['./src/**/*.{html,js,jsx,ts,tsx}'],
  theme: {
    extend: {
      colors: {
        brand: {
          50: '#eef2ff',  100: '#e0e7ff',  500: '#6366f1',  900: '#312e81',
        },
      },
      fontFamily: {
        sans: ['Inter', 'system-ui', 'sans-serif'],
      },
      spacing: { 18: '4.5rem' },
    },
  },
}

After that, bg-brand-500 and text-brand-900 work exactly like the built-in colours. extend adds to the defaults; theme: { colors: {...} } (without extend) replaces them.

The content array is critical. Tailwind scans your files to find which classes you actually used, and only generates those. If a class isn't in your content globs, it simply won't exist in the output. This is why dynamically constructed class names don't work:

// BROKEN — Tailwind can't see this class name
const cls = `bg-${color}-500`;
// BROKEN — same reason
const cls = color === 'red' ? 'text-red-500' : 'text-blue-500';
// WORKS — both class names appear literally in the source
const cls = color === 'red' ? 'text-red-500' : 'text-blue-500';

That third one is the fix, and it's the same trick used in every design system.

When to extract a component

Use @apply to name a repeated set of utilities:

@layer components {
  .btn-primary {
    @apply rounded-lg bg-indigo-600 px-4 py-2 font-medium text-white
           hover:bg-indigo-500 focus-visible:ring-2 focus-visible:ring-indigo-300;
  }
}

Then class="btn-primary" in your markup.

When to extract: the same list appears three or more times, and the list is long enough to hurt. When not: for one-off styles, for anything you need to tweak in different places, or for a "component" that's just one or two utilities — the abstraction costs more than it saves.

And a big one: components with behaviour (a dropdown, a modal, a combobox) don't belong in Tailwind at all. That's what a component library like shadcn/ui or Radix is for. shadcn gives you the structure and behaviour as copy-paste React code, styled with Tailwind utilities. That's the Day-2 shape of things, and it all comes from what you've learned here.

@apply in practice

@layer components {
  .card {
    @apply rounded-xl border border-gray-200 bg-white p-6 shadow-sm;
  }
  .btn {
    @apply inline-flex items-center justify-center gap-2 rounded-lg
           px-4 py-2 text-sm font-medium transition;
  }
  .btn-primary { @apply bg-indigo-600 text-white hover:bg-indigo-500; }
  .btn-ghost   { @apply text-gray-700 hover:bg-gray-100; }
}

What to notice

  • In Tailwind v4 there's no tailwind.config.js by default — you configure with a CSS-first @theme block in your stylesheet. The v3 config shown here is still the mental model, and most tutorials use it.
  • @apply is convenient but has a downside: it hides the styles from the HTML. When you need to override one property, you're back to specificity fights.
