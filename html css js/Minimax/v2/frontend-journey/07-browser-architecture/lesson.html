Browser Architecture

What the browser is actually doing, from the moment you hit Enter to the moment pixels appear.

You've written HTML, CSS and JavaScript. Now let's look at the machine that runs them. This act is the "why" behind a surprising number of rules you already follow — why defer exists, why transform is fast, why images need dimensions, and why a long function freezes the page.

7.1 — From Bytes to a Render Tree

Understand the pipeline: HTML → DOM, CSS → CSSOM, DOM + CSSOM → Render Tree.

Step by step

  1. Parse HTML → DOM. The browser reads bytes, decodes them, and builds a tree of nodes. It doesn't wait for the whole file — it renders progressively as content arrives. (This is why content flashes in as it loads.)
  2. Parse CSS → CSSOM. A separate tree of style rules, and a computation of which rules apply to which nodes. CSS is render-blocking by default: the browser won't paint until the CSSOM is ready, because painting unstyled content then restyling causes a flash.
  3. Combine them → Render Tree. The DOM tree filtered to only visible nodes, each with its computed style attached. (Elements with display: none are excluded. Elements with visibility: hidden are included — they're painted as transparent, so they still occupy space.)
  4. Layout → Paint → Composite. Next step.
HTML bytes  ──parse──>  DOM ──┐
                                    ├──combine──>  Render Tree ──> Layout ──> Paint ──> Composite
CSS bytes  ──parse──>  CSSOM ─┘

The key insight: DOM + CSSOM = Render Tree. JavaScript is not in this pipeline. Which is why a <script> in the <head> without defer stops the parser completely — the DOM can't be built past that point, so nothing can render.

Why <style> blocks in the head are bad

Each <style> block is parsed synchronously and blocks rendering. Ten of them = ten render-blocking pauses. One external stylesheet = one request, one pause, and it's cacheable.

Where JavaScript fits

JavaScript can also block the parser. A classic <script> in the <head> means: stop, download, execute, then continue parsing. During that time, nothing renders.

  • Open DevTools → Elements and note that the DOM is built live as HTML streams in. Pause the network throttling in the Network panel to watch it happen.
  • In the Performance panel, the top track shows exactly this: parse HTML, parse CSS, then the long purple "Layout & Paint" bars.

7.2 — Layout, Paint & Compositing

Know the three rendering stages and which of your CSS choices make each one expensive.

Layout (reflow)

The browser calculates the exact position and size of every box in the render tree. This is geometry — expensive, and triggered by changes to width/height/margin/padding/font-size/position.

It's usually global: change one element's size and the browser recalculates the layout for everything that might be affected. (Modern browsers optimise this, but the mental model is right.)

Paint

The browser fills in the pixels — drawing text, colours, borders, shadows, images. It produces a list of draw commands. Triggered by changes to color, background, box-shadow, border-radius, etc.

Compositing

The browser assembles the painted layers into the final image on screen. If a layer can be handled by the GPU, moving it is nearly free.

change width      -> layout  -> paint -> composite   (slow)
change color      ->          paint -> composite   (medium)
change transform  ->                   composite   (fast, GPU)

This is the payoff of Act 2 Step 2.10. Animating transform and opacity skips layout and paint entirely — the compositor just re-positions an existing layer. That's why they're the only two properties you should animate in hot paths.

Layers

The browser promotes elements to their own compositing layer when it needs to: elements with transform, opacity < 1, position: fixed, will-change, filter, backdrop-filter, and video/canvas.

Layers are not free — each one consumes memory (a full bitmap of the layer). will-change: transform on 500 elements can genuinely hurt performance. Use it sparingly, on elements you're about to animate.

Layout thrashing

// BAD - read then write, in a loop. Each iteration forces a synchronous layout.
elements.forEach(el => {
  const h = el.offsetHeight;      // READ  -> forces layout
  el.style.height = h * 2 + "px";  // WRITE -> invalidates it again
});

// GOOD - batch all reads, then all writes.
const heights = elements.map(el => el.offsetHeight);   // all reads
elements.forEach((el, i) => { el.style.height = heights[i] * 2 + "px"; });  // all writes

This is the single most common cause of "my animation is janky". The Performance panel shows it as repeated purple "Layout" bars inside a long task.

Composite-only properties

transform: translate / scale / rotate   ✅ GPU
opacity                                  ✅ GPU
filter, backdrop-filter                  ✅ GPU
will-change: transform                   ⚠️  use sparingly
width, height, top, left, margin         ❌ forces layout

What to notice

  • In the Performance panel, purple bars = Layout, green bars = Paint, light blue = Composite. If your animation produces purple bars, you're animating the wrong property.
  • DevTools → Rendering → "Paint flashing" makes the browser flash the screen every time it repaints — an amazing way to see what's expensive.

Challenge — Find the thrashing

Write two versions of an animation that moves 200 elements' heights:

  1. A bad version: read and write inside the loop.
  2. A good version: batch reads, then batch writes.

Measure both with performance.now(), then record both in the Performance panel. What do the traces look like?

Then, third version: animate with transform: translateY() instead of height, and compare the paint behaviour.

Stuck? Open the hints
  • In the Performance panel, look for a series of thin purple bars with gaps — that's layout thrashing, and it looks like a sawtooth.
  • The composite-only version should show almost no purple or green at all — just a light blue composite bar.

7.3 — The Critical Rendering Path

Learn the checklist for making a page appear fast — the highest-leverage frontend skill.

The critical rendering path is the sequence of steps the browser takes to go from "HTML arrives" to "first pixels on screen":

HTML  -> parse -> DOM ─┐
                        ├-> Render Tree -> Layout -> Paint -> Composite -> PIXELS
CSS   -> parse -> CSSOM ┘
JS    -> execute -> (may block) -> style recalc -> layout -> paint

The goal of optimisation: get the first meaningful pixels on screen as fast as possible, then let the rest arrive progressively.

The optimisation checklist

  1. Minimise the critical chain. Every resource in the chain delays first paint. HTML → CSS → JS → fonts → images.
  2. Defer JavaScript. defer or type="module". Never a blocking script in the head.
  3. Inline critical CSS. Put the CSS needed for the first screen directly in a <style> in the head, and load the rest asynchronously: 
    <link rel="preload" href="styles.css" as="style" onload="this.rel='stylesheet'">
<noscript><link rel="stylesheet" href="styles.css"></noscript>
  4. Preload key resources. <link rel="preload" as="font" crossorigin href="..."> — fonts are a classic hidden dependency, because CSS discovers them late.
  5. Don't block on fonts. font-display: swap shows a fallback immediately instead of invisible text. (Or use optional and preload.)
  6. Optimise images. Modern formats (WebP/AVIF), correct dimensions (zero CLS), loading="lazy" below the fold, srcset for responsive sizes.
  7. Split CSS. Critical CSS inline, rest deferred. Modern build tools do this automatically.
  8. Reduce server round trips. HTTP/2 or HTTP/3 multiplexes requests over one connection. Fewer, smaller files beat many small ones.

What the browser downloads, and when

Open the Network panel, sort by "Waterfall" view, and you'll see the dependency chain. Typical shape:

HTML (0ms)  ──┬─> CSS (50ms) ──> render-blocking
               ├─> font (80ms) ──> blocks text paint
               ├─> image (120ms) ──> discovered late
               └─> JS (60ms, deferred) ──> after first paint ✓

Preload, prefetch, preconnect

TagMeansUse for
preload"I need this now"the font, the critical image

What to notice

  • The Network panel's Waterfall view is the single best way to understand page performance. Open it on any real site and look at the shape of the bars.
  • font-display: swap is set on the @font-face rule, not on the <link> tag.

Challenge — Optimise a real page

Take any page you like (or build a simple one) and run the checklist against it:

  1. Record a baseline performance profile in the Performance panel. Note LCP (the largest contentful paint marker) and the total blocking time.
  2. Add defer to every script. Re-measure.
  3. Add explicit width and height to every image. Re-measure CLS.
  4. Add font-display: swap to any web font (or remove the font).
  5. Add a preload for the largest above-the-fold image.
  6. Run Lighthouse before and after. Which metric improved most, and why?
Stuck? Open the hints
  • Lighthouse's "Largest Contentful Paint" and "Total Blocking Time" numbers are the two to watch. The Performance panel shows LCP markers on the timeline.
  • Lighthouse is in DevTools → Lighthouse tab. Run it against the file:// page or a local server.

7.4 — Rendering, Tasks & Responsiveness

Connect the event loop to what the user actually sees, and understand INP.

Remember the event loop (Act 4 Step 4.17). Here's the browser's version, with rendering folded in:

  ┌─ pick a task (macrotask): timer, event, I/O
  │    run it on the call stack
  │    if it takes > 50ms -> it's a LONG TASK (bad for INP)
  ├─ drain the microtask queue (promises)
  ├─ if the frame is due: RENDER (style -> layout -> paint -> composite)
  └─ repeat

The browser renders between tasks, not during them. That's why a synchronous loop of 500ms means 500ms of nothing happening on screen — no scroll, no click response, no animation frame.

Long tasks and INP

A long task is any main-thread task taking more than 50ms. While it runs, the browser can't respond to input, and the frame can't be painted.

INP (Interaction to Next Paint) measures the delay between a user interaction and the next frame that reflects it. INP is essentially "how long did the user wait after clicking?"

User doesGoodBad
Clicks a buttonhandler is fast, React re-renders in one framehandler does a 300ms calculation first
Types in a fieldstate update is cheapeach keystroke re-renders 5,000 rows
Scrollstransform-only animationscroll handler queries layout each event

Breaking up long tasks

// Instead of one long task:
items.forEach(item => process(item));

// Yield between chunks:
async function processAll(items) {
  for (let i = 0; i < items.length; i++) {
    process(items[i]);
    if (i % 100 === 0) await new Promise(r => setTimeout(r, 0));
  }
}

Each await yields to the event loop, letting the browser paint and process input between chunks. This is called yielding, and it's how you keep a long job responsive without a worker.

The frame budget

At 60fps, you have 16.7ms per frame. A frame that takes longer means dropped frames. At 120Hz, 8.3ms.

Spend it: ~5ms scripting, ~5ms style/layout/paint, ~5ms idle buffer. If you're consistently over, you have a jank problem — and the Performance panel will show you exactly which part is over budget.

What to notice

  • The Performance panel flags long tasks with a red triangle in the top-right corner of the main-thread track. Hover it to see how long it was and which script caused it.
  • Chrome's "Rendering" panel has a "Frames Per Second" meter in the corner of the viewport when you enable it — watch it while you interact with your app.

Challenge — Make a janky thing smooth

  1. Build a page with 1,000 rows and a button that sorts them on click (a real O(n log n) sort on 1,000 items is enough to feel slow).
  2. Record a Performance profile while clicking it. Where's the long task?
  3. Break the sort into chunks with await between them, yielding every 100 items.
  4. Re-measure. Did the total time change? Did responsiveness change? (This is the point: total time may be the same or slightly worse, but the page stays responsive.)
  5. Now move the sort into a Web Worker (Act 6 Step 6.6) and compare all three.
Stuck? Open the hints
  • The Performance panel's "Interactions" track shows INP — click the flag markers to see the delay for each interaction.
  • Yielding with await new Promise(r => setTimeout(r, 0)) works, but scheduler.yield() (Chrome only) is more explicit.
