Your Five Projects

Everything so far, assembled. Each project is small on purpose — the goal is the pattern, not the pixels.

These are the five you asked for, in increasing order of difficulty. Each one is a complete, working app in a single file. Open it, run it, break it, then extend it with the challenge.

How to work through these: don't just read the code. For each project, delete the JavaScript and write it yourself using the hint list. If you can do that, you've got the concept. If you can't, re-read the explanation and try again. These five projects are the muscle you'll need tomorrow.

The shape they all share

1. Find the elements       (querySelector / querySelectorAll)
2. Keep the state          (a let variable, or a class)
3. Write a render function (state -> DOM)
4. Listen for events       (addEventListener)
5. On event: change state, then call render

That loop — state → render → event → state — is the entire mental model of React. Every project below is a hand-rolled version of it, and when React arrives tomorrow you'll recognise it immediately.

5.1 — Project 1 — Background-Changing Button

The smallest complete interaction: find an element, listen, change it.

What it teaches

  • Finding elements with querySelector
  • Listening for clicks with addEventListener
  • Changing styles from JavaScript
  • Why you usually change a class instead of a style

How it's built

const btn = document.querySelector("#cycle");
const box  = document.querySelector("#box");
const colors = ["#6366f1", "#10b981", "#f59e0b", "#ef4444", "#8b5cf6"];

let index = 0;                                   // the state

btn.addEventListener("click", () => {
  index = (index + 1) % colors.length;            // change state
  box.style.backgroundColor = colors[index];     // render
  label.textContent = colors[index];
});

Note the two kinds of "state change" here. The page's background colour is set with style.backgroundColor — a direct style change. The button's class is changed with classList — and the CSS decides what that class looks like.

Prefer the class approach whenever you can. The CSS stays in the stylesheet (where a designer can find it), and JavaScript just says "this is now in the active state". You'll see this in the dark mode project.

The state → render loop

Even this tiny app has a state (index) and a render step. As projects get bigger, you'll separate them into a named render() function. Do that deliberately in project 3.

What to notice

  • (index + 1) % colors.length wraps around. The modulo operator is how you cycle through a list forever.
  • Setting element.style.X writes an inline style, which beats your stylesheet. If you later try to style it with CSS, use element.style.removeProperty('background-color') or switch to classes.

Challenge — Extend it

  1. Add a "Random" button that picks a random colour (avoid picking the same colour twice in a row).
  2. Add a "Reset" button that returns to the first colour and sets index = 0.
  3. Make the button's own background match the current page colour (use classList or set the style) — and think about what happens when the button is the same colour as the page.
  4. Add a keyboard shortcut: press Space anywhere to trigger the same action. (Hint: document.addEventListener("keydown", ...) and check event.code === "Space".)
Stuck? Open the hints
  • Random that avoids a repeat: let next; do { next = Math.floor(Math.random() * colors.length); } while (next === index);
  • For the keyboard shortcut, be careful — if the user is typing in an input, Space should type a space, not trigger your button. Check event.target.tagName.

5.2 — Project 2 — Number Counter

Hold state in a variable, render it, and handle multiple inputs to the same state.

What it teaches

  • State held in a let variable
  • Multiple elements reading from one piece of state
  • Separating a render() function from the event handlers

How it's built

let count = 0;

function render() {
  display.textContent = count;
  minusBtn.disabled = count <= 0;         // state can affect the UI
  plusBtn.disabled = count >= 100;
}

plusBtn.addEventListener("click", () => { count++; render(); });
minusBtn.addEventListener("click", () => { count--; render(); });
resetBtn.addEventListener("click", () => { count = 0; render(); });

This is the pattern to internalise. Notice:

  • The event handlers do not touch the DOM directly. They change count and call render().
  • render() is the only place that writes to the DOM.
  • Because of that, you can change the state from anywhere — a button, a keyboard shortcut, a timer — and the UI stays correct.

This is exactly how React works: you change state, and the framework calls render for you. You're about to build React by hand.

Also notice: the disabled state

minusBtn.disabled = count <= 0 — the UI is derived from state, and it also controls what the user can do. That's a nice property: you can't get into an invalid state, because the invalid state isn't representable in the UI.

What to notice

  • A disabled button doesn't fire click events — so the counter can't go below zero even if someone calls the handler directly. (Well — it can, if they call the function. Guard in the handler too.)
  • Using textContent (not innerHTML) is right here: the count is data, not markup.

Challenge — Extend it

  1. Add a "step size" input. Changing it changes how much +/- moves the counter.
  2. Add a reset button that also restores the step size to 1.
  3. Show a running total of every increment (e.g. "+3, +1, +10" — a history). Clear it on reset.
  4. Make the counter display turn red when it reaches the max, and green at the min.
  5. Persist the count in localStorage so it survives a refresh.
Stuck? Open the hints
  • For the step input: document.querySelector('#step').value gives a string — use Number(...) on it.
  • localStorage.setItem('count', count) and localStorage.getItem('count'). Remember it returns a string, so wrap it in Number().

5.3 — Project 3 — Progress Bar

Animate a value over time, and learn why you should animate with CSS transitions, not a tight loop.

What it teaches

  • setInterval / clearInterval
  • Animating a width with a CSS transition
  • Why you should not update the DOM 60 times a second

How it's built

let progress = 0;
const INTERVAL = 40;   // ms between ticks

function render() {
  bar.style.width = progress + "%";
  label.textContent = progress + "%";
}

const timer = setInterval(() => {
  progress += 2;
  if (progress >= 100) {
    progress = 100;
    clearInterval(timer);          // stop it!
    console.log("done");
  }
  render();
}, INTERVAL);

Why a CSS transition instead of manual animation? If you update width every 40ms, the browser repaints each time — and if you animate faster than that, you force layout on every frame (the "layout thrashing" problem from Act 2 Step 2.10).

Instead: set the width once, and let the browser's compositor animate the change smoothly. Your JS runs 25 times a second; the animation runs at the display's refresh rate. Let the browser do what it's good at.

Layout thrashing — the thing to avoid

// BAD: read and write layout in a loop -> forces recalculation every iteration
items.forEach(item => {
  const h = item.offsetHeight;   // read  (forces layout)
  item.style.height = h + "px";  // write (invalidates layout)
});

// GOOD: read everything first, then write
const heights = items.map(i => i.offsetHeight);
items.forEach((item, i) => { item.style.height = heights[i] + "px"; });

Stopping cleanly

Timers keep running even when the user has moved on. Always keep the id and clearInterval it when you need to stop — and if the element might be removed, clear it then too.

What to notice

  • setInterval returns a number (the timer id). clearInterval(id) cancels it. setTimeout works the same way with clearTimeout.
  • A 40ms interval gives roughly 25 updates/second, and with a 300ms CSS transition the bar moves smoothly. Try 400ms and watch it look chunky — then compare.

Challenge — Extend it

  1. Make the progress bar accelerate — the further along it is, the faster it goes. (Try adding 2 + progress/20 each tick.)
  2. Add a second button "Fill instantly" that jumps straight to 100% with no animation (remove the transition class or set the width with a 0s duration).
  3. Add an <input type="range"> that lets the user drag the progress manually, which should cancel the running timer.
  4. Change the bar's colour based on the percentage: red under 30, amber under 70, green above. (Use a class and CSS — not inline styles.)
  5. Show a "Complete!" message when it hits 100%.
Stuck? Open the hints
  • To stop the CSS transition for one frame, you can set bar.style.transition = 'none', set the width, then restore it on the next frame with requestAnimationFrame.
  • The input event fires as the slider moves — use event.target.value.

5.4 — Project 4 — Dark Mode Toggle

Combine CSS variables, a class on the root element, localStorage, and system preference detection.

What it teaches

  • How to toggle a class on document.documentElement (the <html> element)
  • CSS variables as a theming system (Act 2 Step 2.3)
  • localStorage for persistence
  • matchMedia for reading the OS preference
  • The anti-flash script from Act 3 Step 3.5

How it's built

// 1. The theme is ONE class on <html>
// 2. CSS variables hold the colours
:root            { --bg: #ffffff; --fg: #15151d; --card: #f7f7fc; }
html.dark        { --bg: #101019; --fg: #e8e8f2; --card: #191926; }

body { background: var(--bg); color: var(--fg); }

// 3. JavaScript toggles the class and saves the choice
const root = document.documentElement;
root.classList.toggle("dark");
localStorage.setItem("theme", root.classList.contains("dark") ? "dark" : "light");

Why put the class on <html> and not on <body>? Because CSS variables cascade downward from where they're defined. Putting the class on the root means the entire page — including portals, modals, and anything you append later — picks up the theme. If you put it on <body>, anything outside the body stays light.

The full toggle logic

const root = document.documentElement;
const KEY = "theme";

function getStored() { return localStorage.getItem(KEY); }
function prefersDark() {
  return window.matchMedia("(prefers-color-scheme: dark)").matches;
}
function apply(theme) {
  root.classList.toggle("dark", theme === "dark");
  localStorage.setItem(KEY, theme);
}

The three modes

A real implementation supports three: light, dark, and system. "System" means "follow the OS", and it should update live when the OS setting changes while the page is open.

What to notice

  • classList.toggle(name, force) — the second argument forces the state to true/false instead of flipping it. Useful for apply(theme).
  • localStorage only stores strings. Storing an object means JSON.stringify on the way in and JSON.parse on the way out.

Challenge — Extend it

  1. Add a three-way switch: Light / Dark / System. "System" should remove the explicit class and follow the OS.
  2. Make "System" update live: listen to matchMedia("(prefers-color-scheme: dark)")'s change event.
  3. Add the anti-flash script to <head> so the page doesn't flash white before your JavaScript runs. (Act 3 Step 3.5.)
  4. Add a smooth transition between themes (the transition is already on the panel — now make sure every themed element transitions, not just the container).
  5. Add a third theme: sepia, with its own variable values.
Stuck? Open the hints
  • For the live OS listener: const mq = window.matchMedia('(prefers-color-scheme: dark)'); mq.addEventListener('change', handler);
  • A common trick for the anti-flash: put a small inline <script> in the head that sets the class before the body renders.

5.5 — Project 5 — Show / Hide Sidebar

The most common real UI pattern: a toggle that changes layout — and the accessibility details that make it good.

What it teaches

  • A boolean state variable
  • CSS transitions for a smooth width/transform change
  • aria-expanded — how you make a toggle button accessible
  • Persisting UI state in localStorage

How it's built

let open = true;

function render() {
  sidebar.classList.toggle("open", open);
  toggleBtn.setAttribute("aria-expanded", String(open));
  toggleBtn.textContent = open ? "Hide sidebar" : "Show sidebar";
}

toggleBtn.addEventListener("click", () => {
  open = !open;      // state
  render();          // render
});

aria-expanded is the detail that matters. A screen reader user can't see that the sidebar is open. Setting aria-expanded="true" on the button tells assistive technology the state of the thing the button controls. This is one line, and it's the difference between a toggle that works for everyone and one that doesn't.

Three ways to implement the hide

TechniqueProsCons
display: nonesimplestcan't animate; removes it from the tab order
width: 0animatablethe content is still focusable — a real a11y bug
transform: translateX(-100%)smooth, GPU-acceleratedstill in the tab order unless you also hide it

The correct approach combines them: animate with transform, and use visibility: hidden (or inert) at the end so the content leaves the tab order. Modern browsers support the inert attribute, which is exactly designed for this.

What to notice

  • inert on the closed sidebar removes it from the tab order and from screen readers, without removing it from the layout (so the transition still works).
  • The transition should be on the sidebar, and the class toggled on it — not on the parent, or you'll animate the wrong element.

Challenge — Extend it

  1. Add a keyboard shortcut ([ or B) to toggle — done above, but make sure it doesn't fire while the user is typing in an input.
  2. Persist the open/closed state in localStorage, and restore it on load.
  3. On small screens, make the sidebar an overlay (position fixed, full height) with a dark backdrop behind it that closes the sidebar when clicked.
  4. Add inert to the main content while the mobile overlay is open, so tabbing doesn't wander behind the overlay.
  5. Add a subtle animation: the sidebar slides, and the main content shifts.
Stuck? Open the hints
  • Overlay: position: fixed; inset: 0 auto 0 0; width: 260px; z-index: 40; and the backdrop position: fixed; inset: 0; background: rgba(0,0,0,.4); z-index: 30;
  • To close on backdrop click, give the backdrop an id and attach a listener to it.
