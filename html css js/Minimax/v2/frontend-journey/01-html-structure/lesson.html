HTML — Structure

HTML is a description of structure. Once this act clicks, the rest of the web makes far more sense.

You already know how to program, so HTML is going to feel small — and it should. There's no logic in it. No variables, no loops, no functions. It's a static description of structure, and your only job is to describe that structure correctly.

The one-sentence version: Python is a program you write; HTML is a result you write down.

# Python — you write instructions, the machine executes them
def build_page():
    return "<h1>Hello</h1>"
<!-- HTML — you write the result, the browser reads it -->
<h1>Hello</h1>

An HTML document is essentially a nested literal you write by hand, which the browser interprets and turns into real objects in memory:

page = {                     page =
  "tag": "html",               <html>
  "children": [                <head>...</head>
    {"tag": "head"},            <body>
    {"tag": "body"},            </body>
  ]                          </html>
}

That in-memory tree is the DOM (Document Object Model). You met it as a word today; in Act 4 you'll be mutating it directly. Today we only write the source.

1.1 — HTML Describes, It Doesn't Do

Lock in the mental model: HTML is a static description of structure, not a program.

Compare the two languages you already know in your head:

PythonHTML
You writeinstructionsthe finished structure
Who executes itthe Python interpreterthe browser
Logicconditionals, loops, functionsnone whatsoever
Outputwhatever your program decidesalways the same, for a given file

There is no if in HTML. There is no for. If you find yourself wanting either, you want JavaScript — and that's fine, that's what it's for. Act 4 gives you the language that actually computes.

The consequence that will save you hours

HTML never raises an error. Python throws NameError on a typo. HTML silently "corrects" your mistake and renders something you didn't ask for. It will not tell you. It will not even tell the console.

Your debugging rule, for the rest of your career: when the browser does something you didn't expect, stop staring at your source and open the DOM in DevTools. The browser may have rewritten your code.

This is the single most important habit in this act. HTML is error-tolerant by design — the parser makes a best guess and moves on, so that ancient pages from 1997 still render. It is a wonderful feature for the web and a nightmare for you until you learn to read the DOM instead of the source.

What to notice

  • HTML has no execution model, so it has no errors — only consequences.
  • The DOM (Elements panel) is the browser's interpretation of your source. When they disagree, the DOM is the truth.

Challenge — Find the non-HTML thinking

For each snippet below, say whether it is valid HTML and what the browser will actually do:

  1. <h1>Hello (no closing tag)
  2. <h1>Hello<h2>World</h2>
  3. <img src="cat.jpg">
  4. <p>A<div>B</div>C</p>

Then verify each answer in DevTools: write them into a page, inspect, and see the actual DOM. The browser's behaviour is the answer key — your instinct is not.

Stuck? Open the hints
  • The Elements panel shows you the truth. If a tag is missing, the tree will show you what the parser did instead.
  • Watch for tags the browser inserts that you never wrote — and tags it moved somewhere else.

1.2 — Anatomy of a Tag

Know the four parts of every element, and the one exception to the open/close rule.

<a href="https://example.com" class="btn" id="home-link">Click me</a>
PartWhat it isPython analogy
athe tag name / element typea class name
href, class, idattributes — key/value pairskeyword arguments
"https://example.com"the valuethe argument value
Click methe content (a text node)—
</a>closing tag—

Almost everything opens and closes. The exception is void elements: they have no content, so they have no closing tag.

<br>   <hr>   <img src="cat.jpg" alt="A cat">
<input type="text">   <meta charset="UTF-8">   <link rel="stylesheet" href="a.css">

The full list of void elements is short enough to memorise: area, base, br, col, embed, hr, img, input, link, meta, param, source, track, wbr.

Why does this matter? Because it's the one place your XML instincts will betray you. Everything else: if you open it, you close it. Write </br> and the browser silently drops the stray close tag.

Attributes are always quoted

Always use "double quotes" or 'single quotes' around values. Unquoted values work in some cases and break in others — quoting is free, so quote everything.

Attributes with and without values

&lt;input type="text" name="email" placeholder="you@example.com"&gt;
&lt;input type="checkbox" checked&gt;              &lt;!-- boolean attribute --&gt;
&lt;button type="submit" disabled&gt;Send&lt;/button&gt;

What to notice

  • Boolean attributes (checked, disabled, required, hidden) are their own presence — no ="true". Writing checked="false" is still true, because the attribute is present. To turn one off, remove it.

  • If the <hr> looks wrong, check you didn't write </hr>.

1.3 — The Document Skeleton

Know what belongs in <head> vs <body>, and why the three meta tags matter.

<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>My Page</title>
  </head>
  <body>
    <!-- everything the user actually sees -->
  </body>
</html>
  • <!DOCTYPE html> — "browser, use modern mode." One line, never think about it again. Without it, browsers enter a quirky legacy mode that quietly breaks real layout and will cost you an hour of confusion.
  • lang="en" — the page's language. Screen readers use it to choose a voice; browsers use it for translation and hyphenation.
  • <head> — metadata for the browser, not for the user. The single exception: <title> is the browser tab text and the default bookmark name, and it's the one <head> content users actually see.
  • <meta charset="UTF-8"> — must be early, ideally first, so text with accents and emoji doesn't become mojibake.
  • viewport — the most important meta tag on the page. Without it, mobile browsers assume a ~980px-wide desktop viewport and zoom out, making everything tiny. This one line is the difference between a site that "works on mobile" and one that doesn't.
  • <body> — everything visible goes here.

The mental model: <head> is the label on the tin; <body> is the tin. The browser reads <head> to learn how to render the page, then renders <body>.

Where CSS and JavaScript live

<head>
  <link rel="stylesheet" href="styles.css">     <!-- CSS: a separate file -->
  <style> h1 { color: teal; } </style>        <!-- CSS: inline -->
  <script src="app.js" defer></script>         <!-- JS: a separate file -->
  <script> console.log("hi"); </script>        <!-- JS: inline -->
</head>

Prefer separate files. Inline <style> and <script> blocks can't be cached, can't be reused, and can't be linted. The one common exception is a tiny critical snippet that must run before the page paints.

What to notice

  • <title> inside <head> is the browser tab text — and also what shows up in search results and bookmarks.
  • defer on a <script> means: download it in parallel, but run it after the HTML is parsed. You'll learn why that matters in Act 7.

Challenge — Three skeletons, one difference

  1. Write a page with a <title> of "My Portfolio — Ana Silva" and a lang of pt-BR. Confirm the tab title changed.
  2. Delete the viewport meta and note the difference in how the page lays out (narrow the browser window to simulate a phone). Put it back.
  3. Add a <meta name="description" content="..."> with a one-sentence description. This is what search engines and social cards show — you'll see it again in Act 11.
  4. Put a <script src="does-not-exist.js"> in the head. Watch the Network panel. What happens, and why doesn't the page break?
Stuck? Open the hints
  • A 404 in the Network panel is not a page error — the browser just moves on. That's the same forgiving-parser philosophy as before, applied to resources.
  • Missing viewport makes mobile browsers scale the page down, so everything looks tiny and unreadable.

1.4 — Nesting & the Forgiving Parser

Understand how the browser builds the tree, and why your source and the DOM can disagree.

Elements nest inside each other, and that nesting defines the relationships in the DOM tree. But HTML has strict rules about what may contain what — and when you break them, the parser doesn't complain. It fixes your code.

The two famous cases

<!-- Case 1: nested paragraphs -->
<p>Outer <p>Inner</p></p>

<!-- Case 2: a <div> inside a <p> -->
<p>A <div>B</div> C</p>

In case 1, the browser sees the second <p> while still inside the first, closes the first one automatically, and you get two sibling paragraphs instead of nested ones. In case 2, <div> is a block-level element and is not allowed inside a paragraph — so the browser closes the <p>, puts the <div> outside it, and reopens a new <p> afterwards.

This is why "the code is right but it renders wrong" is so common in HTML. The fix is always the same: look at the DOM, find where the browser inserted or moved a tag, and fix that — not the tag you were staring at.

Which elements may contain which

The rule of thumb:

  • Inline elements (span, a, strong, em, code, img) may go inside block elements, and inside other inline elements.
  • Block elements (div, p, section, ul, li) may not go inside inline elements — the browser will move them out.
  • Interactive elements (<a>, <button>) cannot be nested inside each other.

You don't need to memorise a table. The parser will tell you — visually, in the Elements panel — every time it disagrees with you. Read the DOM and you'll never mis-nest again.

What to notice

  • The browser never tells you it changed your code. The Elements panel is the only place the truth is visible.
  • Auto-inserted <tbody> (around table rows) and auto-closed <p> are the two you'll hit most.

Challenge — Break it on purpose

Write each of these, then inspect the DOM and write down what the browser did and why:

  1. <p>One<p>Two</p></p>
  2. <ul><li>A<li>B</ul>
  3. <div><span>text</div>
  4. <strong>bold <p>not bold?</p></strong>
  5. A <table> with <tr> and <td> but no <tbody>

For each: did the DOM match your source? If not, what did the browser add, remove, or move?

Stuck? Open the hints
  • Case 4: <strong> is inline, so a block <p> inside it gets ejected.
  • Case 5: the browser inserts <tbody> for you. It's implied by the spec, and every modern browser does it.

1.5 — The Vocabulary of a Page

Learn the semantic elements, and the one rule that keeps HTML clean forever.

HTML gives you a set of elements that each mean something specific. Choosing the right one is most of what "writing good HTML" means.

ElementMeans
<header>introductory content of a page or section
<nav>major navigation links
<main>the one unique content of this page
<section>a thematic grouping, usually with a heading
<article>a self-contained piece of content (a blog post)
<aside>tangentially related content (a sidebar)
<footer>footer info for a page or section
<figure>/<figcaption>self-contained media with a caption

The rule that trips up every programmer

Choose the element by meaning, never by how you want it to look.

Want smaller text? Don't reach for <small> — that means legal fine print. Want a heading? Use <h3> and make it big with CSS. Want a clickable thing that goes somewhere? Use <a>, not <div> with a click handler.

CSS controls appearance. HTML controls meaning. Keeping those two jobs separate is what makes a codebase survive being handed to another person.

Why bother, if it "looks the same"? Three reasons, all of them real:

  1. Accessibility. A <nav> becomes a landmark a screen-reader user can jump to; a <div class="nav"> is invisible to them. <button> is focusable and announces itself as a button; <div onclick> is a div that mysteriously does something.
  2. SEO. Search engines weight semantic structure heavily.
  3. Maintainability. main > section > article is a selector that keeps working. .div-2 is a naming convention that dies at the first redesign.

Bad vs good — same pixels, different meaning

&lt;!-- Bad: meaning is lost --&gt;
&lt;div class="header"&gt;
  &lt;div class="nav"&gt;&lt;div class="link"&gt;Home&lt;/div&gt;&lt;/div&gt;
&lt;/div&gt;
&lt;div class="content"&gt;
  &lt;div class="post"&gt;&lt;div class="title"&gt;Hello&lt;/div&gt;&lt;/div&gt;
&lt;/div&gt;

&lt;!-- Good: meaning is in the markup --&gt;
&lt;header&gt;
  &lt;nav&gt;&lt;a href="/"&gt;Home&lt;/a&gt;&lt;/nav&gt;
&lt;/header&gt;
&lt;main&gt;
  &lt;article&gt;&lt;h1&gt;Hello&lt;/h1&gt;&lt;/article&gt;
&lt;/main&gt;

What to notice

  • A semantic element gives you free browser styling (default margins, list bullets, font sizes). You can override all of it — but you get a sane starting point for free.

Challenge — Semantics-only rewrite

  </div>
</div>

  <div class="headline">Ship faster</div>
  <div class="sub">Build, test, deploy.</div>
</div>

<div class="page-body">
  <div class="post">
    <div class="post-title">Why we rewrote our API</div>

1.6 — Headings, Lists & Text Semantics

Use the text-level elements correctly, and keep your heading outline valid.

Headings

One <h1> per page — the page's own title. Then <h2> for top-level sections, <h3> inside them, and so on. Don't skip levels.

Why? Screen-reader users navigate documents by heading outline, like a table of contents. Jumping from h2 to h4 breaks their mental model of the page's structure. And no, "I want it to look smaller" is not a reason to change the level — that's what CSS is for.

Lists

<ul>              <!-- unordered: bullets -->
  <li>First</li>
  <li>Second</li>
</ul>

<ol>              <!-- ordered: numbers -->
  <li>Step one</li>
  <li>Step two</li>
</ol>

<ol type="A">      <!-- A, B, C -->
<ol start="5">     <!-- starts at 5 -->

Every <li> must be inside a <ul> or <ol>. A stray <li> gets wrapped in an implicit <ul> by the browser.

Text-level semantics

ElementMeansNot
<strong>important"make it bold"
<em>emphasis"make it italic"
<code>a piece of code"use a monospace font"
<mark>text relevant to the current context"highlight it"
<small>side comments / legal fine print"make it tiny"
<abbr>an abbreviation, with a title—
<blockquote>a quotation"indent it"
<time>a machine-readable date—

The pattern: every one of these has a default appearance that happens to be reasonable, but the meaning is the point. <em> inside a sentence is stressed. <strong> is important. If you find yourself wanting italics for style, use CSS.

Two more you will use constantly: <span> (generic inline container) and <div> (generic block container). These are the escape hatches when nothing semantic fits — and "nothing semantic fits" is much rarer than people think. Reach for <div> as a last resort, not a first one.

What to notice

  • <code> and <pre> are two different things: <code> styles a run of code inline; <pre> preserves whitespace and line breaks (and combines with <code> for a code block).

Challenge — Fix the outline

Here is a document with a broken heading outline and mis-used text elements:

<h1>Blog</h1>
<h4>Latest post</h4>
<p>Published <em>today</em> by <strong>Ana</strong></p>
<h2>Latest post</h2>
<p>Read the <span style="font-weight:bold">full article</span> for details.</p>
<h3>More posts</h3>
  1. Rewrite it with a valid heading outline (one h1, then descend one level at a time).
  2. Replace every appearance-driven element with a meaning-driven one.
  3. Turn the final list of "more posts" into a real <ul>.
  4. Add a <time> element for "today" with a proper datetime attribute.
Stuck? Open the hints
  • A heading level should reflect the document's outline, not the font size. Both "Latest post" headings are the same kind of thing, so they should be the same level.
  • <time datetime="2026-10-22">today</time> — the attribute holds the machine-readable value, the text holds the human-readable one.

1.7 — Attributes Are Hooks

Understand id, class and data-* as the interface that CSS and JavaScript will grab onto.

This is where HTML stops being "just markup" and becomes the API that the rest of the frontend attaches to.

AttributeRulesAnalogyUsed by
idunique per pageprimary keyCSS #id, JS getElementById
classreusable, many per element, space-separateda category / tagCSS .class, JS querySelectorAll
data-*anything you inventextra record fieldsJS via el.dataset
<button class="btn primary" data-count="42" id="add-btn">Add</button>

Read it as: "a button, category btn, also primary, carrying a custom field count = 42, with the unique id add-btn."

Python brain: this is a database record. id is the primary key — unique, one per table. class is a many-to-many tag. data-* is a free-form column you invented for this table. In JavaScript, that button becomes an object with el.id === "add-btn", el.classList.contains("primary") === true, and el.dataset.count === "42".

Note the string: data-* values are always strings, because HTML attributes are text. You convert them yourself — Number(el.dataset.count).

Why this is the single most important idea in Act 1

You are not writing markup "for the browser". You are writing markup that your own CSS and your own JavaScript will target later. Every framework you use tomorrow — React, Next.js, shadcn — is built on exactly this: your components emit HTML, and they find each other via ids, classes and data attributes.

Give things semantic, stable names: id="checkout-form" beats id="div1". Six months from now, .search-bar still means something; .box does not.

Other attributes you'll meet constantly

  • href on <a> — the URL. href="#" is a placeholder that jumps to the top of the page.
  • src on <img>, <script>, <iframe> — the resource URL.
  • alt on <img> — the description (Act 1, Step 1.8).
  • type on <input> and <button> — the behaviour variant. On <button> the default is submit, which surprises people constantly.
  • target on <a> — _blank opens a new tab.
  • rel — relationship hints, including the security-critical noopener.

What to notice

  • class values are space-separated: class="btn primary" is TWO classes, not one class with a space in it.
  • A data-* attribute name must be lowercased and hyphenated in HTML: data-user-id becomes el.dataset.userId in JS (camelCase automatically).

Challenge — Name things like you'll find them in six months

Below is a page written with meaningless names. Rewrite the attributes so that:

  • every id is unique and describes what the thing is
  • every class describes a role or a style, and can be reused
  • at least one element carries a data-* attribute holding a piece of data that JavaScript would need (an id, a price, a status)
<div class="a" id="x1">
  <div class="b" id="x2">Buy Now</div>
  <div class="c">$49.00</div>
  <div class="d" id="x3">Add to cart</div>
</div>

Then explain in one sentence each: which is the id a JavaScript developer would look up, and why is the price a data-* rather than an id?

Stuck? Open the hints
  • One element, one id. If you need to identify two different product cards, that's a data-* (like data-product-id="123"), not two ids.
  • Classes are for reuse: two buttons that look the same share class="btn" even if their ids differ.

1.8 — Forms & Inputs

Learn the form vocabulary — this is the part that directly feeds your API, form-submit and file-upload work later.

Forms are the single most important interactive element on the web, and they're the bridge between HTML and everything you'll build in Act 6: reading input values, submitting data, uploading files. So this step matters more than it looks.

The anatomy

<form action="/subscribe" method="post">
  <label for="email">Email address</label>
  <input type="email" id="email" name="email" placeholder="you@example.com" required>

  <label for="plan">Plan</label>
  <select id="plan" name="plan">
    <option value="free">Free</option>
    <option value="pro" selected>Pro</option>
  </select>

  <label for="bio">Short bio</label>
  <textarea id="bio" name="bio" rows="4"></textarea>

  <label>
    <input type="checkbox" name="newsletter" value="yes">
    Send me the newsletter
  </label>

  <button type="submit">Subscribe</button>
</form>

Four rules that will save you

  1. Every input needs a label with a matching for. Clicking the label focuses the input, screen readers announce the label, and browsers validate correctly. Without it, users get an unlabelled box. This is the #1 accessibility bug in real code.
  2. name is what gets submitted. id is what CSS and JS use. They are different attributes serving different masters — a subtle point that trips everyone up once. An input with no name is not submitted at all.
  3. Use the right type. type="email" gives mobile keyboards and built-in validation; type="number", type="date", type="url", type="search" each do the obvious thing on mobile. Use type="text" only when nothing else fits.
  4. <button> defaults to type="submit". If your button isn't meant to submit the form, write type="button". A "Cancel" button without it will submit the form — one of those bugs you'll meet in week two of any job.

Security note, early. A <form> submits its values to action as application/x-www-form-urlencoded by default. If you ever put user input into that URL, understand that it lands in browser history, proxy logs and server logs. Modern apps almost always intercept the submit with JavaScript and use fetch() instead — Act 6, Step 6.4.

The input types you will actually use

&lt;input type="text"&gt;
&lt;input type="email"&gt;
&lt;input type="password"&gt;
&lt;input type="number" min="0" max="100" step="1"&gt;
&lt;input type="date"&gt;
&lt;input type="url"&gt;
&lt;input type="tel"&gt;
&lt;input type="search"&gt;
&lt;input type="checkbox"&gt;
&lt;input type="radio"&gt;
&lt;input type="file" accept="image/*" multiple&gt;
&lt;input type="hidden" name="csrf_token" value="abc123"&gt;
&lt;input type="range" min="0" max="100"&gt;
&lt;input type="color"&gt;

What to notice

  • A <label> can wrap its input instead of using for — both work, but for/id is easier to reuse.
  • required, min, max, pattern, step give you browser-native validation for free. You can style it with :invalid and :user-invalid.
  • placeholder is a hint, not a label. It disappears the moment the user types — never use it as the only label.

Challenge — A signup form, done right

  • Email — email input, required
  • Password — password input, required, minlength="8"
  • Country — a select with 3 options, one preselected
  • A "newsletter" checkbox, unchecked by default
  • A submit button labelled "Create account" and a second button that must not submit the form
  • Every input has a proper <label>

Extra credit: add a hidden input called signup_source with the value landing-page, and explain what it's for.

Stuck? Open the hints

  • The hidden input is for data your JavaScript or server needs but the user doesn't have to see — the same trick a real app uses for a CSRF token.

1.9 — Images, Links & Entities

Write accessible images and links, and handle special characters correctly.

Images

<img src="cat.jpg" alt="A cat asleep on a keyboard" width="300" height="200">
  • alt is not decoration. If the image fails to load, or a screen reader reads the page, that text is all the user gets. Describe the content and purpose — "A cat asleep on a keyboard", not "cat image" or "image1".
  • For a purely decorative image, alt="" is correct — screen readers will skip it entirely. alt="decorative" is worse than nothing.
  • Always set width and height. The browser needs them to reserve space before the image loads, which stops your page from jumping around. This is one of the cheapest real performance wins there is.
  • loading="lazy" defers loading off-screen images. One attribute, real speedup on long pages.

Links

<a href="https://example.com" target="_blank" rel="noopener">Example</a>

rel="noopener" is a security detail, and it's a good early taste of Act 8: a page opened in a new tab can otherwise reach back into the original tab's window object. Add it to every target="_blank" link, every time.

Use <button> for actions and <a> for navigation. A button that looks like a link is fine; a link that does something other than navigate is a bug waiting to happen (middle-click, "open in new tab", and keyboard users all break).

Entities

Three characters need escaping in HTML text:

CharacterEntityWhy
&&amp;starts a character reference
<&lt;starts a tag
>&gt;finishes a tag

There are also named entities for common characters: &nbsp; (a non-breaking space), &copy; (©), &hellip; (…), &mdash; (—), &rarr; (→).

Where escaping matters most: when you generate HTML from JavaScript. If you ever build markup with innerHTML and interpolate user input into it, you have created an XSS vulnerability. Act 8 Step 8.4 covers exactly this. The safe habit: use textContent whenever you're inserting data rather than markup.

What to notice

  • An <img> is a void element — no closing tag.
  • src can be relative (cat.jpg), absolute (/assets/cat.jpg), or a full URL. Relative paths are resolved against the page's URL, not the CSS file's.

Challenge — Accessible media page

Build a short article page:

  1. One <figure> containing an <img> and a <figcaption>
  2. The image needs a meaningful alt, plus explicit width and height attributes
  3. One link to an external site with target="_blank" and rel="noopener"
  4. One link with href="#" as a placeholder
  5. A paragraph containing &, < and > as real characters (not as &amp;)

Then verify: does the alt read naturally when spoken aloud? (Screen readers sometimes say "image of" for you — if yours does, don't start the alt with "image of".)

Stuck? Open the hints
  • <figure> is the container; <figcaption> goes inside it and is automatically associated with the image.
  • The browser converts &amp; to & in the rendered page. If you want a literal ampersand character on screen, write &amp; in the source.
