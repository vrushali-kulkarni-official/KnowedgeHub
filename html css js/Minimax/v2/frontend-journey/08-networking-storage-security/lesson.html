Networking, Storage & Security

How the web talks to servers, where data lives, and how to not let someone else take over your app.

This act covers the parts of the front end that aren't about pixels: how requests work, where you store things, and the three attacks you must be able to recognise and defend against.

Why this matters for you specifically: these are the topics that interviewers ask about, that break production apps, and that separate "I can build a website" from "I can build a safe website".

8.1 — HTTP Fundamentals

Understand the request/response model well enough to debug any API problem.

Every time your page loads a file, asks for data, or submits a form, the browser makes an HTTP request and the server sends back an HTTP response.

GET /api/users/42 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJhbGci...
Cookie: session=abc123
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax

{ "id": 42, "name": "Ana" }

Methods

MethodMeansSafe?Idempotent?
GETread a resourceyesyes
POSTcreate / trigger an actionnono
PUTreplace a resource entirelynoyes
PATCHpartially updatenono
DELETEremovenoyes

Safe = doesn't change server state. Idempotent = calling it twice has the same effect as calling it once. These matter for retries and caching.

Status codes

CodeMeaningWhat your code should do
200OKparse the body
201Createdparse the body, expect the new resource
204No Contentdon't call .json() — there's no body
301 / 308Permanent redirectfollow automatically
302 / 307Temporary redirectfollow automatically
400Bad Requestyour fault — fix the payload
401Unauthorizednot logged in (the name is a misnomer)
403Forbiddenlogged in, but not allowed
404Not Foundthe resource doesn't exist
409Conflictduplicate, or a stale version
429Too Many Requestsback off and retry later
500Server Errortheir fault — show a friendly message

401 vs 403 trips up everyone: 401 means "who are you?" (unauthenticated), 403 means "we know who you are, but no" (unauthorised).

Headers that matter

RequestResponse
Content-TypeContent-Type — what format the body is
AuthorizationSet-Cookie — the server setting a cookie
AcceptCache-Control, ETag — caching rules
OriginAccess-Control-* — CORS permissions

What to notice

  • fetch() by default sends Accept: */* and no Content-Type for a GET. Add headers explicitly with headers: { ... }.
  • A 204 response has an empty body — calling response.json() on it throws a JSON parse error. Check response.status === 204 first, or just check response.ok and only parse if there's content.

Challenge — Read the wire

  1. Open DevTools → Network, reload any page, and find the HTML document request. Read the status, the request method, and the response headers.
  2. Find a request that returned 304 (Not Modified) and explain what that means (hint: caching, Act 8 Step 8.7).
  3. Write a script that makes three requests to https://jsonplaceholder.typicode.com and logs, for each: the status, the content-type, and the number of keys in the parsed body.
  4. Then make one request to a URL that returns 404 and confirm your error handling (not a crash).
Stuck? Open the hints
  • The Network panel's "Headers" tab shows the raw request and response. "Payload" and "Response" tabs show the body.
  • A 404 still resolves — response.ok is false but nothing throws. Test both paths.

8.2 — Client-Side Storage

Choose the right storage mechanism for what you're building.

MechanismSizeSync?Sent to server?Cleared
Cookie~4KByesyes, every requestmanually / on expiry
localStorage~5-10MByesnonever (until cleared)
sessionStorage~5-10MByesnowhen the tab closes
IndexedDBlargeno (async)nomanually
Cache Storagelargeno (async)nomanually

Cookies

document.cookie = "theme=dark; path=/; max-age=3600; SameSite=Lax";
// read (only non-HttpOnly cookies are visible here!)
document.cookie;

Cookies are special because the browser attaches them to every request to that domain automatically. That's why auth sessions use them — the server doesn't need any client-side code.

Cookie flags:

  • HttpOnly — JavaScript can't read it. Always use for session tokens. This is your main defence against token theft via XSS.
  • Secure — only sent over HTTPS.
  • SameSite=Lax — not sent on cross-site POSTs. Your main defence against CSRF. (Modern browsers default to Lax.)
  • Path, Max-Age/Expires — scope and lifetime.

localStorage / sessionStorage

localStorage.setItem("theme", "dark");
localStorage.getItem("theme");        // "dark" or null
localStorage.removeItem("theme");
localStorage.clear();

// objects need JSON
localStorage.setItem("user", JSON.stringify({ id: 1 }));
JSON.parse(localStorage.getItem("user"));   // { id: 1 }

localStorage is synchronous. Reading it blocks the main thread. For anything large, use IndexedDB. And never store anything sensitive in localStorage — it's readable by any script on the page, so one XSS bug and your token is gone. (This is the central tension in Act 8 Step 8.6.)

IndexedDB

An asynchronous, transactional key-value database in the browser. It can store structured data, blobs and files, and it doesn't block the main thread. Its API is callback/promise-heavy, which is why most people use a small wrapper library.

Decision guide

I need to…Use
Send a token to the server on every requestCookie (HttpOnly)
Remember a user's theme / preferenceslocalStorage
Keep data that dies with the tabsessionStorage
Store a big dataset for offline useIndexedDB
Cache files for offline useCache Storage (+ a Service Worker)

What to notice

  • localStorage and sessionStorage throw a SecurityError in some privacy modes. Wrap access in try/catch if that matters.
  • Storage is per-origin: http://localhost:3000 and http://localhost:3001 are different origins and don't share storage. This trips people up constantly in development.
  • An HttpOnly cookie is invisible to document.cookie — but it IS still sent with requests. That's the whole point.

Challenge — A preferences store

Build a small preferences system:

  1. Store the user's theme, their name, and their "compact mode" toggle in localStorage.
  2. On page load, read all three and apply them to the page (theme class, name in a header, a CSS class for compact mode).
  3. Save each change immediately as it happens.
  4. Add a "Reset all" button that clears the app's keys (careful — don't call localStorage.clear() if other apps share the origin; remove your own keys instead).
  5. Now move the theme into a document.cookie instead, and explain what changed (and why you might not want that).
Stuck? Open the hints
  • A tiny helper makes this much cleaner: const store = { get(k, d) { return JSON.parse(localStorage.getItem(k)) ?? d }, set(k, v) { localStorage.setItem(k, JSON.stringify(v)) } }
  • Remember: localStorage.getItem returns null for a missing key, and JSON.parse(null) returns null — not an error.

8.3 — CORS

Understand why the browser blocks some requests, and how to fix it.

Same-origin policy: a page on https://a.com may only read responses from https://a.com. The "origin" is the triple scheme + host + port — https://example.com and http://example.com are different origins.

CORS (Cross-Origin Resource Sharing) is the mechanism that lets a server explicitly opt out of that restriction for specific origins.

The crucial thing: CORS is enforced by the browser, not the server. Your fetch() still goes out, and the server still processes it — the browser just withholds the response from your JavaScript.

That means: CORS is not a security control for your server. It protects the browser user's data. A non-browser client (curl, Postman, a server-side fetch) ignores CORS entirely.

Simple vs preflight

A "simple request" (GET/POST/HEAD, with simple headers like Content-Type: application/json… actually JSON is not simple) is sent directly, and the server must include Access-Control-Allow-Origin in the response.

Anything "non-simple" triggers a preflight: the browser first sends an OPTIONS request asking permission:

OPTIONS /api/users HTTP/1.1
Origin: https://myapp.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400

Only after a successful preflight does the real request go out.

HeaderMeaning
Access-Control-Allow-Originwhich origins may read this
Access-Control-Allow-Methodswhich methods are allowed
Access-Control-Allow-Headerswhich request headers are allowed
Access-Control-Allow-Credentialsallow cookies to be sent
Access-Control-Max-Agehow long to cache the preflight

Two rules that surprise people:

  1. With credentials, you cannot use Access-Control-Allow-Origin: *. You must name the exact origin. (Because * would allow https://evil.com to read the response with the user's cookies.)
  2. In fetch, sending cookies cross-origin requires credentials: "include" — and the server must send Access-Control-Allow-Credentials: true.

How to fix a CORS error

  1. Read the error in the Console — it names the exact header missing.
  2. Look at the Network panel for the failed request (often it's the OPTIONS request, and it's there even though your code never made one).
  3. If you own the server: configure it (Act 10 Step 10.2).
  4. If you don't own the server: you can't fix it from the client. Use a proxy on your own server, or find an API that allows CORS.

What to notice

  • A file:// page has the origin null — which many servers won't allow. That's why fetching from a local file often fails with CORS.
  • The preflight OPTIONS request appears in the Network panel. It may be marked as "(blocked)" or hidden behind a filter.
  • In the Network panel, DevTools can show you the CORS headers of a response under the response's Headers tab.

Challenge — Diagnose a CORS failure

  1. Write a script that fetches from https://api.github.com/users/octocat. Does it work? Why or why not?
  2. Now fetch from an endpoint that definitely doesn't send CORS headers (try https://httpbin.org/get or any random API). Read the error message carefully — what exactly is it telling you?
  3. In the Network panel, find the failed request. What type is it (the preflight OPTIONS or the actual request)? What status did it get?
  4. Open a request to a site that does send CORS headers and look at the Access-Control-Allow-Origin response header. What does it say?
  5. Write a short paragraph explaining, in plain English, what you would tell a backend developer to fix it.
Stuck? Open the hints
  • The Console error usually says: "Access to fetch at '...' from origin '...' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource."
  • The GitHub API works because it sends Access-Control-Allow-Origin: *.

8.4 — XSS & Content Security Policy

Recognise the three kinds of cross-site scripting and defend against them.

XSS (Cross-Site Scripting) = your app runs attacker-controlled JavaScript in a user's browser. If it works, the attacker can read the user's page, steal their session token, and act as them. It's the most common web vulnerability, and it is entirely preventable.

The three kinds

TypeHow the payload arrivesExample
Reflectedin the URL/search?q=<script>...</script>
Storedsaved in a database, shown to other usersa comment containing a script
DOM-basednever sent to the server — pure client-sidelocation.hash → innerHTML

The DOM-based one is the one to watch in modern apps, because it can hide in a client-side framework with no server involvement at all.

How it happens

// VULNERABLE - innerHTML parses and executes
el.innerHTML = userInput;

// ALSO VULNERABLE - building HTML strings
el.innerHTML = `<p>${userInput}</p>`;

// SAFE - textContent inserts text, never markup
el.textContent = userInput;

// SAFE - and if you must use innerHTML, sanitize first
el.innerHTML = DOMPurify.sanitize(userInput);

The rule: innerHTML is only safe for strings you wrote. textContent is safe for anything. If a framework gives you "dangerouslySetInnerHTML", that's the framework telling you the same thing.

Defence in depth

  1. Don't inject. textContent over innerHTML. This alone stops the vast majority of XSS.
  2. Sanitize when you must. DOMPurify is the standard. Never write your own sanitizer.
  3. Use a CSP (Content Security Policy) — the browser's last line of defence.
  4. Escape on the server too — defence in depth, because other clients consume your API.
  5. HttpOnly cookies — so even if XSS happens, the token can't be read.

Content Security Policy

<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self'; object-src 'none'">
DirectiveControls
default-srcthe fallback for everything else
script-srcwhere scripts may come from
style-srcwhere styles may come from
img-srcwhere images may come from
connect-srcwhere fetch/XHR may connect
frame-ancestorswho may embed this page (clickjacking)
object-src 'none'kill plugins (legacy XSS vector)

Strict CSP, no 'unsafe-inline'. A CSP that allows inline scripts allows inline scripts — an attacker who can inject a <script> tag can also bypass it. The modern strict version:

script-src 'self' 'nonce-{random-per-response}'

Each allowed script tag gets a unique nonce that the attacker can't know. This is how frameworks like Next.js implement CSP without breaking inline scripts.

Other browser security headers

HeaderDoes
Content-Security-Policyrestricts what the page may load/run
X-Frame-Options / frame-ancestorsprevents clickjacking
Strict-Transport-Security (HSTS)forces HTTPS
Referrer-Policycontrols how much URL is leaked in the Referer header
X-Content-Type-Options: nosniffstops MIME sniffing

What to notice

  • React escapes {"..."} by default, so setting innerHTML-like behaviour requires dangerouslySetInnerHTML. That name is a warning, not a convenience.
  • A CSP violation shows up in the Console as "Refused to execute inline script". That's the CSP working.

Challenge — Prove the difference

  1. Use the input above to paste <img src=x onerror="console.log('XSS!')">. With the safe renderer, nothing happens. Now call the unsafe renderer on the same input. What happens?
  2. Add a CSP to the page via a <meta http-equiv="Content-Security-Policy"> tag with script-src 'self' and try again. What does the Console say now?
  3. Write a renderUserList function that takes an array of { name, bio } and renders them safely. Then find the one place where you'd need innerHTML and explain what you'd do instead.
  4. Explain, in two sentences, why textContent is safe and innerHTML is not — in terms of what the browser does with the string.
Stuck? Open the hints
  • An onerror handler fires when the image fails to load — it's a reliable way to execute JS without a <script> tag.
  • The CSP message names the exact directive that blocked it.

8.5 — CSRF, SameSite & Tokens

Understand cross-site request forgery and how modern cookies mostly solve it.

CSRF (Cross-Site Request Forgery): the attacker can't read your data, but they can make your browser send a request to a site where you're logged in — because the browser attaches your cookies automatically.

<!-- on evil.com, while you're logged into bank.com -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker">
  <input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>

The browser sends the request with your session cookie. The server can't tell it apart from a legitimate one — because, from its point of view, it's a normal request from an authenticated browser.

Defences

  1. SameSite cookies — the modern default answer.
    • SameSite=Strict — the cookie is never sent on cross-site requests at all. Breaks nothing if you're a pure SPA; breaks things if you land on your site from an external link (you'd appear logged out for one request).
    • SameSite=Lax — sent on top-level GET navigations, not on cross-site POSTs. This is the modern default and the right choice for almost everything.
    • SameSite=None — always sent, requires Secure. Needed for genuine cross-site embedding (e.g. Stripe iframes).
  2. CSRF tokens — the server embeds a random token in the form, and checks it on submission. The attacker's page can't read your page, so it can't produce a valid token. The classic double-submit cookie pattern is a practical variant.
  3. Custom headers — a Authorization header set by JavaScript triggers a preflight, which a cross-site form can't cause. This is why token-based APIs are inherently CSRF-resistant.
  4. Check the Origin header server-side.

The clean modern rule: for a same-site SPA, use SameSite=Lax (or Strict) session cookies, and you're protected from CSRF without a token. If you need cross-site embedding, add CSRF tokens.

The related attack: clickjacking

An attacker iframes your page and overlays a transparent button, tricking a user into clicking it. Defended by frame-ancestors 'none' (or the older X-Frame-Options: DENY).

What to notice

  • CSRF requires the server to rely on cookies alone. If your API requires an Authorization header (a JWT), CSRF isn't possible — because a cross-site form can't set custom headers.
  • SameSite=None without Secure is rejected by modern browsers.

Challenge — Spot the vulnerable design

For each scenario, decide: is it vulnerable to CSRF? What should the server do?

  1. A banking site where the session is a HttpOnly; SameSite=Strict cookie, and actions are triggered by POST forms.
  2. An API where the client sends Authorization: Bearer <jwt> on every request.
  3. A legacy internal tool that uses a session cookie with no SameSite attribute and POST endpoints.

Then: for scenario 3, list the three mitigations you could apply (cookie's SameSite, a CSRF token, and checking the Origin header) and explain what each one stops.

Stuck? Open the hints
  • The key question for each: "does the browser attach the victim's credentials to a request the attacker can trigger?"
  • A CSRF token must be unpredictable and bound to the session — otherwise the attacker can guess it.

8.6 — JWT & Sessions

Understand what a JWT is, what it is not, and where to store one safely.

A JWT (JSON Web Token) is a compact, signed, self-contained token that carries claims. It's three base64url segments separated by dots:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjQyLCJyb2xlIjoiYWRtaW4iLCJpYXQiOjE3MDAwMDAwMDB9.Xk3abc123signature
└──────── header ────────┘ └────────── payload ──────────┘ └── signature ──┘
  • Header — the algorithm (HS256, RS256).
  • Payload — the claims: sub (subject/user id), iat (issued at), exp (expiry), plus whatever you add.
  • Signature — proves the token wasn't tampered with. The server verifies it with a secret key.

Decoding a JWT client-side

function decode(token) {
  const payload = token.split(".")[1];
  const json = atob(payload.replace(/-/g, "+").replace(/_/g, "/"));
  return JSON.parse(json);
}

const claims = decode(token);
console.log(claims.exp, new Date(claims.exp * 1000));

You can decode a JWT, but you cannot trust it. The payload is base64-encoded, not encrypted — anyone can read it. And you cannot verify the signature in the browser (that requires the secret key). Always treat a client-decoded JWT as untrusted display data. The server must verify it on every request.

Never put secrets in a JWT payload. It is visible to the user.

Access tokens vs refresh tokens

Access tokenRefresh token
Lifetimeshort (5-60 min)long (days-weeks)
Sent withevery API requestonly to the refresh endpoint
Containsclaimsa token ID
Revocablehard (until it expires)easy (server-side list)

Where to store the access token

StorageXSS riskCSRF riskVerdict
localStoragehigh — readable by any scriptnonesimple, common, risky
sessionStoragehighnonesame, but per-tab
HttpOnly cookienone — JS can't read ityes (mitigated by SameSite)strongest with SameSite=Lax
in-memory variablehigh (but gone on refresh)noneneeds a refresh flow

The modern consensus for a web app that needs Authorization headers: HttpOnly cookie + SameSite + CSRF protection. For a pure SPA with a backend you also control, the HttpOnly cookie wins on security. The "JWT in localStorage" pattern is common because it's easy, and it's genuinely weaker.

What to notice

  • atob is the browser's base64 decoder. JWT uses base64url, so you must replace - with + and _ with / — and pad with = if needed.
  • atob gives you a binary string. For UTF-8 text, use decodeURIComponent(escape(atob(s))) or TextDecoder.

Challenge — Build an auth helper

  1. Write decodeToken(token) that safely extracts the payload, and returns null for a malformed token (no try/catch crash).
  2. Write isExpired(token) using the exp claim.
  3. Write isAdmin(token) reading the role claim — and add a comment saying this is display only and the server must check authorisation itself.
  4. Write setSession(token) and getSession() using localStorage, and clearSession().
  5. Now the important part: write a short note (in a comment) explaining what would change if you used an HttpOnly cookie instead, and what you'd lose (the ability to read the token from JavaScript).
Stuck? Open the hints
  • Wrap JSON.parse in a try/catch — a malformed token is a normal thing to encounter.
  • Date.now() is milliseconds; JWT's exp is seconds. Divide by 1000.

8.7 — HTTP Caching

Understand how browsers cache, and how to make your app load fast on a second visit.

Caching lets the browser skip the network entirely for resources it already has. Two strategies:

1. Cache-Control (freshness)

Cache-Control: max-age=3600          // fresh for 1 hour
Cache-Control: no-cache          // always revalidate (but may still 304)
Cache-Control: no-store          // never cache (sensitive data)
Cache-Control: public, max-age=31536000, immutable   // for hashed assets
Cache-Control: private, max-age=0   // only the browser may cache it

2. ETag / If-None-Match (revalidation)

When a cached resource goes stale, the browser asks "has it changed?":

GET /app.js HTTP/1.1
If-None-Match: "abc123"

HTTP/1.1 304 Not Modified
ETag: "abc123"

304 means "your copy is still good" — no body is sent, and the browser uses its cached copy. That's how a "hard refresh" is actually cheap.

The good pattern for assets

Build tools put a content hash in the filename: app.9f3a2b.js. If the content changes, the filename changes, so you can cache it forever:

<script src="/app.9f3a2b.js"></script>   <!-- cache for a year -->
<link rel="stylesheet" href="/app.9f3a2b.css">

Meanwhile index.html should not be cached hard, so users get the new asset filenames immediately: Cache-Control: no-cache.

The rule of thumb: hashed filenames → cache forever. HTML → revalidate every time.

Cache-Control vs localStorage

They're different tools. The HTTP cache stores responses (images, JS, CSS) and is managed by the browser with heuristics you don't control precisely. localStorage stores your data and is entirely under your control. Don't cache API responses in localStorage by default — use the HTTP cache and ETag revalidation, which is far more efficient.

Seeing it work

In DevTools → Network, check the "Disable cache" box and compare:

  • First load: many 200s with full bodies
  • Reload: 304s (or "from memory cache" / "from disk cache")

The Size column shows "(disk cache)" vs the actual transfer size. That's the metric that matters — transfer size, not content size.

What to notice

  • The Network panel's Size column shows two numbers: the transferred size and the decoded size. A cached resource shows 0 B transferred.
  • In DevTools, the "Disable cache" checkbox only works while DevTools is open — that's why a normal reload may look cached when a hard reload doesn't.

  3. Reload. Which requests were served from cache? What did the transfer size become?

  5. Explain why you would not set a one-year cache on index.html.
