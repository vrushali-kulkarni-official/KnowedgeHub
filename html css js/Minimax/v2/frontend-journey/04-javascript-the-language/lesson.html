4.1 — How JavaScript Runs

Understand that JS is a language that needs a host, and that the browser is that host.

Python runs because you have a Python interpreter on your machine. JavaScript has no such thing by itself — it's a language that needs a host environment that gives it capabilities. The browser is one host. Node.js is another.

That's why "JavaScript" and "the DOM" are often confused. The DOM is not part of the JavaScript language — it's a set of APIs the browser host provides. The language itself is just values, functions and control flow.

Three ways to get JS into a page

<!-- 1. External file (use this) -->
<script src="app.js"></script>

<!-- 2. Inline block -->
<script>
  console.log("hi");
</script>

<!-- 3. Module (Act 4 Step 4.14) -->
<script type="module" src="app.js"></script>

Where you put the <script> tag matters (and this is not a nitpick — it's Act 7's core lesson):

  • In <head>, without defer or async: the browser pauses, downloads the script, runs it, then continues parsing the HTML. Your script can't find elements that don't exist yet.
  • At the end of <body>: HTML is already parsed, so the script can find elements. This works but blocks rendering while it downloads.
  • With defer: the browser downloads the script in parallel with the HTML, then runs it after parsing finishes. Best of both worlds. Use this.
  • With async: download in parallel, run as soon as it's ready — order is not guaranteed. Only for independent scripts.

Your first statements

console.log("Hello, world!");
console.log(42, "items", true, null, undefined);
console.log("I can do math:", 2 + 2 * 2);
  • Statements end with ;. (ASI — automatic semicolon insertion — means you can omit them, and the language guesses. Write them anyway.)
  • Whitespace doesn't matter for parsing, but use it for humans. JS uses {} for blocks, not indentation — indentation is purely for readability. You'll still indent, because humans.
  • Comments: // for one line, /* ... */ for many. Same as Python's # and """...""".
  • console.log is a browser API (part of the DevTools), not part of the language. It exists in Node too.

Python brain: console.log is print(), except it prints a live object — you can expand it and inspect it later, and it shows you the value at the time you logged it, which is a debugging superpower Python doesn't have.

What to notice

  • The browser Console is a JavaScript REPL. Type an expression and it evaluates immediately. This is your Python REPL, and it's how you learn the language fast.
  • Errors show up in the Console with a stack trace and a clickable file:line. Click it and it jumps to the source.

4.2 — Values & Variables

Learn <code>let</code>, <code>const</code>, <code>var</code> — and why one of them is basically banned.

Declaring a variable

let age = 25;          // can be reassigned
const name = "Ana";       // cannot be reassigned
var legacy = "avoid me";  // old, has bugs — don't use

Three keywords, one difference in intent, two differences in behaviour.

ScopeHoistingReassignable
varfunctionhoisted as undefinedyes
letblockhoisted, but TDZyes
constblockhoisted, but TDZno

Use const by default, let when you must reassign. This is the universal modern convention. const isn't about immutability of the value — a const array can still be pushed to. It means the binding (the name → value link) can't be pointed somewhere else.

What const actually does

const user = { name: "Ana" };
user.name = "Maria";     // FINE — the object changed
user = { name: "Maria" }; // ERROR — the binding can't be repointed

const list = [];
list.push(1);      // FINE
list = [2, 3];     // ERROR

Python brain: const is like a name you can't rebind. In Python you can always do x = 5 again; in JS, const is a promise to yourself that you won't. It also gives the runtime real optimisation opportunities, and it makes code far easier to read: when you see const, you know the reference never changes.

Why var is banned

Two classic bugs, both of which let/const fix:

// Bug 1: var is function-scoped, so the loop variable is shared
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);   // 3, 3, 3  (not 0, 1, 2!)
}
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);   // 0, 1, 2  ✅
}

// Bug 2: var is hoisted, so it silently exists before its declaration
console.log(x);   // undefined — no error!
var x = 5;

Rule: never use var. If you see it in a tutorial, it's old code.

Assignment vs declaration

Python makes you choose: x = 5 (assign) or x: int = 5 (declare with type). JavaScript has no separate declaration syntax — x = 5 just creates the variable if it doesn't exist. The keywords are what make it a declaration.

Semicolons and ASI

JS inserts semicolons for you at line breaks in most cases — but not all, and the cases where it guesses wrong are legendary. Always write semicolons. It's free.

The full lifecycle of a binding

let counter = 0;        // declaration + initialisation
counter = counter + 1;  // reassignment
counter += 1;           // compound assignment (same as Python's +=)

// const can't be reassigned:
// counter = 99;        // TypeError

What to notice

  • JavaScript has no separate "undeclared" error at runtime by default — assigning to an undeclared variable in sloppy mode creates a global. In modules and strict mode it throws a ReferenceError. Always declare your variables.
  • let a = 1, b = 2; declares two variables in one statement — but one statement per line reads better.

4.3 — Types & <code>typeof</code>

Know every type JavaScript has, and that only one of them is really dynamic.

JavaScript has seven types. You should know all of them by name even though you'll use four daily.

TypetypeofExample
number"number"42, 3.14, NaN, Infinity
string"string""hi", 'hi', `hi`
boolean"boolean"true, false
undefined"undefined"never assigned
null"object" !deliberately "nothing"
object"object"{}, [], null, functions
symbol"symbol"unique hidden key
bigint"bigint"9007199254740993n

Two legendary quirks, both of which you'll meet in interviews and in real bugs:

1. typeof null === "object". This is a 1995 implementation bug that was never fixed because changing it would break the web. The only way to check for null is x === null.

2. NaN !== NaN. NaN means "not a number", and by specification it is not equal to anything, including itself. Test with Number.isNaN(x).

There are no integers and no separate float type

Just number, which is an IEEE-754 double. 0.1 + 0.2 is 0.30000000000000004 — same problem Python has, same reason. For money, never use floats.

null vs undefined — the distinction that matters

let a;                  // undefined — never assigned
let b = null;           // null — deliberately empty

let obj = {};
obj.missing;            // undefined — the key isn't there
obj.present = null;     // null — the key IS there, and its value is empty

Python brain: undefined ≈ "this key doesn't exist" or "this function returned nothing". null ≈ None. The rule of thumb: if you set it to nothing, use null; if nothing set it, it's undefined.

JavaScript is dynamically typed, but strongly typed at runtime

Unlike Python, you don't declare types. But types still exist and are checked at runtime — so the failure mode is different, not absent.

let x = 5;
x = "hello";    // perfectly legal — the variable's type changed
x.foo();        // TypeError: x.foo is not a function  ← caught at RUNTIME, not compile time

TypeScript (which you'll meet right after this course) exists to catch that class of bug before it runs. That's the entire reason it exists.

typeof results

console.log(typeof 42);            // "number"
console.log(typeof "hi");          // "string"
console.log(typeof true);          // "boolean"
console.log(typeof undefined);     // "undefined"
console.log(typeof null);          // "object"  <- the famous bug
console.log(typeof {});            // "object"
console.log(typeof []);            // "object"  <- arrays are objects!
console.log(typeof function(){});  // "function"
console.log(typeof Symbol("x"));   // "symbol"
console.log(typeof 10n);           // "bigint"

What to notice

  • typeof on an undeclared variable returns "undefined" instead of throwing — that's a deliberate feature, used to check whether a global exists.
  • Arrays report typeof === "object". To test for an array specifically, use Array.isArray(x).

4.4 — Strings & Template Literals

Handle text properly, including the quoting rules that trip up Python programmers.

Three kinds of quotes

const a = "double quotes";
const b = 'single quotes';
const c = `backticks`;

The first two are equivalent — pick one and be consistent. The third is different: backticks are template literals, and they do two things the others can't:

const name = "Ana";
const age = 30;

// Concatenation (works, but ugly)
const msg1 = "Hello " + name + ", you are " + age;

// Template literal (interpolation)
const msg2 = `Hello ${name}, you are ${age}`;

Inside ${ } you can put any expression, including function calls and ternaries. This is the single most useful string feature in JS.

Python brain: template literals are f-strings on steroids. f"Hello {name}" ≈ `Hello ${name}`. The difference: JS interpolates automatically without the f prefix, and it works for multi-line strings too.

Multi-line strings

// Regular quotes: newlines are NOT allowed
const bad = "line one
line two";     // SyntaxError

// Backticks: newlines are fine
const good = `line one
line two`;

Python's triple-quoted strings have the same property — but JS backticks also do interpolation, so you don't need """ and f"" separately.

Useful string methods

const s = "Hello World";

s.length            // 11
s.toUpperCase()     // "HELLO WORLD"  (returns a NEW string)
s.toLowerCase()
s.indexOf("World")  // 6   (-1 if not found)
s.slice(0, 5)       // "Hello"
s.slice(-5)         // "World"   (negative = from the end)
s.replace("World", "JS")
s.split(" ")        // ["Hello", "World"]
s.trim()            // remove leading/trailing whitespace
s.includes("World") // true
s.startsWith("Hell")
s.padStart(10, "0") // "00HelloWorld"  (great for IDs / time formatting)
`s`.repeat(3)       // "sss"

Almost every string method returns a new string — strings are immutable in JavaScript, exactly like in Python. let vs const for strings: use const, since the string itself never changes; you reassign the variable instead.

Template literals with expressions

const items = 3, price = 9.99, tax = 0.18;
const total = items * price * (1 + tax);
console.log(`Total: $${total.toFixed(2)}`);   // Total: $35.37
console.log(`${items > 2 ? "many" : "few"} items`);

Careful with ${: inside a template literal, a literal ${ needs a backslash: \${. This bites when you're embedding code examples in a template string.

String methods, the ones you will actually use

const email = "  Ana.Silva@Example.COM  ";
const clean = email.trim().toLowerCase();
console.log(clean);                       // ana.silva@example.com
console.log(clean.includes("@"));         // true
console.log(clean.split("@"));             // ["ana.silva", "example.com"]

const id = "42";
console.log(id.padStart(6, "0"));          // 000042
console.log(Number(id) + 1);              // 43

What to notice

  • toFixed(2) rounds to 2 decimal places and returns a string. Number(x) converts a numeric string back to a number.
  • .length is a property (no parentheses); .trim() is a method (with parentheses). This distinction is worth internalising — you'll meet it everywhere.

4.5 — Truthiness, Coercion, <code>??</code> & <code>?.</code>

Understand how JavaScript decides if something is 'true' — and stop being surprised by it.

Falsy values

Exactly eight values are falsy. Everything else — including [], {}, "0" and "false" — is truthy.

false
0
-0
0n
NaN
""        // empty string
undefined
null

The two that bite hardest: [] and {} are truthy, because they exist. "0" is truthy, because it's a non-empty string. And 0 is falsy, so if (items.length) fails when you have zero items — but if (items) fails when you have an empty array, which is a bug waiting to happen.

if (items) { }        // wrong: [] is truthy!
if (items.length) { }  // right: 0 is falsy

Coercion

JavaScript will convert types when it needs to. Usually this is convenient ("5" * 2 === 10), and occasionally catastrophic.

"5" + 5    // "55"   <-- + prefers concatenation
"5" - 5    // 0      <-- - prefers numbers
"5" * "2"  // 10
"" + 1     // "1"
1 + null  // 1
[] + []   // ""     <-- both become ""
[] + {}   // "[object Object]"

== vs ===

Behaviour
== (loose)compares after converting types
=== (strict)compares type AND value — no conversion
1 == "1"    // true   (loose: string converted to number)
1 === "1"   // false  (strict: different types)
0 == ""     // true   (both falsy -> both become 0)
0 === ""    // false
null == undefined   // true
null === undefined  // false

Always use === and !==. The only exception most style guides allow is x == null, which is a deliberate way to check for "null or undefined" in one go.

The two modern operators

Nullish coalescing ?? — return the right side only if the left is null or undefined:

const input = "0";
input || "default"   // "default"  <-- BUG: "0" is truthy-ish but falsy? no, it's truthy...
                      // Actually "" || "default" -> "default"  (empty string is falsy)
0 || 10             // 10        (0 is falsy, so you get 10 - often NOT what you want)
0 ?? 10             // 0         (0 is not null/undefined, so it's kept)  ✅
"" ?? 10            // ""        ✅
null ?? 10          // 10        ✅

Optional chaining ?. — stop the chain if something is null or undefined:

const user = { profile: { name: "Ana" } };
user.profile.name            // "Ana"
user.address?.city           // undefined (no error - address doesn't exist)
user.address?.city ?? "N/A"  // "N/A"
user.profile.name.toUpperCase()  // "ANA"
// user.profile.nickname.length  <-- TypeError without ?.
user.profile.nickname?.length    // undefined, no error

Python brain: ?? is roughly x if x is not None else default (but it also catches "missing", which Python's get() handles too). ?. is like Python's getattr(obj, "x", None) chain, or safer navigation in other languages. Both are enormous quality-of-life improvements over Python's if obj and obj.attr chains.

What to notice

  • || returns the left value if it's truthy, else the right — it returns the value, not a boolean. That's why "" || "x" gives "x" and not true.
  • ?? only checks null/undefined. || checks all falsy values. That's the whole difference.

4.6 — Arrays

Master the workhorse data structure — and the methods that replace most of your Python loops.

JS arrays are like Python lists, with two differences: they can hold mixed types, and they're actually objects (so typeof says "object").

const nums = [1, 2, 3];
const mixed = [1, "two", true, null, { a: 1 }];   // allowed (but usually a bad idea)

nums[0]        // 1
nums.length    // 3
nums.at(-1)    // 3  (modern; Python's negative indexing)
nums.push(4)   // add to end, returns new length
nums.pop()     // remove from end, returns the element
nums.shift()   // remove from front
nums.unshift(0)// add to front
nums.includes(2)
nums.indexOf(9)  // -1 if not found
nums.slice(1)    // new array (doesn't mutate!)
nums.reverse()   // MUTATES
nums.sort()      // MUTATES

The one rule to memorise: methods that mutate vs methods that return a new array. push, pop, splice, sort, reverse mutate. map, filter, slice, concat, flat don't. This is exactly like Python, where .sort() and .append() mutate but sorted() and slicing don't.

The iteration methods — this is where JS earns its keep

const nums = [1, 2, 3, 4, 5];

nums.forEach(n => console.log(n));            // just iterate (no return)
nums.map(n => n * 2);                         // [2,4,6,8,10]  new array
nums.filter(n => n > 2);                    // [3,4,5]        new array
nums.find(n => n > 3);                      // 4             first match
nums.findIndex(n => n > 3);                  // 3             index of first match
nums.some(n => n > 4);                      // true          at least one
nums.every(n => n > 0);                     // true          all of them
nums.reduce((sum, n) => sum + n, 0);          // 15            one value
nums.includes(3);
MethodReturnsPython equivalent
mapnew array, same length[f(x) for x in xs]
filternew array, subset[x for x in xs if p(x)]
findfirst matching elementnext(x for x in xs if p(x))
some / everybooleanany / all
reduceone accumulated valuefunctools.reduce
forEachundefinedfor x in xs: f(x)

reduce deserves a moment

const total = nums.reduce((sum, n) => sum + n, 0);
//              ^ accumulator   ^ current value
//                                ^ initial value (required for numbers!)

Without the initial value, reduce uses the first element as the accumulator — which is why reduce on an empty array without an initial value throws, and why reduce with + on strings surprises people. Always pass the initial value.

Chaining

const result = users
  .filter(u => u.active)
  .map(u => u.name.toUpperCase())
  .sort()
  .slice(0, 5);

This chain is the most common JavaScript pattern in existence, and you'll write it in every project.

The pipeline pattern

const users = [
  { name: "ana",   active: true,  score: 82 },
  { name: "bruno", active: false, score: 91 },
  { name: "carla", active: true,  score: 97 },
];

const top = users
  .filter(u =&gt; u.active)
  .map(u =&gt; u.name)
  .sort();

console.log(top);                                  // ["ana", "carla"]
console.log(users.reduce((s, u) =&gt; s + u.score, 0));

What to notice

  • Arrow functions get a shorthand: n => n * 2. If the body is a single expression, the return is implied. If it's a block, you need an explicit return.
  • for...of iterates values (like Python's for x in list), while for...in iterates keys/indices (like iterating a dict).

4.7 — Objects

Understand JS objects as dictionaries, and the reference semantics that surprise everyone.

A JS object is roughly a Python dict — but it's also the foundation of the whole language. Functions, arrays and dates are all objects.

const user = {
  name: "Ana",
  age: 30,
  isActive: true,
  greet() { return `Hi, ${this.name}`; },   // method shorthand
  "weird key": 1,
};

Accessing

user.name          // dot notation
user["name"]        // bracket notation
user["weird key"]   // required for keys with spaces/special chars
user.missing        // undefined (not an error!)
user.missing?.deep  // undefined

Reading a missing property is never an error in JS — it gives undefined. That's a big deal: it means "does this key exist?" is "name" in user or user.name !== undefined.

Built-in object methods

Object.keys(user)      // ["name", "age", ...]
Object.values(user)    // ["Ana", 30, ...]
Object.entries(user)   // [["name","Ana"], ["age",30], ...]

user.hasOwnProperty("name")   // true (older style)
Object.hasOwn(user, "name")   // true (modern)
"name" in user                // true (also checks the prototype chain!)

Python brain: Object.keys(d) ≈ d.keys(), Object.values(d) ≈ d.values(), Object.entries(d) ≈ d.items(). And user.get("name") in Python ≈ user.name in JS (both give None/undefined for a missing key) — except JS doesn't have get, you just use the dot.

Reference semantics — the thing that bites

const a = { x: 1 };
const b = a;         // b points to the SAME object
b.x = 2;
console.log(a.x);    // 2  <-- a changed too!

const c = { x: 1 };
const d = { ...c };  // shallow copy
d.x = 2;
console.log(c.x);    // 1  <-- independent

Objects are passed by reference (technically: the reference is passed by value, which is the same practical thing). When you pass an object to a function and the function mutates it, the caller sees the change.

Shallow copy means shallow. { ...obj } copies the top level only. If obj.nested is an object, both copies point to the same nested object. For a deep copy you need structuredClone(obj) (modern) or JSON.parse(JSON.stringify(obj)) (loses Dates, Maps, functions).

Freezing

const config = Object.freeze({ mode: "dark" });
config.mode = "light";   // silently fails (or throws in strict mode)

Arrays are objects

const arr = [1, 2, 3];
arr.length          // 3
arr[0]              // 1
arr.map(x => x * 2)
Object.keys(arr)    // ["0", "1", "2"]  <- string keys!

Object essentials

const user = { name: "Ana", age: 30, tags: ["a", "b"] };

console.log(Object.keys(user));
console.log(Object.entries(user));
console.log("name" in user);
console.log(user.missing);                 // undefined, no error

const copy = { ...user };                  // shallow
copy.name = "Bruno";

const deep = structuredClone(user);
deep.tags.push("c");

  • The in operator checks the prototype chain too. "toString" in user is true! Use Object.hasOwn(user, "toString") for a strict own-property check.
  • delete obj.key removes a property. You can't delete a variable declared with const.

4.8 — Destructuring, Spread & Rest

Learn the three ES6 features you will use in literally every modern file.

Destructuring — pull apart objects and arrays

const user = { name: "Ana", age: 30, city: "Lisbon" };

// Object destructuring
const { name, age } = user;
const { name: userName } = user;          // rename
const { name = "Anonymous" } = {};        // default
const { address: { street } = {} } = user; // nested, with a safe default

// Array destructuring
const [first, second, ...rest] = [10, 20, 30, 40];
// first=10, second=20, rest=[30,40]

Note the last one: destructuring a property of undefined throws (TypeError: Cannot destructure property 'x' of undefined). That's why the = {} default is so common — and why const { data } = response is safer as const { data } = response ?? {}.

Rest vs spread — same ..., opposite meaning

WhereMeaning
Spreadproducing a value: ...rightexpand an array/object into elements
Restcollecting: ...leftgather the remaining items into an array/object
// Spread: expand
const a = [1, 2];
const b = [...a, 3, 4];            // [1,2,3,4]
const merged = { ...obj1, ...obj2 };

// Rest: collect
function sum(...nums) { return nums.reduce((a, b) => a + b, 0); }
sum(1, 2, 3);                       // 6
const { password, ...safeUser } = user;   // omit a key

The ...rest pattern for omitting keys is a security primitive, not just a convenience. When you send a user object to the client, spreading it and dropping password is how you avoid leaking it. You will see this pattern everywhere in real code.

Optional chaining and nullish coalescing, together

const city = user?.address?.city ?? "Unknown";
const items = cart?.items?.length ?? 0;

Read it as: "go as deep as safely possible, then fall back." This pattern replaces almost every defensive if (x && x.y && x.y.z) chain in Python codebases.

Python brain: destructuring is Python's tuple unpacking (a, b = pair), but for dicts too, and with a JS-only shorthand ({name} = obj is shorthand for {name: name} = obj). Rest and spread are Python's *args/**kwargs and [*a, *b]/{**a, **b} — same idea, different syntax.

The three features in one example

const user = { name: "Ana", age: 30, address: { city: "Lisbon" } };

const { name, age } = user;
const { name: alias, age = 18 } = user;
console.log(name, alias, age);

const [first, ...others] = [1, 2, 3, 4];
console.log(first, others);

const merged = { ...user, active: true };
console.log(merged.active);

const { address, ...withoutAddress } = user;
console.log("still has address?", "address" in withoutAddress);

What to notice

  • Destructuring declarations need the const/let keyword: const { name } = user; — not { name } = user; (that's a syntax error; you need parentheses in a different context).
  • The = {} default in destructuring only applies when the value is undefined — not for null. const { a } = null still throws.

4.9 — Functions

Write functions in all three JS forms and know exactly when to use each.

Three forms

// 1. Declaration — hoisted, can be called before its definition
function add(a, b) {
  return a + b;
}

// 2. Expression — assigned to a variable, NOT hoisted
const add = function (a, b) {
  return a + b;
};

// 3. Arrow — expression or block body, NOT hoisted
const add = (a, b) => {
  return a + b;
};
const add = (a, b) => a + b;   // implicit return

Python brain: form 1 is def. Forms 2 and 3 are add = lambda a, b: a + b — but the arrow version can take a block body with multiple statements, which Python's lambda can't. So the arrow function is more like a small def than a lambda.

Parameters

function greet(name = "friend", greeting = "Hello") {
  return `${greeting}, ${name}!`;
}

function sum(...numbers) {          // rest parameter
  return numbers.reduce((a, b) => a + b, 0);
}

function logAll(label, ...items) {  // rest must be LAST
  console.log(label, items);
}

Arrow functions vs regular functions — the one real difference

Both are functions. But arrow functions have no own this — they inherit it from the surrounding scope. Regular functions get this from how they're called.

const obj = {
  name: "Ana",
  regular: function () { return this.name; },   // "Ana"  (this = obj)
  arrow: () => this.name,                     // undefined (this = module scope)
  method() { return this.name; },               // "Ana"  (shorthand = regular)
};

Practical rule:

  • Use an arrow function for callbacks (map, filter, event handlers) and for short function bodies. It's also impossible to accidentally break this, which is why it's the community default.
  • Use a regular function (or method shorthand) when you need this to refer to the object the method was called on — object methods, constructors, and anything using arguments.

Also: arrow functions can't be used as constructors (new) and have no prototype. Details you'll meet in Act 4 Step 4.16.

IIFE — Immediately Invoked Function Expression

(function () {
  const privateData = "nobody else can see this";
  console.log(privateData);
})();

Historically used to create a private scope. Still used for UMD modules and "module pattern". Arrow version: (() => { ... })();

Arguments vs rest

Regular functions have an arguments object (array-like, not a real array). Arrow functions don't. If you want a real array in a regular function, use rest parameters instead.

The same function, three ways

function addDecl(a, b) { return a + b; }
const addExpr = function (a, b) { return a + b; };
const addArrow = (a, b) => a + b;

console.log(addDecl(1, 2), addExpr(3, 4), addArrow(5, 6));

const obj = {
  name: "Ana",
  regular() { return this.name; },
  arrow: () => (typeof this === "undefined" ? "no this" : "module this"),
};
console.log(obj.regular());
console.log(obj.arrow());

What to notice

  • A function without an explicit return returns undefined — not null, not an empty object.
  • Arrow functions have no arguments, no prototype, and can't be new'd. They're not a drop-in replacement for regular functions in every position.

4.10 — Scope, Hoisting & Closures

Understand where variables live, and why a function can remember them forever.

Three kinds of scope

  • Global — everything outside any function.
  • Function — created by a function body. var lives here.
  • Block — created by {} (if, for, a bare block). let and const live here.

Lexical scoping: an inner scope can read outer variables, but not vice versa.

const outer = "global";

function demo() {
  const inner = "function scope";
  console.log(inner);   // ✅
  if (true) {
    const block = "block scope";
    console.log(block); // ✅
    console.log(inner); // ✅ — inner is visible from the block
  }
  console.log(block);    // ❌ ReferenceError
}
console.log(inner);      // ❌ ReferenceError

Hoisting and the temporal dead zone

Both var and let/const are "hoisted" — the declaration is moved to the top of its scope. But:

Before the declaration
var x = 1x is undefined (no error)
let x = 1ReferenceError — the TDZ

The "temporal dead zone" is the window between entering the scope and the declaration. It exists so that let behaves predictably instead of silently giving you undefined.

Python brain: Python resolves names at call time, so a function body can reference a variable defined later at module level, as long as it exists by the time the function is called. JS resolves names too, but the TDZ turns "use-before-declaration" into an error rather than undefined. Same underlying idea, stricter contract.

Closures — the idea that makes JavaScript powerful

A closure is a function that remembers the variables from the scope where it was created, even after that scope has finished executing.

function makeCounter() {
  let count = 0;                 // lives in the closure
  return function increment() {
    count += 1;
    return count;
  };
}

const counter = makeCounter();
counter();   // 1
counter();   // 2
counter();   // 3

const other = makeCounter();    // a completely separate count
other();     // 1

Each call to makeCounter() creates a fresh count. That's the whole point — counter and other don't share anything. This is how you create private state in JavaScript, and it's the foundation of: module patterns, function factories, event handlers, React hooks, and every debounce implementation you'll ever write.

Python has closures too, so you already have the intuition:

# Python
def make_counter():
    count = 0
    def increment():
        nonlocal count
        count += 1
        return count
    return increment

Same idea. JavaScript's version is more often used with arrow functions and is usually written on one line.

A closure creating private state

function makeCounter() {
  let count = 0;
  return () => {
    count += 1;
    return count;
  };
}

const counter = makeCounter();
const other = makeCounter();
console.log(counter(), counter(), counter());  // 1 2 3
console.log(other());                          // 1 - separate state

What to notice

  • The classic loop-closure bug: for (let i = 0; i < 3; i++) setTimeout(() => console.log(i)) prints 0, 1, 2 — because let creates a new binding per iteration. With var it prints 3, 3, 3. This is a per-iteration binding, which is one of the best parts of let.
  • Closures keep their outer variables alive in memory. That's useful (memoization) and it's also how you accidentally create a memory leak (a listener that can never be removed).

Stuck? Open the hints
  • The bank is one closure variable plus a returned object of functions. The functions can all see the same balance.
  • The unique-id generator is the same pattern: let id = 0; return () => ++id; — and two calls to the factory create two independent counters.

4.11 — Control Flow & Loops

Cover the syntax differences from Python, plus the loop methods that avoid most manual loops.

Conditionals — nearly identical to Python

if (x > 0) {
  console.log("positive");
} else if (x === 0) {
  console.log("zero");
} else {
  console.log("negative");
}

const label = x > 0 ? "positive" : "not positive";   // ternary

The differences: JS uses === not == (see Step 4.5), and the ternary is condition ? a : b (same as Python). JS has no elif — it's else if.

switch

switch (action) {
  case "add":
    addItem();
    break;                      // without break, it FALLS THROUGH
  case "remove":
    removeItem();
    break;
  default:
    console.log("unknown action");
}

break is optional in Python but mandatory in JS (fall-through is a feature there). The last case often doesn't need one.

Loops

// classic for
for (let i = 0; i < 5; i++) { console.log(i); }

// for...of — iterates VALUES (like Python's for x in list)
for (const item of items) { console.log(item); }

// for...in — iterates KEYS (like iterating a dict)
for (const key in obj) { console.log(key, obj[key]); }

// while / do...while
let n = 0;
while (n < 3) { n++; }
do { n--; } while (n > 0);

Python brain: for (const item of items) is Python's for item in items. for (const key in obj) is Python's for key in obj.keys() — and it's the JS equivalent of iterating a dict. Note that for...in also walks the prototype chain, so Object.keys(obj) is usually safer.

Breaking out

outer:
for (let i = 0; i < 3; i++) {
  for (let j = 0; j < 3; j++) {
    if (j === 1) continue outer;   // labelled continue
    if (i === 2) break outer;       // labelled break
  }
}

JS has labels — Python doesn't. They let you break out of nested loops. Rarely needed, but good to know.

Prefer the array methods

Most for loops in modern JS exist to build a new array. Use map/filter/forEach instead:

// imperative
const names = [];
for (const u of users) {
  if (u.active) names.push(u.name);
}

// declarative
const names = users.filter(u => u.active).map(u => u.name);

Use for...of when you need the index, need to break out, or are iterating something that isn't an array (a string, a Map, a generator). Use forEach when you just want to run something for each item. Use map/filter when you want a new array.

What to notice

  • There's no ++ on a string in a meaningful sense, and no += on numbers with a string — "a" + 1 is "a1".
  • for...of works on anything iterable: arrays, strings, Map, Set, generators. for...in works on any object (keys as strings).

4.12 — The DOM

Read and change any page from JavaScript — the core skill of the whole front end.

The DOM is the browser's live object tree. JavaScript's job on the web is almost always: find elements, read from them, change them, and react to events.

Finding elements

document.getElementById("email")        // one element by id  (fastest)
document.querySelector(".card")          // FIRST match of any CSS selector
document.querySelectorAll(".card")       // ALL matches -> NodeList
document.querySelector("form input[type=email]")
document.querySelector("[data-count]")

querySelector and querySelectorAll take any CSS selector — everything from Act 2 applies. This is the single most important connection between your CSS knowledge and your JavaScript knowledge.

Python brain: document.querySelectorAll(".card") is like a database query — it returns a live list of matching nodes. And querySelector returning null (not undefined) is a JS quirk worth knowing: el.querySelector(...).textContent throws if nothing matched, but el.querySelector(...)?.textContent doesn't.

Reading and writing

const el = document.querySelector("#name");

el.textContent            // READ: the text, as plain text
el.textContent = "New"    // WRITE: replaces all children with a text node

el.innerHTML             // READ/WRITE: raw HTML string  ⚠️
el.value                 // READ: the value of an input
el.classList.add("active")
el.classList.toggle("active")
el.setAttribute("data-x", "1")
el.getAttribute("data-x")
el.disabled = true
el.href = "/new"

textContent vs innerHTML is the most important security decision in front-end development.

textContent inserts text — the browser escapes it, so <b> shows up as literal text. innerHTML parses and executes the string as HTML.

el.textContent = userInput;              // ✅ safe
el.innerHTML = userInput;                // ❌ XSS vulnerability

el.textContent = "<b>Hi</b>";      // shows: <b>Hi</b>
el.innerHTML = "<b>Hi</b>";          // shows: Hi (bold)

Rule: use innerHTML only with strings you wrote yourself. For anything from a user or an API, use textContent. Act 8 Step 8.4 is entirely about this.

Creating and removing

const li = document.createElement("li");
li.textContent = "New item";
li.className = "list-item";
list.appendChild(li);

li.remove();                        // modern
list.replaceChild(newLi, oldLi);

The render pattern you'll use forever

function render(items) {
  const list = document.querySelector("#list");
  list.textContent = "";                 // clear
  for (const item of items) {
    const li = document.createElement("li");
    li.textContent = item.name;
    list.appendChild(li);
  }
}

Clear-then-rebuild is simple and correct. (It's also what React automates for you — remember this pattern when you get there.)

Find, read, write

const box = document.querySelector("#demo-box");
console.log("textContent:", box.textContent);
console.log("innerHTML  :", box.innerHTML);
box.textContent = "Replaced with plain text";
console.log("after:", box.textContent);

What to notice

  • textContent reads the text of an element and all its descendants; innerHTML reads the markup. For an input, you want .value, not .textContent.
  • querySelectorAll returns a NodeList, not an Array — it has forEach but not map. Use [...nodeList].map(...) or Array.from(nodeList) if you need array methods.

4.13 — Events

Make the page respond — and understand bubbling, which explains 80% of event bugs.

const btn = document.querySelector("#save");

btn.addEventListener("click", function (event) {
  console.log("clicked!", event.type);
});

// Arrow version (preferred)
btn.addEventListener("click", (event) => {
  console.log("clicked!", event.target);
});

Common event types

EventFires when
clickan element is clicked
inputthe value of an input changes (every keystroke)
changethe value is committed (blur for text, immediately for checkboxes)
submita form is submitted
keydown / keyupa key is pressed / released
focus / bluran element gains / loses focus
scrollthe page or a container scrolls
mouseenter / mouseleavethe pointer enters / leaves (doesn't bubble)

The event object

btn.addEventListener("click", (event) => {
  event.target        // the element that was clicked
  event.currentTarget // the element the listener is attached to
  event.type          // "click"
  event.key           // for keyboard events: "Enter", "a", "Escape"
  event.preventDefault()   // stop the default browser behaviour
  event.stopPropagation()  // stop the event bubbling further up
});

Bubbling — the mental model that matters

When an event fires on an element, it doesn't stop there. It bubbles up through every ancestor, and each ancestor's listener for that event type fires too.

<div id="outer">
  <button id="inner">Click me</button>
</div>

Clicking the button fires: button's listener → div's listener → body's listener → document's listener → window's. That's bubbling.

Event delegation is the payoff: instead of attaching a listener to 100 list items, attach ONE to the parent and check what was clicked.

list.addEventListener("click", (event) => {
  const item = event.target.closest("li");
  if (!item) return;                 // clicked the list, not an item
  console.log("clicked item:", item.textContent);
});

This is how every framework handles events, and it means you can add items to a list later and they just work.

Preventing default behaviour

form.addEventListener("submit", (event) => {
  event.preventDefault();     // stop the browser navigating/reloading
  // now handle it with fetch() instead
});

This is how every modern form works: intercept the submit, do a fetch(), and never reload the page.

Python brain: the DOM event system is a publish-subscribe system. addEventListener ≈ subscribing to a topic; event.target ≈ the message payload; bubbling ≈ the message being relayed up the tree. You already know the pattern from any pub/sub library.

Bubbling and delegation

const outer = document.querySelector("#demo-outer");
const inner = document.querySelector("#demo-inner");

inner.addEventListener("click", () => console.log("1. button listener"));
outer.addEventListener("click", () => console.log("2. parent listener (bubbled)"));
document.addEventListener("click", () => console.log("3. document listener (bubbled)"));

inner.addEventListener("click", (e) => {
  e.stopPropagation();
  console.log("stopPropagation called - 2 and 3 will NOT run");
});

What to notice

  • event.target is the deepest element clicked; event.currentTarget is the element with the listener. They differ when an event bubbles — use currentTarget inside the handler.
  • Use event.preventDefault() on submit, on click on links you handle yourself, and on checkbox/radio clicks you want to intercept.
  • keydown fires for every key; check event.key === "Enter" rather than assuming.

4.14 — Modules & npm

Split code into files, import what you need, and understand what npm actually is.

ES modules

// math.js
export function add(a, b) { return a + b; }
export const PI = 3.14159;
export default class Calculator { }

// app.js
import Calculator, { add, PI } from "./math.js";
import * as math from "./math.js";
  • export — make things available to other files.
  • export default — one per file, imported without braces.
  • import { x, y } from "./file.js" — named imports.
  • import x from "./file.js" — default import.
  • import * as everything from "./file.js" — namespace import.

Modules require a server. If you open an index.html via file://, import fails with a CORS error. You need some HTTP server. Options:

  • VS Code's Live Server extension (right-click → Open with Live Server) — easiest, zero setup.
  • npx serve . in the terminal.
  • Python's built-in: python3 -m http.server 8000 then open http://localhost:8000.

This is the moment to switch from "double-click the file" to "serve the folder". Get used to it now — the React part of the course requires it.

What npm actually is

npm is three things:

  1. A package registry — a massive public database of code packages.
  2. A package manager — npm install downloads them.
  3. A tool runner — npm run build runs scripts from package.json.
npm init -y           # create package.json
npm install lodash  # add a dependency
npm install -D vite # add a dev dependency
npm run dev         # run the "dev" script

Key idea: node_modules is a folder of downloaded code you never edit. package.json lists what you depend on. package-lock.json records the exact versions so everyone gets the same tree.

Python brain: npm ≈ pip + venv + requirements.txt, and package.json ≈ pyproject.toml. The big difference: in Python you import by module name and the import happens at runtime; in JS bundlers statically analyse your imports and bundle only what you actually use. That static analysis is why import paths must be literal strings — the same rule you hit with Tailwind's class names.

Module scripts are strict mode

<script type="module"> code is always strict mode, has its own scope, and is deferred by default (like defer). That means:

  • No accidental globals.
  • this at the top level is undefined, not window.
  • You must use the full file path with the extension: "./math.js".

Two files, one page

&lt;!-- index.html --&gt;
&lt;script type="module" src="./app.js"&gt;&lt;/script&gt;

&lt;!-- app.js --&gt;
import { greet } from "./greet.js";
console.log(greet("Ana"));

What to notice

  • The extension is required in the import path: "./math.js", not "./math". Node.js also requires the extension.
  • Named exports are better for utilities; default exports are better for a file's main thing. Both can coexist in one file.

4.15 — Errors: try / catch / throw

Handle failure properly — and stop letting one bad response kill your whole app.

Three keywords

try {
  riskyThing();
} catch (error) {
  console.error("Something went wrong:", error.message);
} finally {
  cleanup();          // always runs, even after an error
}

You can also throw your own errors:

if (age < 0) {
  throw new RangeError("Age cannot be negative");
}

Built-in error types

TypeWhen
Errorthe generic one
TypeErrorwrong type or undefined property
RangeErrorvalue out of range
ReferenceErrorvariable doesn't exist / TDZ
SyntaxErrorthe code can't be parsed

JS has no except clause like Python — you check the error's name or instanceof instead:

try {
  JSON.parse(badJson);
} catch (error) {
  if (error instanceof SyntaxError) {
    // handle parse failure
  } else {
    throw error;      // re-throw anything you didn't expect
  }
}

Custom error classes

class ApiError extends Error {
  constructor(message, status) {
    super(message);              // must call super() before using `this`
    this.name = "ApiError";
    this.status = status;
  }
}

try {
  throw new ApiError("Not found", 404);
} catch (error) {
  console.log(error.name, error.status, error.message);
}

The most important error-handling pattern in the front end

async function loadUser(id) {
  try {
    const response = await fetch(`/api/users/${id}`);
    if (!response.ok) {                 // fetch does NOT throw on 404 or 500!
      throw new Error(`HTTP ${response.status}`);
    }
    return await response.json();
  } catch (error) {
    console.error("Could not load user:", error.message);
    return null;                        // or re-throw, or show a UI error
  }
}

The single most common async bug in JavaScript: fetch() only rejects on network failure. An HTTP 404 or 500 is a successful fetch — response.ok is false, but nothing throws. If you don't check response.ok, you'll try to parse an error page as JSON and get a confusing "Unexpected token < in JSON" error.

Always check response.ok.

Python brain: try/catch/finally is exactly Python's try/except/finally — but JS has no except SomeError: syntax, so you check error.name or error instanceof. And Python's raise is JS's throw.

try / catch / finally in action

function risky(shouldFail) {
  if (shouldFail) throw new TypeError("simulated failure");
  return "ok";
}

try {
  console.log(risky(false));
  console.log(risky(true));
} catch (error) {
  console.log("caught:", error.name, "-", error.message);
} finally {
  console.log("finally always runs");
}

class AppError extends Error {
  constructor(message, code) {
    super(message);
    this.name = "AppError";
    this.code = code;
  }
}
try {
  throw new AppError("Something specific broke", "E42");
} catch (error) {
  console.log(error.name, error.code, error.message);
}

What to notice

  • error.message is the human-readable string; error.name is the type; error.stack is the full trace with file and line.
  • In a catch block, if you don't handle a case, re-throw it. Swallowing every error is how bugs become invisible.

4.16 — Classes, Prototypes & <code>this</code>

Understand the object model underneath JavaScript's class syntax.

JavaScript's object model is prototype-based. Every object has a hidden link to another object (its prototype), from which it inherits properties.

const animal = {
  speaks: true,
  speak() { return "..."; },
};

const dog = Object.create(animal);   // dog inherits from animal
dog.bark = function () { return "Woof"; };

dog.speak();   // works - inherited
dog.bark();    // works - own

Classes are syntax over prototypes

class Animal {
  constructor(name) {
    this.name = name;          // this = the new object
  }
  speak() {
    return `${this.name} makes a sound`;
  }
}

class Dog extends Animal {
  constructor(name, breed) {
    super(name);               // MUST call super() before using `this`
    this.breed = breed;
  }
  speak() {
    return super.speak() + " (woof)";
  }
}

const rex = new Dog("Rex", "Collie");
rex.speak();

Python brain: this is the biggest conceptual difference between the two languages, and it runs in the opposite direction from Python:

  • Python: the class owns the behaviour, and instances have a __dict__. Dog and Animal are separate objects with a class hierarchy.
  • JavaScript: the instance owns the behaviour via its prototype chain. rex doesn't "contain" Dog.prototype; it points to it. class is a convenient way to write that chain.

Python's self is explicitly the first argument. JavaScript's this is implicit and determined at call time — that's the next section.

How this is determined

In order of priority:

  1. Explicit: fn.call(obj), fn.apply(obj), fn.bind(obj) — you set it yourself.
  2. As a method: obj.fn() — this is obj.
  3. As a constructor: new Fn() — this is the freshly created object.
  4. Plain call: fn() — this is undefined in strict mode (or the global object in sloppy mode).
function say() { return this?.name; }

const obj = { name: "Ana", say };
obj.say();        // "Ana"     (method call)
const detached = obj.say;
detached();       // undefined  (plain call - this is lost)
obj.say.call({ name: "Bruno" });  // "Bruno"  (explicit)

Why arrow functions exist: an arrow function has no this of its own — it inherits the this of the scope where it was defined. That makes it immune to the "detached method" problem above, which is why callbacks are almost always arrows.

Extending built-ins

class MyError extends Error {
  constructor(msg, code) {
    super(msg);
    this.name = "MyError";
    this.code = code;
  }
}
console.log(new MyError("x", 1) instanceof Error);   // true

Extending Array or String is possible but usually a bad idea — it breaks assumptions everywhere. Extend your own classes instead.

this, four ways

function say() { return this && this.name; }

const obj = { name: "Ana", say };
console.log("method call :", obj.say());

const detached = obj.say;
console.log("plain call  :", detached());

console.log("call()      :", obj.say.call({ name: "Bruno" }));
console.log("bind()      :", obj.say.bind({ name: "Carla" })());

function Point(x, y) { this.x = x; this.y = y; }
console.log("new         :", new Point(1, 2));

class Animal {
  constructor(name) { this.name = name; }
  speak() { return `${this.name} makes a sound`; }
}
class Dog extends Animal {
  constructor(name, breed) { super(name); this.breed = breed; }
  speak() { return super.speak() + " (woof)"; }
}
console.log("class       :", new Dog("Rex", "Collie").speak());
console.log("instanceof  :", new Dog("Rex") instanceof Animal);

What to notice

  • In a class method, this is the instance. In a static method, this is the class itself.
  • Object.create(animal) creates an object inheriting from animal without calling any constructor — the raw prototype mechanism underneath class.
  • Methods defined in a class body are non-enumerable, which is why Object.keys(instance) doesn't include them.

4.17 — The Event Loop

Predict the exact order your code runs in — the skill that separates fluent JavaScript developers from confused ones.

JavaScript is single-threaded: one call stack, one thing running at a time. The event loop is what lets it wait for slow things (network, timers) without freezing.

The three parts

  • Call stack — the functions currently executing. LIFO.
  • Web APIs — browser-provided async machinery (setTimeout, fetch, event listeners). They run outside JavaScript and schedule a callback when done.
  • Queues — where callbacks wait. There are two, and the difference is the whole story.

The rule

  1. Run the current task until the call stack is empty.
  2. Take all the microtasks (and keep going until the microtask queue is empty).
  3. Take one macrotask.
  4. Render (if needed).
  5. Go to 1.
Microtasks (high priority)Macrotasks (low priority)
Promise.then() / .catch()setTimeout
queueMicrotask()setInterval
MutationObserver callbacksuser events (click, scroll)
await continuationsI/O callbacks

Python brain: JavaScript's event loop is like Python's asyncio event loop, with one important difference. In asyncio, awaiting yields control and other tasks run. In JS, awaiting also yields to the microtask queue — and microtasks always run before the next macrotask, no matter how many are queued.

The classic prediction exercise

console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => console.log("3"));

console.log("4");

// Output: 1, 4, 3, 2

Why: 1 and 4 are synchronous (they run immediately, in order). Then the stack empties, so the microtask 3 runs before the macrotask 2 — even though the timeout was scheduled first.

async function main() {
  console.log("A");
  await null;                    // even awaiting null yields!
  console.log("B");
}
main();
console.log("C");
setTimeout(() => console.log("D"), 0);
Promise.resolve().then(() => console.log("E"));

// Output: A, C, B, E, D

await always resumes in a microtask, never synchronously. That's why B comes after C.

Blocking

Because there's one thread, a long synchronous loop freezes the page — no clicks, no scrolling, no rendering. That's why Act 6 has Web Workers.

The practical takeaway: never write a long synchronous loop over thousands of items on the main thread. Chunk it, or move it to a Web Worker. And remember that await yields to the event loop, so code after an await runs later than code after it looks.

Predict, then run

console.log("1 - sync");
setTimeout(() => console.log("5 - macrotask (timeout)"), 0);
Promise.resolve().then(() => console.log("4 - microtask (promise)"));
console.log("2 - sync");

(async () => {
  console.log("3 - async body starts sync");
  await null;
  console.log("6 - after await (microtask)");
})();

console.log("Expected order: 1, 2, 3, 4, 5, 6");

What to notice

  • A setTimeout(fn, 0) is not "immediate" — it's "as soon as possible after the current task and all microtasks". The delay is a minimum, not a guarantee.
  • await on a non-promise value still yields — it waits one microtask tick. That's why await null changes the ordering.
