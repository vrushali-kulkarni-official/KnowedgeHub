6.1 — Promises & async/await

Understand asynchronous execution as a value you can wait on.

A Promise is a value that isn't ready yet. Python's closest relative is asyncio.Future.

const p = new Promise((resolve, reject) => {
  setTimeout(() => resolve("done"), 1000);
});

p.then(value => console.log(value));     // "done" (later)
p.catch(err => console.error(err));
p.finally(() => console.log("always"));

The three states

  • pending — still working
  • fulfilled — succeeded, with a value
  • rejected — failed, with a reason

Once a promise settles, it never changes. That's why a promise is safe to await multiple times.

async/await

async function getUser(id) {
  const response = await fetch(`/api/users/${id}`);
  const user = await response.json();
  return user;
}

async makes a function always return a promise. await pauses that function until a promise settles, and resumes it in a microtask (Act 4 Step 4.17).

Python brain: async def / await is almost a perfect match. The differences:

  • Python's await yields to the event loop. JavaScript's await also yields — but to the microtask queue, which runs before the next macrotask.
  • In Python, asyncio.gather runs coroutines concurrently. In JS, Promise.all does the same thing.
  • JS has no asyncio.run() — the browser (or Node) owns the loop.

Error handling

try {
  const data = await fetch(url).then(r => r.json());
} catch (error) {
  // network error OR the .then threw
}

Unlike Python's except, a JS try/catch around an await catches both network rejections and errors thrown by the code after the await. One try covers the whole async body.

Sequential vs parallel

// SEQUENTIAL - slow, 2 seconds total
const a = await fetch("/a");
const b = await fetch("/b");

// PARALLEL - fast, ~1 second total
const [a, b] = await Promise.all([fetch("/a"), fetch("/b")]);

This is the single most important async performance rule. Start all your requests first, then await them together.

The classic bug:

// WRONG - waits for a before even starting b
const a = await fetch("/a");
const b = await fetch("/b");

// RIGHT - both start immediately
const [a, b] = await Promise.all([fetch("/a"), fetch("/b")]);

Other useful combinators

MethodResolves when
Promise.allall resolve (rejects if any rejects)
Promise.allSettledall settle — never rejects, gives you each result's status
Promise.racethe first one settles
Promise.anythe first one fulfills (rejects only if all reject)

What to notice

  • An unhandled promise rejection shows up in the console but doesn't stop your code. In Node it can crash the process. Always attach a .catch or use try/catch.
  • Promise.all with an empty array resolves immediately with []. Useful for the "if the list is empty, skip the request" case.

6.2 — Fetch & Rendering Data

Pull data from an API and render it — the shape of almost every real app.

The fetch pipeline

async function load() {
  const response = await fetch("/api/items");
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const data = await response.json();
  return data;
}

Three distinct steps, three distinct failure modes:

  1. fetch() rejects only on network failure (no connection, DNS failure, CORS block).
  2. A 404 or 500 resolves normally — you must check response.ok yourself.
  3. response.json() can throw if the body isn't valid JSON.

Check response.ok. Every time. Skipping it is the number-one cause of "Unexpected token < in JSON at position 0" errors, which is actually the browser's HTML error page failing to parse as JSON.

JSON

const obj = JSON.parse('{"a":1}');   // string -> object  (like Python json.loads)
const str = JSON.stringify({ a: 1 });  // object -> string  (like Python json.dumps)

The render loop

function render(items) {
  const list = document.querySelector("#list");
  list.textContent = "";                 // clear
  for (const item of items) {
    const li = document.createElement("li");
    li.textContent = item.name;          // textContent, not innerHTML
    list.appendChild(li);
  }
}

Always textContent for data. The moment you use innerHTML with data from an API, you have an XSS vulnerability (Act 8 Step 8.4). The only reason to use innerHTML is markup you wrote yourself.

Loading, empty, and error states

Real UI has three states, and beginners forget two of them:

async function load() {
  showLoading();
  try {
    const items = await loadItems();
    if (items.length === 0) showEmpty();
    else render(items);
  } catch (error) {
    showError(error.message);
  } finally {
    hideLoading();
  }
}

Every real app needs all three. Designing them is a design decision, not an afterthought.

Using a public API right now

const res = await fetch("https://jsonplaceholder.typicode.com/posts?_limit=5");
const posts = await res.json();
console.log(posts.map(p => p.title));

What to notice

  • response.json(), response.text() and response.blob() can each be called only once — the body is a stream. Read it once.
  • CORS (Act 8 Step 8.3) is why some APIs work from a page and others don't. The error is in the Console, not in your code.

  3. an error state with a Retry button

Then: add a search box that filters the already-loaded list (don't re-fetch on every keystroke — filter the data you have).

Finally, simulate a failure by pointing the URL at a bad host and confirm your error state shows up.

  • Keep the fetched data in a variable, and have the search box filter that variable and call render(filtered).

6.3 — Forms, FormData & File Upload

Intercept a form, read its values, and send them — including files.

Reading values from a form

const form = document.querySelector("#form");
const email = form.email.value;            // by name
const email2 = form.querySelector("#email").value;   // by id

Note: form.email works because named form controls are accessible as properties of the form element. This is a genuinely useful, underused feature.

Intercepting the submit

form.addEventListener("submit", async (event) => {
  event.preventDefault();      // stop the page navigating
  const data = Object.fromEntries(new FormData(form));
  console.log(data);           // { name: "Ana", email: "a@b.c" }
});

Two steps, both essential:

  1. event.preventDefault() — otherwise the browser navigates away and your code never finishes.
  2. new FormData(form) — builds an object of all the form's named controls. Checked checkboxes and selected options are included; unchecked checkboxes are not (that's correct HTML behaviour — a missing key means "unchecked").

FormData vs JSON

FormDataJSON
Content-Typeset automatically (multipart/form-data)you set it: application/json
Filesyesno (not without base64 encoding)
Nested valuesflat (or formdata.append(name, value, filename))arbitrarily nested
Readable in DevToolsnoyes
// JSON
await fetch("/api/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name, email }),
});

// FormData - note: NO Content-Type header!
const fd = new FormData();
fd.append("name", name);
fd.append("avatar", fileInput.files[0]);
await fetch("/api/users", { method: "POST", body: fd });

Do NOT set Content-Type manually when sending FormData. The browser must set it itself, because the boundary (the separator between parts) is generated at send time. If you set it to multipart/form-data without a boundary, the server can't parse the body and you'll get a confusing 400.

File uploads

const input = document.querySelector("#avatar");
input.addEventListener("change", () => {
  const files = input.files;          // a FileList
  const file = files[0];              // a File
  console.log(file.name, file.size, file.type);
  console.log(file instanceof File);
});
  • input.files → a FileList (array-like, has length and index access).
  • Each File has name, size (bytes), type (MIME string, from the browser — not verified content!), and lastModified.
  • You can read the file as text, data URL, or blob: file.text(), URL.createObjectURL(file).

Python brain: FormData is like a requests files={...} dict, and File is like Django's UploadedFile. The browser handles the multipart encoding for you, exactly like requests does.

What to notice

  • file.type comes from the browser and is not a security check — a user can send a .exe renamed to .jpg. Always validate on the server.
  • Object.fromEntries(new FormData(form)) gives a plain object — but multiple values with the same name (checkboxes) need formData.getAll(name) instead of get(name).

Challenge — A working signup form

Build a signup form that:

  1. On submit, prevents the default and reads all values with FormData.
  2. Validates the email client-side and shows an error message under the field (use textContent).
  3. Shows the payload it would send as JSON, so you can see the shape.
  4. Adds a file input for an avatar, and shows the file's name and size after selection.
  5. Sends it to a fake endpoint with fetch and body: formData — without setting a Content-Type header — and handles the failure gracefully (the endpoint won't exist, so the error path will run — that's the point).
Stuck? Open the hints
  • form.elements.email.value is a reliable way to read a field by name.
  • To preview a selected file: URL.createObjectURL(file) into an <img>. Remember to URL.revokeObjectURL when you replace it.

6.4 — Higher-Order Functions & Functional Patterns

Write functions that take and return functions — and use closures for real.

A higher-order function is a function that takes a function as an argument, or returns one. Python has these too (map, sorted(key=...), decorators).

function withLogging(fn) {
  return function (...args) {
    console.log("calling", fn.name);
    return fn(...args);
  };
}

const loggedSum = withLogging((a, b) => a + b);
loggedSum(1, 2);   // "calling sum" then 3

Common patterns

// map with an index
names.map((name, i) => `${i + 1}. ${name}`);

// filter with extra conditions
users.filter(u => u.active && u.score > 80);

// reduce into a Map (grouping)
const byRole = users.reduce((acc, u) => {
  (acc[u.role] ??= []).push(u);
  return acc;
}, {});

// sort with a comparator
items.sort((a, b) => a.price - b.price);

// chaining with a custom method
const words = text.toLowerCase().split(/\s+/).filter(Boolean);

Memoization — a closure doing real work

function memoize(fn) {
  const cache = new Map();
  return function (...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) return cache.get(key);
    const result = fn(...args);
    cache.set(key, result);
    return result;
  };
}

const slowSquare = memoize(n => { /* expensive */ return n * n; });

This is the payoff of closures: the cache lives inside the returned function, is private, and persists for exactly as long as someone holds a reference. No class, no global, no cleanup needed.

Watch out for:

  • Unbounded caches are a memory leak. Add a size limit for real use.
  • Caching by JSON.stringify(args) breaks for functions, DOM nodes, and circular objects. For objects, use a WeakMap keyed by the object itself.

Composition

const withPrefix = s => "Mr. " + s;
const upper = s => s.toUpperCase();
const greet = s => `Hello, ${s}`;

const formal = compose(greet, upper, withPrefix);
formal("ana");   // "Hello, MR. ANA"

What to notice

  • ??= (logical assignment) is new-ish and handy: acc[u.role] ??= [] creates the array only if it's missing. It also works with ||= and &&=.
  • Array methods accept an index as a second argument: map((v, i) => ...) and filter((v, i) => ...). reduce gets (acc, value, index, array).

Challenge — Build a utility belt

Write these higher-order functions yourself:

  1. once(fn) — calls fn only the first time; later calls return the first result.
  2. debounce(fn, ms) — delays fn until ms have passed without another call. (Act 6 Step 6.5.)
  3. curry(fn) — turns f(a, b) into f(a)(b).
  4. pipe(...fns) — left-to-right function composition.

Each one takes a function and returns a function. Each one must be built with a closure — no classes.

Test debounce by calling it 5 times in 100ms and confirming the function only ran once.

Stuck? Open the hints
  • once is: let called = false, result; return (...args) => { if (!called) { called = true; result = fn(...args); } return result; }
  • debounce needs a timer id in the closure, cleared and re-set on every call.

6.5 — Debounce, Throttle & requestAnimationFrame

Keep the UI responsive when the user does things too fast.

The problem

Typing in a search box fires an input event on every keystroke. If each one triggers an API call, you'll fire 8 requests for an 8-letter word, and 7 of them are wasted. Worse, a heavy input handler makes typing feel laggy.

Debounce — wait until they stop

function debounce(fn, delay) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

const search = debounce(() => fetchResults(input.value), 300);
input.addEventListener("input", search);

The function runs only after the user stops for 300ms. Use it for: search suggestions, autosave, validation after typing, resize handlers that trigger layout.

Throttle — run at most every N ms

function throttle(fn, interval) {
  let last = 0, timer = null;
  return function (...args) {
    const now = Date.now();
    const remaining = interval - (now - last);
    if (remaining <= 0) {
      clearTimeout(timer);
      last = now;
      fn.apply(this, args);
    } else if (!timer) {
      timer = setTimeout(() => {
        last = Date.now();
        timer = null;
        fn.apply(this, args);
      }, remaining);
    }
  };
}

Use it for: scroll handlers, mouse-move handlers, infinite-scroll loading, drag tracking.

DebounceThrottle
Runsonce, after activity stopsat a fixed maximum rate
During continuous activitynever runsruns periodically
Use for"the user finished typing""this happens a lot, don't overdo it"

requestAnimationFrame — the right way to animate

function animate() {
  el.style.transform = `translateX(${x}px)`;
  x += 1;
  if (x < 500) requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

rAF runs your callback right before the next repaint, synced to the display's refresh rate (usually 60 or 120Hz). It's far better than setInterval(fn, 16), because it:

  • pauses when the tab is in the background (no wasted work),
  • stays in sync with the actual refresh rate,
  • is the only correct way to drive a canvas or a smooth drag.

requestIdleCallback — do low-priority work

requestIdleCallback((deadline) => {
  if (deadline.timeRemaining() > 5) {
    // do a little work while the browser is idle
  }
});

Perfect for: prefetching, analytics, pre-computing a list, cleaning up unused resources. Never use it for anything the user is waiting on.

What to notice

  • The this inside a debounced/throttled function is lost unless you use fn.apply(this, args). That's exactly what apply is for — this is a legitimate use of it.
  • requestIdleCallback isn't supported in Safari (as of writing). Feature-detect with if ('requestIdleCallback' in window) and fall back to setTimeout(fn, 1).

Challenge — Make it feel instant

  1. Build a search box that only queries after the user stops typing for 400ms. Log every call so you can prove it works.
  2. Add a debounced window resize handler that logs the new width — and show the difference with and without debouncing (scroll a resize by dragging the window).
  3. Implement throttle and use it on a scroll listener that updates a "scroll position" readout.
  4. Rewrite the scroll readout using requestAnimationFrame instead — and explain why rAF is smoother here.
  5. Bonus: use requestIdleCallback to precompute a list of 10,000 squares while the user is idle, and measure how long it takes.
Stuck? Open the hints
  • For the resize test, use the browser's device toolbar (Ctrl+Shift+M) and rotate it — that fires many resize events quickly.
  • A rAF-based scroll handler typically stores the latest scroll value and only re-renders on the next frame: let ticking = false;

6.6 — Web Workers

Move CPU-heavy work off the main thread so the page never freezes.

JavaScript is single-threaded. A long synchronous calculation blocks everything — clicks, scrolling, animations, rendering. The page appears frozen and the browser may show the "This page is unresponsive" dialog.

The solution

// worker.js - a completely separate script, running on its own thread
self.onmessage = function (e) {
  const result = heavyWork(e.data);
  self.postMessage(result);
};

// main.js
const worker = new Worker("worker.js");
worker.postMessage({ data: myBigArray });
worker.onmessage = (e) => console.log("result:", e.data);

A worker is a full JavaScript environment on a background thread. It has no DOM (no document, no window), but it has fetch, setTimeout, IndexedDB, and postMessage.

Main threadWorker
DOM, windowself, no DOM
UI renderingno rendering
document.querySelectornot available
fetchfetch (with CORS rules)
blockingnever blocks the UI

Transferring data

By default, data is copied to the worker (structured clone). For big typed arrays you can transfer instead — zero copy, and the original becomes unusable:

const buffer = new ArrayBuffer(1024 * 1024 * 50);
worker.postMessage({ buffer }, [buffer]);   // transfer list

When you actually need a worker:

  • Parsing a huge JSON payload
  • Image/video processing (pixel loops)
  • Encrypting/decrypting large amounts of data
  • Syntax highlighting a huge file
  • Complex math (physics, geometry, statistics)

For a list of 100 items — don't. The overhead of starting a worker is real. Measure first.

Service workers are different

A Web Worker does computation. A Service Worker intercepts network requests — it's a proxy between your app and the network. That one is Act 9 Step 9.3.

What to notice

  • You can't create a Worker from a file:// page — the browser blocks it (same-origin policy). Serve the folder.
  • A worker script must be a separate file (or a Blob URL). You can't inline it in a <script> tag.
  • Workers have no access to localStorage — use IndexedDB instead, or pass data via postMessage.

Challenge — Move it to a worker

  1. Create worker.js that receives a number and posts back the result of the heavy calculation.
  2. Create index.html that starts the worker, sends the number, and displays the result and the elapsed time.
  3. Serve the folder (Live Server or python3 -m http.server) — workers don't work from file://.
  4. Compare: run the same work on the main thread and on the worker, and measure both. While the worker runs, keep clicking around — the page should stay responsive.
  5. Add a "Cancel" button that calls worker.terminate().
  6. Bonus: send a 50MB ArrayBuffer using the transfer list and measure the difference in copy time.
Stuck? Open the hints
  • In the worker, self is the global object (like window in the main thread). Use self.onmessage = (e) => { self.postMessage(result) }.
  • worker.terminate() kills the thread immediately — there's no graceful shutdown.

6.7 — Performance & Best Practices

Know the handful of rules that cover most real-world performance wins.

The rules that matter most

  1. Batch DOM writes. Changing the DOM repeatedly in a loop forces layout recalculation. Write once, at the end. (Read all, then write all — never interleave.)
  2. Animate transform and opacity only. They don't trigger layout or paint. (Act 2 Step 2.10.)
  3. Use requestAnimationFrame for visual updates, not setInterval. (Act 6 Step 6.5.)
  4. Debounce/throttle anything triggered by user activity. (Act 6 Step 6.5.)
  5. Lazy-load images and code you don't need yet: loading="lazy" on images, import() for code.
  6. Do the least work — a faster algorithm beats any micro-optimisation. .filter().map() over 10,000 items is usually fine; sorting 10,000 items inside a loop is not.

Lazy-loading JavaScript

// dynamic import - the chunk is fetched only when needed
button.addEventListener("click", async () => {
  const { openEditor } = await import("./editor.js");
  openEditor();
});

This is code splitting, and it's the single biggest performance feature of modern bundlers. React's React.lazy and Next.js's dynamic imports are built on exactly this.

Measuring, not guessing

ToolQuestion it answers
Performance panelWhat's slow? Layout, paint, script, or a long task?
Network panelWhat did I download? How big? How long did the server take?
Coverage panelWhat CSS/JS did I download but never use?
LighthouseAn overall score: performance, a11y, SEO, best practices
Memory panelWhat am I leaking?

The workflow that actually works: measure → find the bottleneck → change one thing → measure again. Never optimise blind. The Performance panel's "Frames" and "Main Thread" tracks will show you a red "Long Task" bar if your JavaScript is blocking — that's usually the answer.

The Core Web Vitals that matter

MetricMeasuresGood
LCPlargest contentful paint — when the main content appears< 2.5s
INPinteraction to next paint — how fast the UI responds to input< 200ms
CLScumulative layout shift — how much the page jumps< 0.1

INP is the one you'll feel. A heavy click handler, a big re-render, or a long synchronous task all hurt it. Everything in the list above is aimed at INP and LCP.

What to notice

  • CLS is caused by content that appears late (images without dimensions, ads, fonts). Setting width/height on images is the biggest fix.
  • The Coverage panel shows you unused CSS — it's how you discover that a framework's stylesheet is 200KB and you use 12% of it.

Challenge — Optimise something real

Build a page that renders 2,000 list items, then make it fast:

  1. Measure the render time with performance.now() around the render call.
  2. Open DevTools → Performance → record while rendering. What is the long task doing?
  3. Try three fixes and measure each:
    • build the whole list as a string and assign it once with innerHTML (much faster, but only safe for trusted data)
    • use a DocumentFragment and append it once
    • render only the first 50 items and add a "Show more" button
  4. Report the before/after numbers. Which fix won, and why?

Bonus: use IntersectionObserver to render more items as the user scrolls (that's infinite scroll — and it's how you avoid rendering 10,000 items at once).

Stuck? Open the hints
  • A DocumentFragment: const frag = document.createDocumentFragment(); ... frag.appendChild(li); ... list.appendChild(frag); — one DOM insertion instead of 2,000.
  • IntersectionObserver fires a callback when elements enter the viewport — perfect for lazy rendering.
