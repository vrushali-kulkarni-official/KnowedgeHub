Act 9 · Step 9.3

Service Workers & PWAs

Understand the proxy between your app and the network, and what it unlocks.

What to notice

  • Always call event.respondWith() synchronously in the fetch handler — if you await something first, the browser gives up and goes to the network directly.
  • When you update a service worker, the old one stays active until every tab using it is closed. skipWaiting() and clients.claim() can change that, but carefully.
  • Debug a service worker in DevTools → Application → Service Workers, and check "Offline" in the Network panel to simulate a lost connection.

Try it (needs a server)

Service workers require https:// or localhost. Start the Act 10 server (node server.js), then open http://localhost:3000/sw-demo and register the worker from the console:

await navigator.serviceWorker.register("/sw.js");
console.log("registered!");

Then in DevTools → Application → Service Workers, check Offline and reload. The page still works.

Challenge — Make it work offline

  1. Create sw.js with a cache-first strategy for static assets and a network-first strategy for /api/* requests.
  2. Register it from your page and verify in DevTools → Application → Service Workers.
  3. Go offline (Network panel → Offline checkbox) and reload. What still works? What doesn't?
  4. Add a versioned cache name (myapp-v1) and delete old caches in the activate handler.
  5. Add a manifest.json and an icon, and check DevTools → Application → Manifest. Is your app installable?
  6. Advanced: implement stale-while-revalidate for the API, so the app shows cached data instantly and updates when the network responds.
Stuck? Open the hints
  • The "Offline" checkbox in the Network panel is the fastest way to test a service worker.
  • Version your cache name and, in the activate handler, delete every cache that isn't the current version.
