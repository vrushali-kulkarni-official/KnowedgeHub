9.1 — Streaming Responses

Read a response as it arrives, and render it live — the technique behind every AI chat UI.

Normally, await response.json() waits for the entire body before you get anything. For an AI response, you want to show tokens as they arrive.

Reading a stream

const response = await fetch("/api/stream");
const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const chunk = decoder.decode(value, { stream: true });
  output.textContent += chunk;   // append as it arrives
}

Three pieces:

  • response.body is a ReadableStream.
  • getReader() locks it so you can pull chunks.
  • TextDecoder converts bytes → text. The { stream: true } option is essential: a multi-byte character (like an emoji) can be split across two chunks, and without this you'd get a broken character. The decoder buffers the remainder for you.

Handling partial lines

Server-sent-style protocols send data: ... lines. A chunk can contain half a line, so you need a buffer:

let buffer = "";
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const lines = buffer.split("\n");
  buffer = lines.pop();              // keep the incomplete last line
  for (const line of lines) {
    if (line.startsWith("data: ")) {
      handle(line.slice(6));
    }
  }
}

Why this matters beyond AI chat: streaming makes a slow response feel fast. The user sees progress immediately instead of staring at a spinner for 10 seconds. Any long-running server response can be streamed this way.

Aborting

const controller = new AbortController();
fetch("/api/stream", { signal: controller.signal });
controller.abort();   // cancel the request

Always wire the abort controller to a "Stop" button — it's the expected UX for streaming UIs.

What to notice

  • response.body is null in some older browsers and for some responses (like a 204). Guard with if (!response.body) return;.
  • You can also use for await (const chunk of response.body) — a much nicer syntax, and it handles the reader cleanup for you. Check browser support for async iteration over streams.

9.2 — Server-Sent Events (SSE)

Receive server-pushed updates over one long-lived HTTP connection.

SSE is a one-way, server→client stream over plain HTTP. The server keeps the connection open and pushes text/event-stream data.

Server side (Node)

app.get("/events", (req, res) => {
  res.writeHead(200, {
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
  });
  res.write("data: " + JSON.stringify({ time: Date.now() }) + "\n\n");
  const t = setInterval(() => {
    res.write("data: " + JSON.stringify({ n: Math.random() }) + "\n\n");
  }, 2000);
  req.on("close", () => clearInterval(t));
});

Client side

const es = new EventSource("/events");
es.onmessage = (e) => console.log("message:", e.data);
es.onerror = () => console.log("connection error (browser auto-reconnects)");
es.close();   // stop

The format: each message is data: <content> followed by a blank line. Other fields exist: event: (a named event type), id: (for reconnection), retry: (reconnect delay in ms).

SSEWebSocket
Directionserver → clientboth ways
Protocolplain HTTPWebSocket (upgrades)
Reconnectautomaticmanual
Headers / authnormal headers (limited)only at handshake
Complexityvery lowhigher
Use fornotifications, live updates, AI chatchat, collaborative apps, games

Why SSE over WebSocket for most cases? It's plain HTTP — it works through proxies, it reconnects automatically, it sends Last-Event-ID on reconnect so the server can resume, and it needs no extra library. Use WebSocket only when the client genuinely needs to push data to the server frequently.

Named events

// server
res.write("event: price\ndata: {"symbol":"ACME","price":123}\n\n");

// client
es.addEventListener("price", (e) => console.log("price update:", JSON.parse(e.data)));

Note: a named event does not fire onmessage — you need addEventListener("price", ...).

What to notice

  • SSE requires HTTP/1.1+ and works over HTTP/2. It does not work from a file:// page.
  • EventSource auto-reconnects with a backoff, and sends the last id it saw in the Last-Event-ID header — let your server use that to resume.
  • To send auth with SSE you can't set custom headers on EventSource. Use a cookie, or use fetch + ReadableStream (Act 9 Step 9.1) instead.

  6. Now: send a message to the server from the client over the same connection. Can you? What's the alternative?
Stuck? Open the hints
  • SSE is one-way by design. To send data to the server, use a separate fetch POST, or move to WebSockets.
  • The reconnect backoff is visible in the Network panel as repeated /events requests with increasing gaps.

9.3 — Service Workers & PWAs

Understand the proxy between your app and the network, and what it unlocks.

A Service Worker is a script the browser runs in the background, separate from your page, that intercepts every network request your page makes.

// sw.js
self.addEventListener("install", (event) => {
  event.waitUntil(caches.open("v1").then(c => c.addAll(["/", "/app.js", "/style.css"])));
});

self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then(cached =>
      cached || fetch(event.request)
    )
  );
});

The lifecycle

  1. register — navigator.serviceWorker.register("/sw.js")
  2. install — the worker runs; you usually pre-cache assets here
  3. activate — the worker is live; clean up old caches here
  4. fetch — every request from the page passes through the worker

Service workers only run on secure origins — HTTPS, or localhost. That includes http://localhost:3000, so local development is fine.

What you can build with it

FeatureHow
Offline supportserve cached assets when the network fails
Installable appa manifest + a service worker + HTTPS
Push notificationsthe PushManager API
Background syncretry failed requests when connectivity returns
Stale-while-revalidateshow the cached copy instantly, refresh in the background

Cache strategies

// Cache first (good for static assets that change rarely)
cached || fetch(request)

// Network first (good for API data that must be fresh)
fetch(request).catch(() => caches.match(request))

// Stale-while-revalidate (best of both)
const cached = await caches.match(request);
const network = fetch(request).then(res => {
  caches.open("v1").then(c => c.put(request, res.clone()));
  return res;
});
return cached || network;

Service workers are genuinely powerful and genuinely dangerous. A bug in a fetch handler can break your entire site — including for users who can't clear it easily. Always version your caches and clean up old ones in the activate handler. Test in a fresh window each time, not a persistent one.

The web app manifest

<link rel="manifest" href="/manifest.json">

{
  "name": "My App",
  "short_name": "MyApp",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#6366f1",
  "icons": [{ "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" }]
}

What to notice

  • Always call event.respondWith() synchronously in the fetch handler — if you await something first, the browser gives up and goes to the network directly.
  • When you update a service worker, the old one stays active until every tab using it is closed. skipWaiting() and clients.claim() can change that, but carefully.
  • Debug a service worker in DevTools → Application → Service Workers, and check "Offline" in the Network panel to simulate a lost connection.

Challenge — Make it work offline

  5. Add a manifest.json and an icon, and check DevTools → Application → Manifest. Is your app installable?
  6. Advanced: implement stale-while-revalidate for the API, so the app shows cached data instantly and updates when the network responds.
Stuck? Open the hints
  • The "Offline" checkbox in the Network panel is the fastest way to test a service worker.
  • Version your cache name and, in the activate handler, delete every cache that isn't the current version.

9.4 — WebSockets

Know when you need full-duplex communication, and the shape of the API.

A WebSocket is a persistent, bidirectional connection. The client can send and receive at will, on the same socket.

// Client
const ws = new WebSocket("wss://example.com/live");
ws.onopen = () => { console.log("connected"); ws.send(JSON.stringify({ type: "join", room: "42" })); };
ws.onmessage = (e) => console.log("message:", JSON.parse(e.data));
ws.onclose = () => console.log("disconnected");
ws.onerror = (e) => console.log("error", e);
ws.close();

// Server (ws library on Node)
const { WebSocketServer } = require("ws");
const wss = new WebSocketServer({ port: 8080 });
wss.on("connection", (socket) => {
  socket.on("message", (data) => console.log("got:", data.toString()));
  socket.send("hello from server");
});

Choosing between SSE and WebSockets

NeedUse
Server pushes updates, client only listensSSE — simpler, auto-reconnect
Client sends data frequently over the same channelWebSocket
Binary dataWebSocket
Work with HTTP infrastructure / proxiesSSE

Rule of thumb: start with SSE. It's plain HTTP, it reconnects by itself, and it needs no extra dependency. Reach for WebSockets only when you truly need the client to push on the same channel at high frequency — chat, collaborative editors, multiplayer games.

Getting the data into the DOM

A WebSocket is just a stream of messages. Combine it with Act 9 Step 9.1's streaming pattern to render tokens as they arrive:

ws.onmessage = (event) => {
  const { token } = JSON.parse(event.data);
  output.textContent += token;
};

For a chat UI, keep the messages in an array (your state) and re-render — the Act 5 pattern. The WebSocket just updates that array.

What to notice

  • Use wss:// (secure) in production — ws:// is blocked on HTTPS pages.
  • Always implement reconnection with exponential backoff. Networks drop; a production app must recover.
  • WebSocket connections are not throttled by the browser's HTTP limits, but they're also not free — don't open one per user per notification.
