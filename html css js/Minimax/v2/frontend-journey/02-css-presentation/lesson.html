CSS — Presentation

The cascade, the box, and the two layout systems (flex and grid) that you will use every single day.

HTML said what things are. CSS says how they look. The two are completely separate — which is exactly why you can restyle a page without touching its structure, and why a broken stylesheet never breaks the content.

CSS has one surprising core idea, and everything else is detail: the cascade. When several rules try to set the same property on the same element, the browser picks a winner by asking a fixed set of questions. Learn those questions and CSS stops being mysterious.

How to use this act: for every step, open the runnable file and change the values — change 40px to 200px, change red to rebeccapurple, delete a rule and see what breaks. CSS is not learnable by reading. It's learnable by poking.

2.1 — What CSS Is & Where It Lives

Learn the only syntax CSS has, and the three places a rule can live.

A CSS rule has exactly two parts: a selector (which elements) and a declaration block (what to do to them).

selector { property: value; property: value; }
h1 {
  color: #6366f1;
  font-size: 2rem;
}
  • h1 — the selector. "Every <h1> element."
  • color — the property.
  • #6366f1 — the value.
  • Semicolon after each declaration. The last one is optional; write it anyway.

Three places a rule can live

WhereSyntaxWhen
Inline<h1 style="color:red">almost never
Block<style> ... </style>small pages, critical CSS
External<link rel="stylesheet" href="a.css">everything else

Inline styles win over everything (except !important) — they beat every stylesheet rule, no matter the specificity. That's why inline styles are a debugging trap: you cannot override them without !important. If a style "won't apply", check for an inline style attribute first.

Comments

/* this is a CSS comment */

Not //. That's a JavaScript comment, and it's a very common mistake on day one.

Linking a stylesheet

&lt;head&gt;
  &lt;link rel="stylesheet" href="/css/styles.css"&gt;
&lt;/head&gt;

What to notice

  • The href path is relative to the HTML file, not to the CSS file. This trips people up constantly.

Challenge — Three roads to the same style

Create a page with a heading that is green and 24px. Achieve it three different ways:

  1. An external stylesheet (styles.css linked from the head)
  2. A <style> block in the head
  3. An inline style attribute on the element

Then: make the inline style red while the other two stay green, and explain in one sentence why the red wins. Finally, add !important to the external rule and see the balance flip.

Stuck? Open the hints
  • The order of the three mechanisms is: external/block rules < inline style < !important.
  • The !important flag isn't a magic bullet — it makes the rule impossible to override without another !important, which is a maintenance trap.

2.2 — Selectors & Specificity

Predict which rule wins, every time, without guessing.

The selectors you'll actually use

p            { }   /* type */
.card         { }   /* class */
#header       { }   /* id */
.card p       { }   /* descendant: a p inside .card */
.card > p     { }   /* child: a direct p inside .card */
.card + .card { }   /* adjacent sibling */
.card ~ p     { }   /* general sibling */
a[href^="https"] { }  /* attribute */
input:checked    { }  /* state (pseudo-class) */
button:hover     { }  /* state */

That list is 95% of real-world CSS. Learn these and you can read any stylesheet.

Specificity — the scoring system

When two rules set the same property on the same element, the browser scores them and picks the higher score. Each selector contributes points:

Selector partPoints
id (#foo)100
class (.foo), attribute ([type="text"]), pseudo-class (:hover)10
type (div), pseudo-element (::before)1
the universal selector (*)0

Read it like a number, not like a sum: #header .card p scores 1-1-1 = 111. .card p scores 0-1-1 = 11. The 111 wins, every time.

Tiebreak: if two rules have the same specificity, the one that comes later in the stylesheet wins. That's the "cascade" part of the name — the rules cascade down the stylesheet.

The one thing to internalise: specificity means you can never "override" a high-specificity rule with a low-specificity one, no matter how much later it appears. This is why people reach for !important and then regret it. The fix is to write selectors of equal specificity, or to keep one class per concern.

Two practical habits that prevent almost all specificity wars:

  1. One class per concern. .btn for the button, .btn--danger for the red variant — not .red.bold.rounded.
  2. Never go below "class" for styling. A chain like body .wrapper .card h2 span (0-1-4) is nearly impossible to override later. Keep your selectors short.

Reading specificity as a number

#header .card p   ->  1-1-1  ->  111   (wins)
.card p           ->  0-1-1  ->   11
p                 ->  0-0-1  ->    1

What to notice

  • The * selector has zero specificity, so * { box-sizing: border-box } never conflicts with anything.
  • Pseudo-classes like :hover count as classes (10). A class in an element's HTML is not the same thing as a .class selector — only selectors score.

Challenge — Score these

For each selector, work out the specificity score and say which rule wins when they all target the same element:

  1. div
  2. .box
  3. div.box
  4. #main .box
  5. nav ul li a
  6. nav ul li a:hover
  7. input[type="text"]
  8. input[type="text"]:focus

Then build a test page with a button styled by four different rules of increasing specificity and confirm the order of winners with the DevTools Styles panel (it shows struck-through rules — the ones that lost).

Stuck? Open the hints
  • :hover and :focus are pseudo-classes, worth 10 each — the same as a class.
  • In the DevTools Styles panel, a struck-through declaration means a higher-specificity rule overrode it. That's your whole cascade, visualised.

2.3 — Inheritance & Custom Properties

Control how properties flow down the tree, and build themable values with CSS variables.

Some properties inherit, most don't

Inherited (children take the parent's value): color, font-family, font-size, line-height, text-align, visibility, letter-spacing.

Not inherited: margin, padding, background, border, width, height, display, position.

Python brain: inheritance in CSS is on the property, not on the element. It's like a class attribute being read down an object tree, but each property decides for itself whether to pass it on. There's no inherit: false global switch.

Three keywords override this per property: inherit (force it on), initial (reset to the spec default), unset (inherit if inheritable, else initial).

Custom properties — your first design tokens

:root {
  --brand: #6366f1;
  --brand-dark: #4f46e5;
  --radius: 10px;
  --space: 16px;
}

.btn {
  background: var(--brand);
  border-radius: var(--radius);
  padding: calc(var(--space) / 2) var(--space);
}

Custom properties (--name) are the only way to store a value in CSS. They are inherited by default, and they can be redefined on any element — which makes them the foundation of theming and dark mode.

Why this matters for tomorrow: Tailwind, shadcn/ui and every modern design system are built on CSS variables. When you see bg-background text-foreground in a shadcn component, those are CSS variables under the hood. Learning them now means shadcn won't be a black box.

Theming by redefining one variable

:root            { --bg: #ffffff; --fg: #15151d; }
html[data-theme="dark"] { --bg: #101019; --fg: #e8e8f2; }

body { background: var(--bg); color: var(--fg); }

What to notice

  • Custom properties are resolved at use time, not at definition time. If --brand changes on an ancestor, everything using var(--brand) below it updates instantly.
  • var(--x, fallback) provides a fallback value if the variable isn't defined — worth using for safety.

Challenge — A themeable card

Build a card that works in both light and dark mode using only custom properties:

  1. Define --card-bg, --card-fg, --card-border and --accent in :root.
  2. Add a class .dark that redefines those four variables.
  3. Style the card using var() only — no literal colours anywhere in the card rule.
  4. Add a button that toggles the .dark class. (Hint: Act 4 has the JavaScript, but you can also do it with a tiny inline onclick just to see the effect.)

Now change --accent in one place and confirm every accent in the card updates. That's the payoff.

Stuck? Open the hints
  • You need three variables, not one: the card's own background is different from the page's background, and in dark mode both change.
  • If a child element ignores your variable, check whether you're redefining the variable on the card instead of on :root — variables resolve from the element they're used on, walking up.

2.4 — The Box Model

Predict the size of every element on the page, exactly.

Every element on the web is a rectangle, and every rectangle is made of four nested layers:

┌─────────────────────────────────┐  margin  (space OUTSIDE, always transparent)
│ ┌───────────────────────────────┐ │  border
│ │ ┌───────────────────────────┐ │ │  padding  (space INSIDE, takes the bg colour)
│ │ │                           │ │ │  content  (text, images, ...)
│ │ └───────────────────────────┘ │ │
│ └───────────────────────────────┘ │
└─────────────────────────────────┘

Two box-sizing modes decide how width is interpreted:

Modewidth: 200px meansTotal space taken
content-box (default)the content area is 200px200 + padding + border
border-boxthe whole box is 200pxalways 200

Always use border-box. Nearly every modern project starts with:

*, *::before, *::after { box-sizing: border-box; }

It makes width mean what you think it means. (Tailwind does this for you automatically — which is one of the nice things about it.)

Margin collapse

Vertical margins between block elements collapse: the browser uses the larger of the two, not the sum. Two blocks with 20px and 30px top margins sit 30px apart, not 50px.

This is genuinely surprising and it is the cause of most "why is there a gap here" questions. It does not happen for horizontal margins, does not happen for flex or grid children, and does not happen when a parent has padding, a border, or overflow: auto.

The global reset every project starts with

*, *::before, *::after { box-sizing: border-box; }
body { margin: 0; }

What to notice

  • margin pushes things apart and is outside the element. padding is inside and takes the element's own background colour. Confusing the two is the single most common CSS beginner bug.
  • The * selector has zero specificity, so it never fights with your own rules.

Challenge — Calculate it before you run it

For each of these, write down the total width before you open DevTools:

  1. width: 200px; padding: 20px; (content-box)
  2. The same, with box-sizing: border-box
  3. width: 200px; padding: 20px; border: 5px solid; (content-box)
  4. width: 50%; padding: 20px; inside a 800px-wide parent (content-box)
  5. Two sibling blocks with margin-bottom: 20px and margin-top: 30px — what's the gap?

Then verify each one in DevTools. The last one is the margin-collapse case — if your prediction was 50px, you're right about the arithmetic and wrong about the rule.

Stuck? Open the hints
  • In DevTools, hover the element and the tooltip shows you the exact used values for content, padding, border and margin.
  • Margin collapse takes the maximum, not the sum: 30px.

2.5 — Display & the Normal Flow

Understand the default layout algorithm, and how to take an element out of it.

CSS lays out elements in a predictable way if you don't interfere. This is called normal flow, and understanding it explains 90% of "why is my layout weird".

displayBehaviour
blockStarts on a new line, fills the width, stacks vertically. The default for div, p, section, h1.
inlineFlows inside a line of text. The default for span, a, strong, img.
inline-blockInline, but you can set width/height. img and button behave like this by default.
noneRemoved from the page entirely — not just invisible. It takes no space and isn't focusable.

The two you will meet most in real code:

display: flex;        /* the element becomes a flex container */
display: inline-flex; /* flex, but participates in an inline line */
display: grid;        /* the element becomes a grid container */
display: none;       /* gone */
visibility: hidden;  /* invisible, but still takes up space */

display:none vs visibility:hidden: the first removes the element from the layout entirely (everything shifts up); the second keeps its space reserved. Choosing wrong causes "why did my whole page jump" bugs.

Sizing

width: 50%;          /* % of the PARENT's content width */
max-width: 640px;   /* the cap — this is what makes readable text columns */
min-width: 0;       /* critical inside flex/grid: lets items shrink */
margin: 0 auto;     /* centres a block horizontally */

max-width is underrated. A page of text at 2000px wide is unreadable — your eyes can't scan that. max-width: 65ch is a great default for body text, and margin: 0 auto centres it.

Inline vs block, side by side

&lt;p&gt;A &lt;span&gt;inside&lt;/span&gt; a paragraph stays in the line. &lt;/p&gt;

&lt;div&gt;A div starts on its own line and fills the width.&lt;/div&gt;

What to notice

  • Setting width on an inline element does nothing. That's why inline-block exists.
  • You can override a UA default like display: inline on a <span> — but then you're on the hook for all the other inline quirks.

Challenge — A readable article column

Build a page that demonstrates the difference between block and inline layout:

  1. A <div> with a background — show that it fills the width and starts on a new line.
  2. Three <span>s with backgrounds on one line — show that they flow inside the text.
  3. Convert one span to inline-block with a fixed width, and another to display: none. Notice that the second one doesn't leave a gap, but a visibility: hidden one would.
  4. Add a <main> with max-width: 65ch; margin: 0 auto; and put a long paragraph in it. Read it. Compare with the same paragraph at full width.
Stuck? Open the hints
  • For the display:none vs visibility:hidden comparison, put a background on the parent so you can see whether the space is still reserved.

2.6 — Flexbox

Master the one layout system you'll use every single day.

Flexbox lays out items in one dimension — a row or a column. It's the right tool for toolbars, nav bars, button groups, form rows, and "put this thing next to that thing and make it flex".

Vocabulary

  • Container — the element with display: flex.
  • Items — its direct children. Only direct children are flex items; grandchildren are not.
  • Main axis — the direction items flow (set by flex-direction).
  • Cross axis — perpendicular to it.

The properties that matter

.container {
  display: flex;
  flex-direction: row;       /* row | column | row-reverse | column-reverse */
  justify-content: flex-start; /* along the MAIN axis: space distribution */
  align-items: stretch;     /* along the CROSS axis: alignment */
  gap: 12px;                /* space between items (always prefer this over margins) */
  flex-wrap: nowrap;        /* wrap onto multiple lines */
}

Mnemonic that actually sticks: justify = main axis, align = cross axis.

Sizing items

.item { flex: 1; }        /* grow:1 shrink:1 basis:0% — equal columns */
.item { flex: 0 0 200px; } /* fixed-ish: no grow, no shrink, 200px basis */
.item { flex: 1 1 auto; }  /* grow to fill, but start from content size */

flex: 1 means "share the leftover space equally" — the trick behind equal-width columns. flex: 0 0 200px means "don't grow, don't shrink, start at 200px" — the trick behind fixed-width sidebars.

Always use gap, not margin tricks. gap only adds space between items, so there's no leading/trailing space to fight with, and it works with wrapping. The old margin-right + :last-child {margin:0} dance is unnecessary in every browser that matters.

A complete flex container in one shot

.toolbar {
  display: flex;
  align-items: center;
  gap: 8px;
}
.toolbar .spacer { flex: 1; }   /* pushes everything after it to the right */

What to notice

  • Flex items have min-width: auto by default, which means a long unbreakable word can stop them shrinking. The classic fix is min-width: 0 on the item.
  • align-items: stretch (the default) makes all items the same height as the tallest one. flex-start makes them keep their natural height.

Challenge — Build a navbar with flexbox

No float, no position: absolute — flexbox only:

  1. A horizontal bar containing a logo on the left, three links in the middle, and a button on the right.
  2. Make the middle links push the button to the far right (the spacer trick).
  3. Make the whole bar a column layout on narrow screens: logo on top, links below, full width. (Do this with a media query — Act 2 Step 2.9.)
  4. Give the links a gap of 16px and remove all default list bullets and padding.

Extra credit: make the button margin-left: auto instead of using a spacer element. Same result, less markup — when is that better?

Stuck? Open the hints
  • The spacer approach uses flex: 1 on an empty div. The margin-left: auto approach avoids the extra element — the browser pushes the rest of the flex line away.
  • ul has default padding-left and list-style. Reset both: list-style: none; padding: 0;

2.7 — CSS Grid

Lay out in two dimensions, and stop reaching for nested flex hacks.

Grid lays out items in two dimensions — rows and columns at once. That's the difference from flexbox, and it's why grid replaced most "float" and "flex-in-a-flex" layouts.

.grid {
  display: grid;
  grid-template-columns: repeat(3, 1fr);   /* 3 equal columns */
  grid-template-columns: 200px 1fr 200px;  /* sidebar | content | sidebar */
  grid-template-rows: auto 1fr auto;      /* header | main | footer */
  gap: 16px;
}

1fr means "one share of the free space" — the fr unit is grid's most useful idea. 200px 1fr 200px gives you fixed sidebars and a fluid middle.

Explicit placement

.layout {
  display: grid;
  grid-template-columns: repeat(4, 1fr);
  grid-template-rows: auto 1fr auto;
  grid-template-areas:
    "head head head head"
    "side main main main"
    "foot foot foot foot";
}
.head { grid-area: head; }
.side { grid-area: side; }

grid-template-areas is the most readable layout system ever invented. You draw the layout as ASCII art. A "media query" version of it (Act 2 Step 2.9) can redraw the whole page for mobile by changing just those strings.

Spanning

.wide { grid-column: span 2; }   /* across two columns */
.full { grid-column: 1 / -1; }      /* across ALL columns */

Flex or grid?

UseWhen
FlexboxOne dimension. Rows of items, toolbars, button groups, "these should share the space equally".
GridTwo dimensions. Page layouts, card grids, dashboards, forms with aligned fields.

Rule of thumb: if you're about to nest two flexboxes to fake rows and columns, use grid instead.

A classic app shell in 12 lines

.shell {
  display: grid;
  grid-template-columns: 240px 1fr;
  grid-template-rows: auto 1fr;
  grid-template-areas: "side head" "side main";
  min-height: 100vh;
}
.shell > header { grid-area: head; }
.shell > aside  { grid-area: side; }
.shell > main   { grid-area: main; }

What to notice

  • gap works in grid exactly like flex — and again, prefer it over margins.
  • repeat(auto-fit, minmax(240px, 1fr)) is the famous responsive-card-grid one-liner: as many columns as fit, each at least 240px. You'll use it constantly.

Challenge — A dashboard layout

Build a dashboard shell with grid-template-areas:

┌──────────┬──────────────────────┐
│          │  header               │
│  sidebar ├───────────┬──────────┤
│          │  card     │  card    │
│          ├───────────┴──────────┤
│          │  main panel          │
├──────────┴──────────────────────┤
│  footer                         │
└─────────────────────────────────�┘
  1. Name the areas side, head, card1, card2, main, foot.
  2. Make the sidebar and footer span the full width where shown.
  3. Set the main row to 1fr so it fills the remaining height.
  4. Bonus: on narrow screens, redraw the whole thing with a single media query that changes grid-template-areas to a one-column stack.
Stuck? Open the hints
  • An area name that appears in a row's string must appear in every row of the template, or the grid is invalid and the whole rule is dropped.
  • For the mobile version, just change the grid-template-areas value — the HTML stays identical. That's the payoff of named areas.

2.8 — Positioning & Stacking

Take elements out of normal flow deliberately, and control what paints on top.

ValueBehaviourUse for
static (default)Normal flow. top/left are ignored.everything, unless you need otherwise
relativeStays in flow, but can be nudged with top/left/right/bottom. Also creates a positioning context.small nudges, moving a badge
absoluteRemoved from flow. Positioned relative to its nearest positioned ancestor.tooltips, dropdown panels
fixedRemoved from flow and pinned to the viewport — doesn't scroll away.sticky headers, chat widgets
stickyStays in flow until it would scroll out, then sticks.section headers, toolbars

The key idea: an absolutely-positioned element is positioned relative to the nearest ancestor that is itself positioned (relative, absolute, fixed or sticky). If there is no such ancestor, it goes to the initial containing block (the page). This is why an absolutely positioned element sometimes appears in a surprising place — it found a different ancestor than you expected.

Stacking and z-index

z-index only applies to positioned elements (and flex/grid items with a z-index). It works within a stacking context — and here's the gotcha: an element that creates a stacking context (via position + z-index, opacity < 1, transform, filter, will-change, isolation) becomes a ceiling. Its children are locked inside it — a child with z-index: 9999 cannot rise above a sibling of its parent.

This is why "my z-index 9999 element is still behind something" happens. DevTools explains it: the element is covered by something in a different stacking context.

A sticky header and an absolute tooltip

.header { position: sticky; top: 0; z-index: 10; background: #fff; }
.tooltip { position: absolute; bottom: 100%; left: 0; }
/* the tooltip is positioned against .wrap, because .wrap is position: relative */
.wrap { position: relative; }

What to notice

  • position: fixed is relative to the viewport unless an ancestor has transform, filter or will-change — then it becomes relative to that ancestor. A classic mobile bug: a transform on an ancestor breaks position:fixed.
  • Use inset: 0 as a shorthand for top:0; right:0; bottom:0; left:0.

Challenge — A tooltip and a sticky header

  1. Build a button with a tooltip that appears on hover. The tooltip must be positioned relative to the button, not the page — and it must not affect the layout when hidden.
  2. Make a page tall enough to scroll, and give it a header that stays at the top when you scroll. position: sticky only.
  3. Add a z-index to the header so it passes over the content.
  4. Then break it on purpose: set transform: rotate(0.001deg) on an ancestor of the sticky header and see what happens. Now you know why "fixed" headers sometimes jump around on mobile.
Stuck? Open the hints
  • The tooltip wrapper needs position: relative, and the tooltip position: absolute with bottom: 100% to sit above it.
  • For the sticky header, the parent must not have overflow: hidden — a sticky element can't escape a scroll container that isn't scrolling.

2.9 — Responsive Design & Units

Write layouts that adapt to any screen, and size things in units that respect the user's settings.

Units

UnitRelative toUse for
pxnothing — absoluteborders, hairlines, tiny fixed bits
remthe root font size (usually 16px)almost everything
emthe element's own font sizepadding/margins that should scale with the text
%the parent's sizewidths, max-width
vw/vh1% of the viewport width/heightfull-height sections
chthe width of a "0" charactermax-width for text columns

Use rem for typography and spacing. Because rem is relative to the root font size, when the user increases their browser's default font size, your whole layout scales with it. A layout built in px ignores the user's accessibility settings entirely — that's a real problem, not a theoretical one.

Media queries — mobile first

/* base styles: mobile by default */
.container { display: grid; grid-template-columns: 1fr; gap: 16px; }

/* then enhance upward */
@media (min-width: 768px) {
  .container { grid-template-columns: 240px 1fr; }
}

Write the base styles for the smallest screen, then add min-width breakpoints. "Mobile first" isn't a buzzword — it means your default CSS is the simple case, and enhancements are opt-in.

Common breakpoints: 640px (sm), 768px (md), 1024px (lg), 1280px (xl), 1536px (2xl). These are conventions, not standards — but matching Tailwind's defaults is worth it.

Modern fluid sizing

h1 { font-size: clamp(1.5rem, 1.1rem + 2vw, 3rem); }

clamp(min, preferred, max) gives you a size that fluidly scales between a floor and a ceiling. No breakpoints, no JavaScript. It's the modern answer to "responsive typography".

A fluid type scale

:root { --step-0: clamp(1rem, 0.95rem + 0.25vw, 1.125rem); }
body  { font-size: var(--step-0); }
h1    { font-size: clamp(1.8rem, 1.3rem + 2.5vw, 3rem); }

What to notice

  • In DevTools, toggle the device toolbar (the phone/tablet icon) and set a custom width to test breakpoints. You can also type a CSS width directly in the toolbar.
  • prefers-reduced-motion is a media query too — respect it for animations.

Challenge — One layout, three widths

Build a single card component that lays out differently at three sizes without changing its HTML:

  • Under 640px: everything stacked in one column
  • 640px–1024px: image beside the text
  • Over 1024px: image, text, and a sidebar meta column

Then set the page font-size in DevTools to 24px and confirm the layout still works (that's what rem buys you).

Stuck? Open the hints
  • Change the grid-template-columns value at each breakpoint — the HTML doesn't move at all.
  • Using em for the gap inside the card makes the gap scale with the card's font size. Try it.

2.10 — Transitions, Transforms & Animation

Add motion that feels good and stays smooth.

Transition — animate a state change

.btn {
  background: #6366f1;
  transition: background .2s ease, transform .2s ease;
}
.btn:hover { background: #4f46e5; transform: translateY(-1px); }

A transition needs three things: a property that changes, a duration, and a timing function. Without a duration it's instantaneous (nothing animates).

Transform — change shape without triggering layout

transform: translate(10px, 20px);  /* move */
transform: scale(1.1);             /* resize */
transform: rotate(45deg);          /* rotate */
transform: translateX(-50%);      /* the classic "centre absolutely-positioned element" trick */

Why transforms are special: changing width forces the browser to re-run layout (reflow) and repaint. Changing transform can be handled on the compositor thread alone — no layout, no paint. That's the difference between 60fps and jank, and it's why you animate transform and opacity and almost nothing else.

Keyframe animation

@keyframes spin {
  from { transform: rotate(0deg); }
  to   { transform: rotate(360deg); }
}
.spinner { animation: spin 1s linear infinite; }

Note the order: animation: name duration timing iteration fill-mode;. The shorthand is famously hard to read, so many people write the long form:

animation-name: spin;
animation-duration: 1s;
animation-timing-function: linear;
animation-iteration-count: infinite;

Respect user preferences

@media (prefers-reduced-motion: reduce) {
  * { animation-duration: .01ms !important; transition-duration: .01ms !important; }
}

Some people get motion sickness from animations. This media query is a real accessibility requirement, not a nicety.

A complete hover interaction

.card {
  transition: transform .2s ease, box-shadow .2s ease;
}
.card:hover {
  transform: translateY(-4px);
  box-shadow: 0 12px 24px rgba(0,0,0,.12);
}

What to notice

  • Animating width/height/top/left triggers layout every frame. Animating transform and opacity does not. This is the single most useful performance fact in CSS.
  • The transition shorthand order matters: transition: property duration timing-function;

Challenge — Animate it the right way

Take a card and give it a hover state that lifts it. Then:

  1. Make it lift using transform: translateY().
  2. Now rewrite it using margin-top instead, and open DevTools → Performance while hovering repeatedly. What extra work appears, and why?
  3. Add a smooth transition to the hover state — and notice that if you forget the duration, nothing animates at all.
  4. Add a CSS-only "loading spinner" using @keyframes and animation: ... infinite.
Stuck? Open the hints
  • In the Performance panel, look for yellow "Layout" bars — those are the expensive frames. Animating transform shows purple "Composite" bars instead.
