10.1 — Node.js in 45 Minutes

Understand the runtime, the event loop, and enough Express to serve an API.

What Node is

Node runs JavaScript outside the browser. The same language, a different host — and a different set of capabilities. In the browser, JS is sandboxed (no filesystem, no raw sockets). In Node it has filesystem, networking, and process control.

// node hello.js
const fs = require("fs");          // CommonJS
// or
import fs from "node:fs";          // ES modules (needs "type": "module" in package.json)

console.log("Hello from Node");

The event loop is the same

Node's event loop is the same concept as the browser's (Act 4 Step 4.17), plus extra phases for I/O. But there's one crucial difference that trips up every JS developer who moves to the backend:

Node's event loop is not the same as the browser's.

In the browser, setTimeout(fn, 0) and setImmediate(fn) usually run in a predictable order. In Node, inside an I/O callback, the order is reversed. If you write code that depends on the exact ordering of these two, it will behave differently in Node than it did in the browser.

Short version: in Node, setImmediate runs before setTimeout(fn, 0) from within an I/O callback. Outside of one, they're effectively the same. This is a classic interview question and a classic source of "it works on the client but not the server" bugs.

Express in four lines

const express = require("express");
const app = express();

app.use(express.json());                 // parse JSON request bodies
app.get("/api/items", (req, res) => {
  res.json([{ id: 1, name: "Notebook" }]);
});
app.post("/api/items", (req, res) => {
  const item = { id: Date.now(), ...req.body };
  res.status(201).json(item);
});

app.listen(3000, () => console.log("http://localhost:3000"));

Request and response

app.post("/api/items", (req, res) => {
  console.log(req.body);         // parsed body (needs express.json())
  console.log(req.query);        // ?page=2 -> { page: "2" }
  console.log(req.params);       // /items/:id -> { id: "7" }
  console.log(req.headers);      // request headers

  res.json({ ok: true });        // send JSON
  res.status(404).json({ error: "Not found" });
  res.send("plain text");
  res.redirect("/elsewhere");
});

Python brain: Express is Flask/FastAPI distilled. Routing is declarative, middleware is decorators, and there's no type system — you validate input yourself. The req/res pair is roughly Flask's request/response objects.

What to notice

  • express.json() is middleware — it must be registered before the routes that need it, or req.body will be undefined.
  • Node's process.env holds environment variables. Never hard-code secrets.
  • app.use(express.static('public')) serves a folder of static files — that's how you serve a front end from the same origin as your API (and skip CORS entirely).

Challenge — A tiny API

  1. Create a folder with package.json (npm init -y).
  2. npm install express
  3. Write a server with:
    • GET /api/items — returns a JSON array from an in-memory variable
    • POST /api/items — appends an item (with a generated id)
    • DELETE /api/items/:id — removes one
  4. Test all three with curl from a terminal: curl -X POST localhost:3000/api/items -H "Content-Type: application/json" -d '{"name":"Pen"}'
  5. Now add a static route: serve a folder containing your front end, and fetch that page from the same origin. Why does this sidestep CORS?
Stuck? Open the hints
  • npm init -y creates the package.json. npm install express adds it as a dependency.
  • app.use(express.static(path.join(__dirname, 'public'))) serves everything in public/.

10.2 — CORS, Env Vars & Serving a Front End

Configure the things the browser insists on: CORS headers, environment variables, and static hosting.

CORS from the server

// allow one origin exactly
app.use(cors({ origin: "http://localhost:3000" }));

// allow several
const ALLOWED = ["http://localhost:3000", "https://myapp.com"];
app.use(cors({
  origin: (origin, cb) => {
    if (!origin || ALLOWED.includes(origin)) return cb(null, true);
    cb(new Error("Not allowed by CORS"));
  },
  credentials: true,
}));

Never write origin: "*" together with credentials: true. The browser will reject that combination — and rightly so: * would let https://evil.com read your authenticated responses.

You can also set the headers manually (no dependency needed):

app.use((req, res, next) => {
  res.setHeader("Access-Control-Allow-Origin", "http://localhost:3000");
  res.setHeader("Access-Control-Allow-Headers", "Content-Type, Authorization");
  res.setHeader("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS");
  if (req.method === "OPTIONS") return res.sendStatus(204);   // answer the preflight
  next();
});

Environment variables

// .env  (never commit this!)
PORT=3000
JWT_SECRET=super-secret-change-me
DATABASE_URL=postgres://...
// load it
require("dotenv").config();
const port = process.env.PORT || 3000;

Rules:

  • .env holds secrets. Add it to .gitignore. Commit .env.example instead (the keys, no values).
  • Secrets belong on the server. Anything in front-end JavaScript is public — anyone can read your bundle. A JWT secret in front-end code is not a secret.
  • Use process.env.X everywhere, never a literal.

Serving a front end from the same origin

app.use(express.static(path.join(__dirname, "public")));
app.get("*", (req, res) => res.sendFile(path.join(__dirname, "public", "index.html")));

Why this matters: same origin means no CORS at all, cookies work without any special flags, and the browser is happy. Most production apps do exactly this (or use a reverse proxy that does it for them).

What to notice

  • The manual CORS middleware must handle OPTIONS itself — the browser's preflight never reaches your route handlers otherwise.
  • res.setHeader before res.json() — once the response is sent, headers can't be changed.

Challenge — Make the browser happy

  1. Start your Act 10 server and create a page on a different port that fetches from the API. What error do you get?
  2. Add the CORS middleware allowing that origin. Reload. Does it work now?
  3. Now add a route to the server that sets Cache-Control and an ETag, and verify with the Network panel that a reload returns 304 Not Modified.
  4. Move your frontend into public/ and serve it from the same origin. Delete the CORS middleware. Does it still work? Why?
  5. Add a .env with a PORT and a fake JWT_SECRET, load them with dotenv, and confirm the server uses them. Add .env to .gitignore and create .env.example.
Stuck? Open the hints
  • Two servers on different ports = different origins = CORS applies. Same port = same origin = CORS doesn't apply.
  • The ETag can be a hash of the body: crypto.createHash('md5').update(body).digest('hex')

10.3 — Webhooks, End to End

See how a server receives a third-party event and pushes it to a browser.

A webhook is when a third-party service makes an HTTP request to your server when something happens. Stripe says "payment succeeded", so it POSTs to your endpoint.

Why the front end cares

A browser cannot receive a webhook. Webhooks are inbound HTTP requests to a server. Your browser can't be the endpoint — there's no public address to send to, and browsers don't accept incoming connections.

So the flow is always:

Stripe  ──POST──>  YOUR SERVER  ──(SSE / WebSocket)──>  BROWSER
   webhook              stores it, then pushes          the live update

Server side

app.post("/webhooks/stripe", express.raw({ type: "application/json" }), (req, res) => {
  // 1. verify the signature (CRITICAL)
  const sig = req.headers["stripe-signature"];
  if (!verifySignature(req.body, sig, process.env.WEBHOOK_SECRET)) {
    return res.status(400).send("Invalid signature");
  }
  // 2. acknowledge FAST - Stripe retries if you're slow
  res.status(200).send("ok");
  // 3. do the real work
  const event = JSON.parse(req.body.toString());
  broadcast({ type: "payment", data: event });
});

Two critical details:

  • Verify the signature. Otherwise anyone who finds your webhook URL can send fake events. Webhook providers sign the payload with a shared secret.
  • Respond within a few seconds. Providers usually time out and retry. Do the slow work after responding — queue it, or use setImmediate.

Pushing to the browser

const clients = new Set();

app.get("/events", (req, res) => {
  res.writeHead(200, { "Content-Type": "text/event-stream" });
  clients.add(res);
  req.on("close", () => clients.delete(res));
});

function broadcast(payload) {
  for (const client of clients) {
    client.write("data: " + JSON.stringify(payload) + "\n\n");
  }
}

The full picture

  1. Browser opens an SSE connection to /events and stays connected.
  2. Stripe POSTs to /webhooks/stripe.
  3. Your server verifies the signature, responds 200, and calls broadcast().
  4. The browser's EventSource receives the event and updates the DOM.

What to notice

  • Webhooks are at-least-once delivery — providers retry on failure, so you'll get duplicates. Use the event id to deduplicate.
  • Verify the signature with a timing-safe comparison, and never log the full secret.
  • For local testing, most providers have a CLI (e.g. Stripe CLI) that can forward real webhook events to your machine.

Challenge — The full loop

  1. In server.js, add the /webhooks/demo route and the /events SSE route with broadcast().
  2. Build a page that connects via SSE and displays incoming events.
  3. Trigger a fake webhook from a second terminal: curl -X POST localhost:3000/webhooks/demo -H "Content-Type: application/json" -d '{"type":"test","n":1}'
  4. Watch the page update without a refresh.
  5. Add a signature check (a simple shared-secret HMAC) and confirm a request with the wrong signature is rejected.
  6. Now think about production: what happens if your server restarts? Where should events be stored? (Answer: a queue/database, and the browser should be able to catch up — that's what the SSE id / Last-Event-ID is for.)
Stuck? Open the hints
  • Node's crypto module has createHmac('sha256', secret).update(payload).digest('hex').
  • A simple shared-secret check is enough for a learning project. Real providers use asymmetric signatures (a public key you can safely publish).
