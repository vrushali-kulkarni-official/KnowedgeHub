DOM manipulation · Step 7

Walking the tree: parents, children, siblings

Sometimes you do not know the selector — you only know where the click happened. The DOM gives you ways to move up, down and sideways.

The idea

el.parentElement        // the element's parent
el.children            // list of child ELEMENTS (not text nodes)
el.firstElementChild   // first child element
el.lastElementChild    // last child element
el.nextElementSibling  // the next element after me
el.previousElementSibling
el.closest(".card")   // the nearest ancestor (or me) matching this selector

Two words to be careful about:

  • children vs childNodes. children gives you only elements. childNodes also gives you text nodes (the whitespace between your tags!), which is almost never what you want.
  • parentElement vs parentNode. Same idea: parentElement skips the <body> / <html> special case. Prefer parentElement.

closest() is the star of this step. It walks up the tree from the element you give it until it finds one that matches your selector. You will use it for event delegation in the next step.

Use the demo cards. Card 1 has id card-1.
Hint 1
children is a live list — it is an HTMLCollection, not a plain array.
Hint 2
closest() starts at the element itself and walks up, so title.closest(".card") finds the card that contains the title.
Hint 3
Try card.querySelectorAll("*") to list every descendant element.
🎯 Tiny challenge
Without using closest, find the <h4> text of the card that a clicked element belongs to.
  • You start from the clicked element and walk up with parentElement until you hit a card.
  • Then you read the card's title.
  • Then confirm the short way with closest(".card").
✅ Checkpoint — you now know
  • parentElement, children, nextElementSibling — move around the tree.
  • closest(selector) walks up until it finds a match. Super useful.
  • children = elements only. childNodes includes text.
  • querySelector on an element searches that element's subtree only.
