DOM manipulation · Step 9

Data first, DOM second

The mindset shift that separates hobby DOM code from professional front-end code. Keep the truth in JavaScript, and let the DOM be a picture of it.

The idea

There are two ways to build a list in the browser.

Way A: edit the DOM as things happen

// add a row
list.append(makeRow("milk"));

// delete row 2
rows[1].remove();

// mark row 3 as done
rows[2].classList.add("done");

This works, but the DOM is now the only place the data lives. Ask "how many items are left?" and the only way to find out is to count elements. Change one thing in one place and another place silently drifts out of sync. It gets messy fast.

Way B: keep the data, redraw from it

let items = ["milk", "bread"];      // the truth

function render() {                // the DOM is a picture of the truth
  list.innerHTML = "";           // 1. clear
  items.forEach(function (text) {  // 2. rebuild from data
    const li = document.createElement("li");
    li.textContent = text;
    list.append(li);
  });
}

render();   // draw it

Now:

  • To delete an item you change the items array and call render() again.
  • To count what is left you ask the array: items.length. No DOM counting needed.
  • There is exactly one place that knows how a row looks: the render() function.

This is React's whole idea. React does exactly this, but it runs render() for you and only patches the differences. When you meet React in a few days, this step will already be familiar.

The three parts of every little app

Once you see it, every front-end app has the same three parts:

  1. State — the data. let items = [...]
  2. Actions — functions that change the state. function add(text) { items.push(text); render(); }
  3. Render — the function that draws the state onto the page.

Your job as a developer is mostly to keep those three in sync. When something looks wrong, ask: is the state right? is render() right? is the action calling render()?
