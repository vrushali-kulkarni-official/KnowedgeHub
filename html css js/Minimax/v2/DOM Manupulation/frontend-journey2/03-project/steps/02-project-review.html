Code review + how React thinks

We review your app together, look for the parts that should change, and then see how much smaller the same app becomes in React.

The questions I will ask about any DOM code

  1. Where is the truth? If I asked “how many tasks are left?” could you answer from the data alone? If the answer is “count the DOM nodes”, the truth is split in two places.
  2. Does every change go through render()? If you ever change the DOM directly somewhere, you have two sources of truth again.
  3. What happens if the element is missing? Any querySelector result used without a null check is a crash waiting to happen.
  4. Is the listener attached to something that might be replaced? If render() rebuilds the list, a listener attached to an old row is gone. That is why delegation wins.
  5. Is user data going into innerHTML? If yes, that is a bug waiting to happen.

The refactor

If your code grew a bit messy while building, these are the three moves that clean up almost any DOM app:

  1. Group by role, not by feature. Three labelled sections — state, actions, render — beat a pile of mixed functions.
  2. One function per action. addTodo, toggleTodo, deleteTodo. Each one changes the state and calls render(). That is the whole pattern.
  3. Get elements once at the top. const listEl = document.getElementById("todo-list") near the top, then use listEl everywhere. Do not query the same element inside every function.

The same app in React (JSX - do not worry, just look)

This is not JavaScript you can run in a browser tab. JSX is a syntax extension that React compiles. But look at the size of it — and at how close it is to the state + render pattern you already built.

import { useState } from "react";

export default function TodoApp() {
  // state -- exactly like your `let todos = []`
  const [todos, setTodos] = useState([]);
  const [text, setText] = useState("");

  // action
  function addTodo() {
    if (!text.trim()) return;
    setTodos([...todos, { id: Date.now(), text, done: false }]);
    setText("");
  }

  function toggle(id) {
    setTodos(todos.map(t => (t.id === id ? { ...t, done: !t.done } : t)));
  }

  function remove(id) {
    setTodos(todos.filter(t => t.id !== id));
  }

  // render -- React calls this for you
  return (
    <div>
      <ul>
        {todos.map(todo => (
          <li key={todo.id} className={todo.done ? "done" : ""} onClick={() => toggle(todo.id)}>
            {todo.text}
            <button onClick={() => remove(todo.id)}>x</button>
          </li>
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={addTodo}>Add</button>
      <span>{todos.filter(t => !t.done).length} left</span>
    </div>
  );
}

What React actually took off your hands

Compare the two versions line by line and you will find three things React gave you:

  1. No manual rendering. You change the state, React works out which parts of the page changed and patches only those. You never write list.innerHTML = "" again.
  2. No manual event delegation. React already listens once at the root. You write onClick on an element and it just works — including on elements that did not exist yet when the page loaded.
  3. No manual keys. You still write key={todo.id} — but that is the same idea you already learned with data-id.

Everything else — state, actions, events, ids, filter, map — is exactly the JavaScript you just learned. React is not a new language. It is a new way of running the code you can already write.

Where you are now

Look at that list again:

  • You know the JavaScript you need: variables, functions, arrays, objects, callbacks.
  • You know how to find elements, read and write them, create them, style them, delete them.
  • You know the pattern every modern front-end framework is built on: state → render.

Next stop: TypeScript (types for your data), then React, then Next.js. All three sit on top of what you just built with your own hands. You are further along than it feels right now.
