# 5.0 First: What exactly is an embedding?

Let's start from zero.

Suppose you have:

```text
"I like dogs."
```

An embedding model converts it into something like:

```text
[
    0.018,
    -0.231,
    0.741,
    0.019,
    ...
]
```

Maybe the vector has 768 dimensions.

So conceptually:

```text
"I like dogs."
      │
      ▼
embedding model
      │
      ▼
[0.018, -0.231, 0.741, ...]
```

That vector is an **embedding**.

The important point is:

> An embedding is a numerical representation of meaning in a particular embedding model's vector space.

You should not think:

> "The vector is the meaning of the sentence."

Instead think:

> "The vector is a coordinate in a learned semantic space."

---

# 5.0.1 Why are vectors useful?

Consider:

```text
A = "How do I reset my password?"
B = "I forgot my password. How can I change it?"
C = "What is the capital of France?"
```

A good embedding model should produce something conceptually like:

```text
A → [0.21, 0.11, -0.33, ...]
B → [0.22, 0.10, -0.30, ...]
C → [-0.71, 0.55, 0.42, ...]
```

A and B should be close.

C should be far away.

That's the fundamental idea behind semantic search.

---

# 5.0.2 Embeddings are not magic

This is extremely important.

An embedding model doesn't directly answer:

> "What is the answer to this question?"

It represents text in a vector space.

For example:

```text
question
   │
   ▼
embedding
   │
   ▼
search
   │
   ▼
relevant documents
   │
   ▼
LLM
   │
   ▼
answer
```

Therefore:

**Embedding ≠ LLM**

and

**Vector database ≠ knowledge database**

A vector database is fundamentally a system for finding vectors that are close according to some similarity/distance function.

# 5.1 Embeddings Interface

This is the first major LangChain abstraction you should understand.

LangChain gives you an embeddings interface roughly around:

```python

```

The conceptual interface is:

```python
class Embeddings:
    def embed_documents(self, texts: list[str]) -> list[list[float]]:
        ...

    def embed_query(self, text: str) -> list[float]:
        ...
```

The difference is extremely important.

Conceptually:

```text
3 texts
 │
 ├── document 1 → vector 1
 ├── document 2 → vector 2

```

Result:

```python

```

# 5.1.2 `embed_query`

When the user asks:

```text
"What database is good for vector search?"
```

you generally do:

```python
query_vector = embeddings.embed_query(
    "What database is good for vector search?"

```

This produces:

```text
query
 │
 ▼
query embedding
 │
 ▼
vector search
 │
 ▼
candidate documents
```

# 5.1.3 Why have two functions?

This isn't just an API design choice.

Retrieval models often distinguish between:

```text
DOCUMENT
```

and

```text
QUERY
```

because retrieval is asymmetric.

For example:

```text
Document:
"PostgreSQL supports vector similarity search through pgvector."

Query:
"How can PostgreSQL do vector search?"
```

These aren't the same type of text.

Some models therefore apply different instructions or optimization internally.

Google's current embedding API explicitly supports retrieval-specific task types with `gemini-embedding-001`, including `RETRIEVAL_DOCUMENT` and `RETRIEVAL_QUERY`. ([Google AI for Developers][2])

With the newer `gemini-embedding-2`, Google changed the mechanism: task instructions are supplied as part of the text formatting rather than through the old `task_type` field. ([Google AI for Developers][2])

That's a good example of why the distinction between:

```python
embed_documents()
```

and:

```python
embed_query()
```

matters.

---

# 5.1.4 Async embeddings

Modern applications are often asynchronous.

For example:

```python
vectors = await embeddings.aembed_documents(documents)
```

and:

```python
vector = await embeddings.aembed_query(query)
```

Whether the underlying implementation is truly asynchronous depends on the provider/integration.

This distinction matters.

You don't want to assume:

```python
await something()
```

automatically means:

> "The network call itself is natively asynchronous."

Some libraries implement async wrappers around synchronous operations.

For high-throughput services, always understand what your particular integration actually does.

# 5.1.5 Why batching matters

Suppose you have:

```text
100,000 chunks
```

and you call:

```python
embed_documents([one_chunk])
embed_documents([one_chunk])
embed_documents([one_chunk])
...
```

100,000 individual API requests can be terrible.

Instead:

```python
batch = documents[start:start + 100]
embeddings.embed_documents(batch)
```

Conceptually:

```text
100,000 chunks

      ↓

batch 1 → 100
batch 2 → 100
batch 3 → 100
...
batch 1000
```

Advantages:

* fewer network round trips
* better throughput
* lower overhead
* easier retry handling
* usually better utilization of the embedding provider

The exact ideal batch size depends on:

* provider limits
* token limits
* network
* machine memory
* model
* rate limits

Don't hard-code an enormous batch size simply because it works locally.

# 5.1.7 The most important rule in embeddings

You explicitly mentioned this:

> **Never mix embedding models in one index.**

Understand this deeply.

Imagine:

```text
Model A

"hello"
→ [0.1, 0.3, 0.7, ...]
```

Model B:

```text
"hello"
→ [0.9, -0.2, 0.1, ...]
```

These vectors live in different learned spaces.

You cannot meaningfully compare:

```text
Model A vector
```

against:

```text
Model B vector
```

just because both happen to contain 768 numbers.

Even worse, two models may produce the same dimension but completely different semantic geometry.

---

# 5.1.8 Dimension is not identity

This is a common beginner mistake.

These could both be 768 dimensional:

```text
Model A → 768
Model B → 768
```

That does **not** mean:

```text
vector_A <-> vector_B
```

is meaningful.

Think of it like coordinates.

Map A:

```text
(10, 20)
```

Map B:

```text
(10, 20)
```

The same coordinate values don't imply they're locations on the same map.

# 5.3.7 Exact search vs approximate search

Suppose you have:

```text
10 vectors
```

You can simply compare your query against every vector.

That's:

```text
exact nearest-neighbor search
```

Conceptually:

```text
query
  │
  ▼
compare against vector 1
compare against vector 2
compare against vector 3
...
compare against vector N
  │
  ▼
sort by distance
```

For millions of vectors, this gets expensive.

Therefore we use:

```text
approximate nearest neighbor
```

indexes.

The two pgvector indexes you should understand are:

```text
HNSW
IVFFlat
```

---

# 5.3.8 HNSW

HNSW stands for:

> Hierarchical Navigable Small World

Think of it as a graph.

You don't compare against every point.

Instead:

```text
query
 ↓
enter graph
 ↓
navigate toward promising region
 ↓
find nearest candidates
```

pgvector describes HNSW as giving a better speed/recall tradeoff than IVFFlat, at the cost of slower index construction and higher memory usage. ([GitHub][9])

---

# 5.3.9 HNSW `m`

Example:

```sql
CREATE INDEX document_chunks_embedding_hnsw_idx
ON document_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (
    m = 16,
    ef_construction = 64
);
```

`m` controls the maximum number of graph connections per layer.

Current pgvector defaults:

```text
m = 16
ef_construction = 64
```

A larger `ef_construction` generally improves recall while increasing build time and insertion cost. ([GitHub][9])

---

# 5.3.10 HNSW `ef_search`

This is a query-time parameter:

```sql
SET hnsw.ef_search = 100;
```

Higher:

```text
better recall
slower query
```

Lower:

```text
faster query
potentially lower recall
```

pgvector currently defaults `hnsw.ef_search` to 40. ([GitHub][9])

For one transaction/query:

```sql
BEGIN;

SET LOCAL hnsw.ef_search = 100;

SELECT ...;

COMMIT;
```

That's preferable to changing the global setting for every request.

---

# 5.3.11 IVFFlat

IVFFlat works differently.

Conceptually:

```text
all vectors
    │
    ▼
cluster into lists
    │
 ┌──┼──┬──┐
 ▼  ▼  ▼  ▼
L1 L2 L3 L4
```

For a query:

```text
query
 │
 ▼
find promising lists
 │
 ▼
search only those lists
```

This reduces the amount of work.

---

# 5.3.12 HNSW vs IVFFlat

The conceptual trade-off:

| Property                 | HNSW             | IVFFlat              |
| ------------------------ | ---------------- | -------------------- |
| Search quality           | Generally better | Generally lower      |
| Build speed              | Slower           | Faster               |
| Memory                   | Higher           | Lower                |
| Works before data exists | Yes              | No, training needed  |
| Tuning                   | `m`, `ef_*`      | `lists`, `probes`    |
| Typical modern default   | Very attractive  | Useful in some cases |

pgvector's current documentation specifically says HNSW has better query performance in speed/recall terms, while IVFFlat builds faster and uses less memory. ([GitHub][9])

For a new application:

> Start with HNSW unless you have a reason to prefer IVFFlat.

---

# 5.3.13 IVFFlat tuning

Current pgvector guidance suggests starting points approximately:

```text
up to 1M rows:
rows / 1000

over 1M:
sqrt(rows)
```

for the number of lists.

For probes:

```text
sqrt(lists)
```

is a starting point.

These are starting points, not universal truths. ([GitHub][9])

You should benchmark:

```text
recall
latency
CPU
memory
```

against your real dataset.

# 5.3.14 Distance metrics

This is critical.

Common choices:

```text
L2 distance
cosine distance
inner product
```

---

# 5.3.15 Cosine similarity

Cosine similarity asks:

> Are these vectors pointing in the same direction?

Formula:

```text
cosine(A, B) =
(A · B) / (||A|| ||B||)
```

So it focuses on direction rather than raw magnitude.

---

# 5.3.16 Inner product

Inner product:

```text
A · B
```

If vectors are normalized to length 1:

```text
cosine similarity
```

and:

```text
inner product
```

become closely related.

This is why vector normalization matters.

pgvector explicitly notes that if vectors are normalized, inner product can be used for better performance in exact search. ([GitHub][9])

---

# 5.3.17 The normalization trap

Imagine:

```text
A = [10, 0]
B = [1, 0]
```

Their direction is identical.

Cosine similarity:

```text
1
```

But inner product:

```text
10
```

So raw inner product incorporates vector magnitude.

After normalization:

```text
A = [1, 0]
B = [1, 0]
```

then:

```text
A · B = 1
```

Therefore:

> Know whether your embedding model outputs normalized vectors.

Do not casually switch:

```text
cosine
```

to:

```text
inner product
```

without understanding normalization.

---

# 5.3.18 Operators in pgvector

Conceptually:

```text
<->   L2 distance
<#>   negative inner product
<=>   cosine distance
```

For cosine search:

```sql
ORDER BY embedding <=> query_vector
```

Remember:

> pgvector often represents "distance", not "similarity".

Smaller distance is generally better.

# 5.3.20 Metadata filtering vs authorization

This is one of the most important security lessons of this module.

A vector store filter such as:

```python
filter={"tenant_id": tenant_id}
```

is useful.

But do **not** automatically think:

> "My vector store filter is my security boundary."

For a security-sensitive multi-tenant application, you should additionally enforce the tenant boundary at the database authorization layer.

That is where PostgreSQL Row-Level Security becomes powerful.

# 5.3.21 PostgreSQL Row-Level Security

PostgreSQL supports Row-Level Security:

```sql
ALTER TABLE document_chunks
ENABLE ROW LEVEL SECURITY;
```

Then:

```sql
CREATE POLICY tenant_isolation_policy
ON document_chunks
USING (
    tenant_id = current_setting('app.tenant_id')::uuid
);
```

Conceptually:

```text
application says:

tenant = ABC

        ↓

Postgres session:

app.tenant_id = ABC

        ↓

RLS:

only rows belonging to ABC
```

PostgreSQL's RLS is specifically designed to restrict which rows a user can access or modify. If RLS is enabled but no applicable policy allows access, PostgreSQL uses default-deny behavior. ([PostgreSQL][11])

This gives you:

```text
application filter
        +
database enforcement
```

instead of trusting only application code.

                         ▼
                     tenant_id
                         │

The application can do:

This defense-in-depth approach is much stronger.

# 5.7 Search Methods

Now we reach one of the most important retrieval concepts.

You have:

```python
vector_store.similarity_search(query)
```

But that is only one retrieval strategy.

---

# 5.7.1 Similarity search

Simple:

```text
query
 ↓
embedding
 ↓
nearest vectors
 ↓
top K
```

Example:

```python
docs = vector_store.similarity_search(
    query,
    k=5
)
```

This returns the five most similar documents.

This is your baseline.

---

# 5.7.2 Similarity search is not necessarily "the best documents"

Imagine your top five results are:

```text
result 1 → same paragraph
result 2 → almost same paragraph
result 3 → another copy of same idea
result 4 → another copy
result 5 → another copy
```

That's a problem.

You may want:

```text
result 1 → definition
result 2 → implementation
result 3 → security concern
result 4 → example
result 5 → limitation
```

That's where MMR comes in.

---

# 5.7.3 MMR

MMR:

> Maximal Marginal Relevance

The idea:

```text
relevance to query
+
diversity between selected documents
```

LangChain's current vector-store interface exposes:

```python
max_marginal_relevance_search(
    query,
    k=4,
    fetch_k=20,
    lambda_mult=0.5,
)
```

where `lambda_mult` controls the similarity-vs-diversity tradeoff. ([LangChain Reference Docs][17])

---

# 5.7.4 `fetch_k`

This is frequently misunderstood.

Suppose:

```python
k = 5
fetch_k = 20
```

This means:

```text
retrieve 20 candidates
       ↓
apply MMR
       ↓
return 5
```

Not:

```text
retrieve 5
```

This extra candidate set gives MMR enough options to increase diversity.

---

# 5.7.5 `lambda_mult`

Conceptually:

```text
1.0
```

means:

```text
favor similarity
```

while:

```text
0.0
```

means:

```text
favor diversity
```

and:

```text
0.5
```

is approximately a balance.

LangChain's current documentation describes exactly this behavior. ([LangChain Reference Docs][17])

---

# 5.7.6 Score threshold

Sometimes the correct answer is:

> "None of these documents are sufficiently relevant."

Suppose your system returns:

```text
result A → very relevant
result B → relevant
result C → weak
result D → unrelated
```

With a fixed:

```text
top 5
```

you might still return poor documents.

Instead:

```text
only return results
whose relevance >= threshold
```

LangChain supports the search type:

```text
similarity_score_threshold
```

in its vector-store interface. ([GitHub][18])

This is particularly useful for:

```text
"What is our company refund policy?"
```

If your database contains no refund policy, you don't want to blindly return unrelated documents.

---

# 5.7.7 Score thresholds are tricky

Do not assume:

```text
score > 0.8
```

universally means:

```text
good result
```

because score semantics depend on:

```text
distance function
embedding model
normalization
vector store
relevance transformation
```

Therefore:

> Thresholds must be calibrated experimentally.

Create a validation dataset:

```text
query
relevant docs
irrelevant docs
```

Then measure:

```text
precision
recall
MRR
nDCG
```

and determine a threshold empirically.

---

# 5.7.8 Upsert vs re-add

Suppose you already have:

```text
document 123
```

and the document changes.

Bad approach:

```text
add new copy
```

while leaving the old copy.

You may now have:

```text
document 123 old
document 123 new
```

This causes duplicates.

Instead you need a stable identity:

```text
document_id
chunk_id
```

and an update strategy.

Conceptually:

```text
document updated
        │
        ▼
remove old chunks
        │
        ▼
generate new embeddings
        │
        ▼
insert/upsert new chunks
```

---

# 5.7.9 Stable IDs

Use IDs like:

```text
document UUID
```

and:

```text
chunk UUID
```

or deterministic IDs like:

```text
sha256(document_id + chunk_index + content_hash)
```

This enables idempotent ingestion.

For example:

```text
tenant-1/document-7/chunk-12
```

Then running ingestion twice doesn't blindly duplicate data.

---

# 5.7.10 Delete-by-filter

Suppose a user deletes document:

```text
document_id = doc-123
```

You need:

```text
DELETE
WHERE document_id = doc-123
```

across the vector store.

This is another place where metadata design matters.

If you don't store:

```text
document_id
```

you will have trouble deleting its chunks later.

---

# 5.8 MultiVectorRetriever

Now we go into more advanced RAG architecture.

Imagine your document is:

```text
200-page PDF
```

You don't want to embed the whole PDF as one giant vector.

Instead:

```text
Parent document
        │
        ├── child chunk 1
        ├── child chunk 2
        ├── child chunk 3
        └── child chunk 4
```

You embed:

```text
child chunks
```

but return:

```text
parent document
```

This is the idea behind `MultiVectorRetriever`.

Current LangChain describes it as retrieving small embedded child chunks while returning the corresponding parent documents. ([LangChain Reference Docs][19])

---

# 5.8.1 Why is this useful?

Suppose:

```text
parent:
Chapter 7 — Authentication
```

and:

```text
child chunk:
PKCE requires a code verifier...
```

The child chunk gives excellent search precision.

But your LLM may benefit from more surrounding context from the parent.

So:

```text
search child
      │
      ▼
find parent ID
      │
      ▼
load parent
      │
      ▼
send richer context to LLM
```

This is a very important RAG pattern.

---

# 5.8.2 Multi-vector doesn't necessarily mean "multiple embedding models"

This is another conceptual trap.

"MultiVector" here can mean:

```text
multiple vectors representing one parent document
```

For example:

```text
parent document
       │
 ┌─────┼─────┐
 ▼     ▼     ▼
chunk  chunk  chunk
 1      2      3
 │      │      │
vector vector vector
```

The parent is represented by multiple child vectors.

It does **not** necessarily mean:

```text
embedding model A
+
embedding model B
```

# 5.9 Index Lifecycle

This is where beginner tutorials usually stop.

Production systems cannot stop at:

```text
embed
store
search
```

You need lifecycle management.

---

# 5.9.1 What happens when you change embedding models?

Suppose version 1:

```text
model = bge-m3
dimension = 1024
```

You indexed:

```text
10 million chunks
```

Then you decide:

```text
model = Gemini Embedding 2
dimension = 768
```

You cannot simply:

```text
replace a few vectors
```

and keep comparing the old and new vectors together.

The vector spaces are incompatible.

Google explicitly notes that `gemini-embedding-001` and `gemini-embedding-2` use incompatible embedding spaces; moving between them requires re-embedding existing data. ([Google AI for Developers][2])

---

# 5.9.2 Correct migration strategy

Use:

```text
v1 index
v2 index
```

instead of destroying v1 immediately.

For example:

```text
documents
    │
    ├── embedding_v1
    │
    └── embedding_v2
```

or separate tables:

```text
chunks_v1
chunks_v2
```

or separate collections:

```text
knowledge_base_v1
knowledge_base_v2
```

Then:

```text
populate v2
        ↓
evaluate v2
        ↓
switch traffic
        ↓
retire v1
```

This is much safer.

---

# 5.9.3 Blue/green vector index migration

This is a production-quality pattern.

```text
                documents
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
      index-v1             index-v2
          │                   │
       current             testing
```

After validation:

```text
                    documents
                        │
                        ▼
                    index-v2
                        │
                     traffic
```

Then delete:

```text
index-v1
```

later.

This dramatically reduces deployment risk.

---

# 5.9.4 Backups

For PostgreSQL + pgvector:

```bash
pg_dump ...
```

backs up your PostgreSQL database.

Important:

> The embedding vector is data.

Therefore your database backup should include the vector data.

You don't want to discover after a failure:

```text
Postgres restored
```

but:

```text
vector data gone
```

---

# 5.9.5 Rebuilding vectors vs restoring vectors

There are two possible disaster-recovery strategies.

### Strategy A — backup vectors

```text
backup DB
↓
restore DB
↓
vectors immediately available
```

### Strategy B — reconstruct vectors

```text
backup source documents
↓
restore source documents
↓
re-run embedding pipeline
↓
rebuild index
```

Strategy B can be useful, but can be expensive and time-consuming.

For production, I prefer:

```text
backup source documents
+
backup metadata
+
backup vector store
+
versioned ingestion pipeline
```

---

# 5.9.6 Dimension migrations

Suppose:

```text
vector(768)
```

becomes:

```text
vector(1024)
```

You can't simply alter the existing data and magically turn 768-dimensional vectors into meaningful 1024-dimensional vectors.

A new embedding model generally means:

```text
new embedding space
```

Therefore create a new index/table/collection.

# 5.10 Connection Management in FastAPI

This is extremely important for your AI SaaS.

Bad architecture:

```python
@app.get("/search")
async def search():
    vector_store = create_vector_store()
    return await vector_store.search(...)
```

Every request potentially does:

```text
request
 ↓
create DB connection/client
 ↓
initialize vector store
 ↓
search
 ↓
destroy
```

That's wasteful.

---

# 5.10.1 Better architecture

Create long-lived resources during application startup.

Conceptually:

```text
FastAPI starts
      │
      ├── DB engine
      ├── connection pool
      ├── embedding client
      └── vector store
             │
             ▼
        reused by requests
```

---

# 5.10.2 FastAPI lifespan

Modern FastAPI uses lifespan management.

Conceptually:

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup
    app.state.vector_store = ...

    yield

    # shutdown
    await ...


app = FastAPI(lifespan=lifespan)
```

This is where your long-lived clients belong.

---

# 5.10.3 Singleton doesn't mean global spaghetti

You may hear:

> "Use a singleton."

That can mean different things.

Bad:

```python
GLOBAL_VECTOR_STORE = ...
```

with mysterious import-time side effects.

Better:

```text
application lifespan
       │
       ▼
one managed instance
       │
       ▼
available through app state/dependency injection
```

The important idea is:

> one application-managed resource, with explicit startup/shutdown.

---

# 5.10.4 Database connection pooling

Suppose your application has:

```text
100 requests
```

You don't want:

```text
100 database connections
```

Instead:

```text
FastAPI
   │
   ▼
connection pool
 ┌─┬─┬─┬─┬─┐
 │ │ │ │ │ │
 ▼ ▼ ▼ ▼ ▼ ▼
DB connections
```

Requests borrow connections.

Then return them to the pool.

---

# 5.10.5 Why pooling matters

Without pooling:

```text
connect
authentication
TLS
session setup
query
disconnect
```

repeatedly.

With pooling:

```text
borrow existing connection
query
return connection
```

which is much cheaper.

The current `langchain-postgres` ecosystem uses Postgres engines and supports modern async drivers, so it fits naturally into this application-lifetime architecture. ([GitHub][1])

---

# 5.10.6 Embedding clients also need lifecycle thinking

Suppose you're using:

```text

```

then your embedding client may be relatively lightweight.

With API-based providers you may have:

```text

connection pools
retry configurations
rate limiting
```

Do not instantiate everything inside each request.

# 5.17 Similarity vs MMR vs hybrid vs reranking

These concepts must not be confused.

### Similarity

Answers:

> "Which documents are closest to my query?"

```text
query
 ↓
nearest neighbors
```

### MMR

Answers:

> "Which documents are relevant while avoiding too much duplication?"

```text
query relevance
+
diversity
```

### Hybrid

Answers:

> "Can we combine semantic understanding with lexical/exact matching?"

```text
dense
+
sparse
```

### Reranker

Answers:

> "Among these candidates, which are truly the best matches?"

```text
retrieve 50
    ↓
reranker
    ↓
top 5
```

A mature RAG system might use all four:

```text
Hybrid retrieval
      ↓
MMR / candidate selection
      ↓
reranking
      ↓
top context
```

# 5.18 Why you should not immediately retrieve only 3 documents

A common beginner architecture:

```text
query
 ↓
vector search
 ↓
k=3
 ↓
LLM
```

This can be fragile.

A stronger architecture:

```text
query
 ↓
retrieve 30
 ↓
filter
 ↓
MMR/hybrid
 ↓
rerank
 ↓
top 5
 ↓
LLM
```

The important concept is:

> Retrieval and final context selection are two different problems.

# 5.19 Current vs Old LangChain APIs

This deserves its own section because LangChain changes quickly.

| Older/common tutorial pattern                      | Modern direction                            |
| -------------------------------------------------- | ------------------------------------------- |
| `PGVector`                                         | **`PGVectorStore`**                         |
| Putting every integration in `langchain-community` | Prefer dedicated integration packages       |
| Old `langchain` monolithic imports                 | Separate `langchain-*` integration packages |
| Manual provider-specific embedding glue            | LangChain `Embeddings` interface            |
| Recreate DB/vector clients per request             | Application-lifetime clients/pools          |
| Treat metadata filtering as sole tenant security   | Filtering + DB-level authorization/RLS      |
| Mix vectors from different embedding models        | One embedding contract per index            |
| Rebuild production index destructively             | Versioned/blue-green re-indexing            |

The `langchain-community` package is specifically described by LangChain's own skill metadata as not semver-stable, and LangChain recommends dedicated integration packages where they exist. ([GitHub][5])

You will still encounter tutorials containing things like:

rather than old `PGVector` usage. ([GitHub][1])

# 5.23 The five concepts I especially want you to remember

If you remember nothing else from this module, remember these:

### 1. An embedding model defines a vector space

Therefore:

```text
don't mix embedding models
```

inside one index.

---

### 2. Vector dimensions are part of your schema

```text
768
```

isn't merely an implementation detail.

It's part of the contract between:

```text
embedding model
```

and:

```text
vector database
```

---

### 3. Retrieval has multiple stages

Don't think only:

```text
query → vector search
```

Think:

```text
query
 ↓
candidate retrieval
 ↓
filtering
 ↓
hybrid / MMR
 ↓
reranking
 ↓
final context
```

---

### 4. Metadata is just as important as vectors

Your embedding tells you:

> semantic relevance

Your metadata tells you:

> business relevance

For example:

```text
semantic:
"authentication"

metadata:
tenant = ABC
language = en
product = chatbot
version = 3
permission = admin
```

A production retrieval system needs both.

---

### 5. Vector indexes are versioned infrastructure

Treat:

```text
embedding model
chunking
dimensions
distance metric
index configuration
```

as versioned components.

Don't think:

> "The vectors are just stored data."

Think:

> "The vector index is a generated artifact produced by a particular retrieval pipeline."

That mental model becomes extremely important once your RAG system grows.

## One important modern note about Gemini

For your preference toward Gemini, the current Gemini embedding family is worth knowing even if you start locally. As of September 2026, Google's current documentation identifies **`gemini-embedding-2` as the latest stable embedding model**, with 128–3072 output dimensions and recommended sizes of 768, 1536, and 3072. Google's docs also explicitly say that moving from `gemini-embedding-001` to `gemini-embedding-2` requires re-embedding existing data because the embedding spaces are incompatible. ([Google AI for Developers][2])

For **your actual learning project**, however, I would start with **BGE-M3 + pgvector + `PGVectorStore`**, then reproduce the same retrieval pipeline with **Qdrant**, and finally swap the embedding implementation to **Gemini Embedding 2**. That sequence teaches the underlying concepts instead of hiding them behind a managed API.

The next practical step should be **5.1 + 5.2 hands-on**: we can build the embedding layer from scratch using `uv`, BGE-M3/Hugging Face, Ollama, and Gemini, inspect the actual vectors, compare dimensions and normalization, benchmark batching, and then plug the exact same `Embeddings` object into pgvector.
